## 작업 과정에서 배운 것

### 1. BaseEntity 추상화

공통적으로 사용되는 `createdAt`, `updatedAt`, `deletedAt` 같은 필드를 각 엔티티마다 반복적으로 선언하는 대신, `BaseEntity`로 정의하고 모든 엔티티 클래스에서 상속받는 방식으로 추상화했다.

이로 인해 중복 코드가 크게 줄어들었다. 변경이 필요한 경우에도 한 곳만 수정하면 전체 엔티티에 반영되므로 유지보수성이 크게 향상되었다.

또한 소프트 딜리트(Soft Delete) 기능도 `BaseEntity` 안에서 구현할 수 있었다.

`deletedAt` 에 삭제 동작을 수행한 시간을 기록함으로써, 실제 데이터를 삭제하지 않고 논리적으로 삭제 처리했다. 이를 모든 엔티티 클래스에 일관되게 적용했다.

공통 동작을 `BaseEntity`에 정의함으로써 실수로 데이터가 삭제되지 않거나, 조건 누락으로 삭제된 데이터가 조회되는 문제를 사전에 방지할 수 있었다.

## 어려웠던 점

### 1. 다중선택 항목을 어떻게 표현할지

도우미의 강점(`strength`)이나, 리뷰의 좋았던 점(`positive_feedback`)처럼 다중 선택이 가능한 항목들을 어떻게 나타낼지 고민했다. 다중 선택은 카테고리가 정해져 있고 그 중에서 여러 개의 항목을 선택할 수 있는 구조였다.

각 강점 항목을 별도의 테이블로 관리하고, 도우미와의 다대다(M:N) 관계를 정의하는 구조를 고려했다. 즉, `Helper`, `Strength`, 그리고 중간 테이블인 `Strength_Choice`를 두는 방식이다.

하지만 테이블 수가 늘고, 연관 관계가 복잡해진다는 문제가 있었다. 

강점 항목은 자주 변경되거나 늘어나는 요소도 아니고, 수도 많지 않기 때문에 굳이 별도의 테이블로 분리하는 것은 오버엔지니어링이라고 판단했다.

그래서 강점 정보를 도우미 테이블의 컬럼으로써 관리하는 방식으로 변경했다. 처음에는 `"강점1,강점2"`와 같은 콤마로 구분된 문자열 형태로 저장하는 방법을 고려했지만, 표현력과 확장성을 고려해서 JSON 컬럼으로 저장하는 방식을 채택했다. 테이블 간의 연관 관계를 단순화하고, 불필요한 테이블들을 줄일 수 있었다.

# 2. 회고

## Keep

### **1. 애매한 부분을 빠르게 소통해서 시행착오를 줄였다**

- 내가 전담하고 있는 작업이라고 하더라도, 팀원들 사이에서 다양한 의견의 나올 수 있을 것 같은 부분은 즉시 팀원들에게 공유하고 의견들을 들어보았다.
- 특히 도메인 설계는 프로젝트 전체에 많은 영향을 줄 수 있는 부분은 더 신경써서 사람들의 생각을 확인했다.
- 팀원들 모두 각자의 의견을 말해주었고, 피드백을 주고 받은 끝에 최선의 방식을 결정할 수 있었다.
- 작업을 모두 마무리한 뒤에 공유했다면, 뒤늦게 알게 된 이견들로 인해 불필요한 시행착오를 겪었을 수도 있다. 빠른 문제 상황 공유를 통해 큰 우여곡절 없이 작업을 진행할 수 있었다.

### 2. 새로운 작업 방식에 빠르게 적응하고 팀의 흐름에 맞췄다

- 브랜치 관리 방식, 커밋 메세지 형식, 이슈 관리 방식 등, 프로젝트 동안 지키기로 약속한 작업 방식들이 있었다.
- 처음 해보는 방식이 많아서 걱정이 되기도 했지만, 다른 팀원들이 수행한 내용들을 먼저 관찰하고, 참고했다. 중간중간 헷갈리는 부분이 있으면 혼자 고민하기보다는, 팀원들에게 물어보면서 빠르게 작업을 수행했다.
- 몇 차례 직접 해보고나니 금방 익숙해질 수 있었다. 덕분에 흐름을 끊지 않고, 팀의 방식에 따라 원활하게 작업을 수행할 수 있었다.

<br>

## Problem

### **1. 해야 할 작업이 많아지면서 문서화한 내용들이 여러 곳에 분산되고 있다**

- 개인 회고나 학습 기록 등의 개인 문서는 물론, 종합프로젝트 관련된 문서도 기록하고 있다.
- 기록하는 채널 또한 Notion, GitHub 등 다양하다 보니, 정리한 내용들이 여러 곳에 흩어지고 있다는 느낌을 받았다.
- 시간이 지나면, 어떤 내용을 어디에 기록했는지 기억하고 찾기가 어려워질 것 같다.

### 2. 계획했던 것보다 작업 수행이 조금 지연되었다

- 오늘은 엔티티 클래스를 완성하고 마무리하려 했지만, ERD 레벨에서의 수정 사항이 발생하면서 흐름이 뒤로 밀렸다.
- 예상하고 계획했던 작업량을 끝마치지 못했다.

## Try

### **1. 한 눈에 확인할 수 있는 공간을 만들어 두자**

- 정리된 내용을 모아두는 중심 공간을 만들자

- 그 과정에서 얻은 인사이트를 다음 일정을 잡을 때 반영하면서, 시간에 대한 감각을 길러보자.

# 3. 학습내용

## AWS 계정 및 권한 관리 (IAM)

### 루트 유저 vs IAM 관리자(admin 계정)

- **루트 유저**
    - AWS 계정 생성 시 자동으로 생김
    - 모든 권한 보유 + 결제 관련 작업 전용 권한 일부 보유
    - 보안적으로 취약하므로 로그인 지양
- **IAM 관리자(admin 계정)**
    - 루트 유저로 생성한 별도의 관리자 계정
    - 루트와 거의 동일한 권한
    - 보안 정책 적용 가능 → 접근 제어 및 추적 가능

### IAM 구성요소

| 구분 | 설명 |
| --- | --- |
| User | 인증 주체 (개별 사용자) |
| Group | IAM User의 집합, 권한을 묶어서 관리 가능 |
| Role | 특정 권한을 위임하기 위한 역할(user 또는 AWS 리소스에 할당 가능) |
| Policy | JSON 형식의 권한 정의 문서(인증 주체에 권한 부여) |
- **Group**: policy를 구성원 전체에 상속
- **Role**: 일시적으로 기존 policy를 덮어씌움 (사라지면 원래대로 복원)
- **Policy**: 인가(Authorization)의 핵심 → `JSON 형식`으로 작성하여 재사용 가능

### AWS API 사용 방법

| 방법 | 설명 |
| --- | --- |
| Console | 웹 브라우저 기반 GUI |
| CLI | 명령어 기반 AWS 조작 도구 |
| SDK | 프로그래밍 언어(Java/Python 등) 기반 API 호출 |

### Role을 통해 권한 부여 가능한 대상

- IAM User
- AWS 리소스 (예: EC2 인스턴스 → 다른 AWS API 호출 시 필요)

## AWS Global Infrastructure

| 구성요소 | 설명 |
| --- | --- |
| Region | AWS 서비스가 제공되는 물리적 지역 (도시 단위, 이름과 실제 위치는 다를 수 있음) |
| Availability Zone(AZ) | 하나의 Region은 최소 2개 이상의 AZ로 구성AZ는 독립된 물리적 데이터센터 집합 |

## AWS VPC (Virtual Private Cloud)

- Region 내부에서 격리된 네트워크 영역
- 사용자가 직접 IP 대역, 서브넷, 라우팅, 방화벽 등을 설정

### 서브넷(Subnet)

- VPC 내부에서 IP 대역을 나누는 단위
- 각 서브넷은 하나의 AZ에 소속
- 서브넷 간 IP 대역이 겹치지 않게 구성
- 고가용성 확보 → 서로 다른 AZ에 인스턴스를 분산 배치

### CIDR

- 예시: `10.0.0.0/16`
    - 앞 16비트는 고정 → 나머지 16비트를 할당 가능 → 65,536개 IP 사용 가능
- IP 범위는 2^ (32 - 마스킹 비트 수)

```
Region > VPC > Subnet
         └> AZ > Subnet
```

- 서브넷은 반드시 특정 AZ에 속해야 함
- 고가용성을 위해 서로 다른 AZ에 위치한 서브넷을 이용하는 것이 일반적
