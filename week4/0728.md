## 작업 과정에서 배운 것

### 1. 체계적인 프로젝트 진행

지금까지의 프로젝트들에서는 일정 관리나, 코드 관리 과정을 수동으로 해왔던 것 같다.

이번 종합프로젝트를 진행하면서, 이슈나 PR 관리 등을 도구로 자동화시키는 것을 처음으로 경험했다. 템플릿도 사전에 정의해두고 워크플로우로 자동화하여 사용하는 것을 보니 정말 신기했다.

- 처리해야 할 이슈들을 미리 등록
- 이슈를 스프린트에 배정
- 진행 상태를 Kanban 보드로 추적
- 관련 PR과 연결시켜, 병합 시 자동으로 이슈를 Close

위와 같은 프로세스로 프로젝트를 진행할 수 있게 되었다. 확실히 일정을 체계적으로 관리할 수 있고, 팀원들 모두가 프로젝트의 진행 상황에 대해 명확하게 파악할 수 있겠다고 생각했다.

처음으로 해보는 방식이기 때문에 아직 익숙하지는 않지만, 이번 기회에 잘 보고 배워서 다음에는 먼저 직접 적용해볼 수 있도록 노력하고 싶다.

## 어려웠던 점

### 1. ERD 및 테이블 구조 설계의 고민

직접 ERD를 설계하면서, 데이터 정규화를 어느 정도까지 적용할지가 가장 고민이었다.

중복 데이터를 제거하고 다른 테이블을 참조하도록 하면, 데이터의 일관성을 지킬 수 있고, 유지보수도 수월해진다. 하지만 반대로, 조회 쿼리가 복잡해지고 성능이 저하될 수 있다는 우려도 있었다.

또한, 두 테이블 간에 연관 관계를 설정할 때, 어느 쪽이 외래키를 갖는 것이 더 적절한 구조인지도 어려운 문제였다.

와이어프레임을 기반으로 서비스의 흐름을 따라가며, 최대한 자연스럽고 효율적인 구조를 설계해보려고 노력했다. 이후 완성된 ERD를 팀원들에게 공유하고, 고민했었던 부분들을 피드백 받으며 여러 차례 조율해나갔다.

정답이 정해진 활동이 아니기 때문에 오히려 더 어려운 작업이라고 느껴졌다. 서비스의 특성을 이해하고, 그에 맞는 타당한 설계를 하는 것이 가장 중요하다는 것을 깨달았다. 도메인 모델링에 대한 경험을 더 많이 쌓으면서, 이러한 기준을 더 빠르고 명확하게 판단할 수 있는 감각을 길러야겠다고 생각했다.

# 2. 회고

## Keep

### **1. 모르는 건 솔직하게 모른다고 말하기**

- 프로젝트를 진행하다보면 생소한 기술이나 개념을 자주 접하게 된다.
- 솔직히 모르는 내용이 나오면 괜히 흐름을 끊을까봐 말을 꺼내기 망설여지거나, 민망한 마음이 앞서기도 한다.
- 하지만, 회의 중에 가볍게 언급된 내용이라도, 대충 넘어가지 않고 정확하게 알기 위해 물어보는 태도를 가지려고 하고 있다.
- 이런 작은 모호함들이 쌓이다보면, 당장의 대화나 더 나아가서는 프로젝트의 흐름을 점점 따라가지 못하게 된다. 팀 전체를 위해서라도 확실하게 짚고 넘어가는 것이 더 현명한 자세이다.
- 앞으로도 모르는 것이 있으면 부끄러워하지 않고, 솔직하게 말해서 그 순간에 배우려는 자세를 유지하고 싶다.

<br>

## Problem

### **1. 새롭게 익혀야 할 규칙들이 많아졌다**

- 이슈 및 PR 관리, 프로젝트 디렉터리 구조, 커밋 메시지 규칙 등 팀 차원에서 정해진 다양한 약속들이 생겼다.
- 그중 몇 가지는 이전까지 한 번도 접해본 적이 없어서 생소하게 느껴졌고, 나의 미숙함이 다른 팀원들에게 피해를 주지 않을까 걱정이 되기도 했다

### 2. 구현해야 할 기능의 양이 많다

- ERD를 설계하면서 다른 팀들에 비해 도메인의 수가 많고 테이블 간의 관계도 복잡하다는 점을 체감했다.
- 이로 인해 프로젝트 전반의 사이즈 자체가 꽤 큰 편이라는 것을 인식하게 되었고, 일정과 리소스 관리가 더 중요해질 것 같다는 생각이 들었다

<br>

## Try

### **1. 빨리 익숙해지자**

- 처음 접해보는 방식들이 많지만, 반복적으로 사용해보면서 몸에 익히는 것이 가장 중요하다.
- 사소한 실수가 생기더라도, 초반에 많이 시도해보면서 실전 감각을 키우는 것이 낫다.
- 이상하거나 헷갈리는 부분은 바로 질문하고 확인 받으면서, 빠르게 적응해보자.

### 2. 제한된 일정을 효율적으로 활용하자

- 기능은 많고 일정은 제한적인 만큼, 팀원 간의 역할 분담과 일정 조율이 매우 중요하다.
- 프론트엔드 / 백엔드 사이는 물론, 같은 파트 내에서도 서로의 작업을 기다리는 일이 없도록, 우선순위를 명확히 해서 할 일을 병렬적으로 처리할 수 있도록 해야겠다.
- 각자의 진행 상황을 자주 공유하면서, 프로젝트가 병목 없이 매끄럽게 흘러갈 수 있도록 신경 쓰자.

# 3. 학습내용

## Facade Pattern

- 복잡한 서브시스템을 간단한 인터페이스로 감싸서, 클라이언트가 더 쉽게 사용할 수 있도록 해주는 디자인 패턴

### 목적

- 클라이언트가 내부 구현을 몰라도 되게 함
- 복잡한 시스템에 단순한 접근점(Facade) 을 제공
- 의존성을 줄이고, 결합도를 낮춤

### 구조

```
[Client]
   |
   v
[Facade] -------> [SubsystemA]
               \-> [SubsystemB]
               \-> [SubsystemC]
```

- **Client**: 시스템을 사용하는 외부 코드
- **Facade**: 서브시스템을 감싼 단순한 API
- **Subsystem**: 실제로 일을 하는 클래스들

### 예시 (간단한 홈시어터 시스템)

```java
class DVDPlayer {
    void on() { System.out.println("DVD ON"); }
    void play() { System.out.println("Playing DVD"); }
}

class Projector {
    void on() { System.out.println("Projector ON"); }
}

class Amp {
    void on() { System.out.println("Amp ON"); }
    void setVolume(int level) { System.out.println("Volume: " + level); }
}

// Facade
class HomeTheaterFacade {
    private DVDPlayer dvd;
    private Projector projector;
    private Amp amp;

    public HomeTheaterFacade(DVDPlayer dvd, Projector projector, Amp amp) {
        this.dvd = dvd;
        this.projector = projector;
        this.amp = amp;
    }

    public void watchMovie() {
        System.out.println("Get ready to watch a movie...");
        projector.on();
        amp.on();
        amp.setVolume(5);
        dvd.on();
        dvd.play();
    }
}

```

```java
public class Main {
    public static void main(String[] args) {
        HomeTheaterFacade facade = new HomeTheaterFacade(
            new DVDPlayer(), new Projector(), new Amp()
        );
        facade.watchMovie();
    }
}
```

### 적용하기 좋은 상황

- 복잡한 라이브러리나 API를 감싸고 싶을 때
- 시스템 내부 구현을 외부에 노출하지 않도록 하고 싶을 때
- 여러 개의 객체를 함께 사용하는 일련의 작업을 묶고 싶을 때

### 장점

- 사용이 간편해짐 (단일 진입점 제공)
- 결합도 감소 (클라이언트는 내부 클래스를 몰라도 됨)
- 유지보수성 향상

### 단점

- Facade가 모든 기능을 감싸지 못하면 결국 내부 클래스를 직접 써야 함
- 지나치게 많은 책임이 Facade에 몰릴 수 있음 (God Object 위험)
