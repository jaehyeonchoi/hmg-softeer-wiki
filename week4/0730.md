## 작업 과정에서 배운 것

### 1. 변동이 생길 수 있는 작업은 너무 마무리 작업까지 해두지 말자

ERD 설계 후, 다이어그램을 보기 좋게 정리하고 싶어서 테이블의 위치와 순서를 정성스럽게 배치했다.

하지만, 종합프로젝트 회의를 거치면서 와이어프레임에 변동 사항이 있었고, 이에 따라 ERD도 수정이 불가피했다. 테이블 간의 관계도 일부 변경되었기 때문에, 결국 전체적인 구조를 다시 손봐야 했다.

괜히 마무리 작업까지 빠르게 해두었다가, 불필요한 작업이 늘어가고 시간을 낭비하게 된 것 같다. 추후 수정 가능성이 남아있는 작업들은, 완성도를 추구하기보다는 유연함을 최대한 유지하는 것이 더욱 중요하다는 것을 느꼈다.

<br>

## 어려웠던 점

### 1. AWS 네트워크 관련 개념

수업 시간에 AWS 글로벌 인프라의 구조에 대해 공부했다.

특히 VPC, 서브넷, 라우팅 테이블, 인터넷 게이트웨이 등의 개념을 다뤘는데, 처음 접하는 내용이 많았다. 나는 이전까지 EC2와 RDS 인스턴스를 간단하게 써본 경험밖에 없어서 다소 낯설게 느껴졌다.

수업 내용을 따라가면서 대략적인 흐름은 이해했지만, "이걸 왜 써야 하는지", "어떤 상황에서 어떤 식으로 활용할 수 있는지"에 대해서는 확 와닿지 않았다. 내용이 머릿속에 들어왔는데, 들어온 지식을 내가 온전히 소화시키지 못하고 있다는 느낌이 들었다.

개념에 대해 아는 것으로 끝나지 않고, 앞서 말한 의문들에 대해 더 알아볼 필요가 있겠다고 생각했다. 그런 개념들이 등장한 배경이나, 활용되는 방식에 대해 찾아보면서 흐름을 이해하고 싶다.

# 2. 회고

## Keep

### **1. 같이 있는 팀원들에게 감사하는 마음**

- 오늘은 종합 프로젝트에서 기획/디자인 팀원들과의 협업이 마무리되는 날이었다.
- 지난 3주 동안 모두들 열심히 작업해주신 덕분에, 개발에 앞서 걱정해야 할 부분들이 거의 없었고, 방향 설정에도 많은 도움이 됐다. 프로젝트 초반에 탄탄한 기획을 해주신 덕분에, 개발팀은 앞으로의 작업을 보다 안정적으로 이어갈 수 있을 것 같다.
- 특히나 기획/디자인 팀원분들은 이 작업이 본인의 평가에 반영되지 않는데도 불구하고, 그렇게 열정적으로 참여해주셔서 감사한 마음이 더욱 크다.
- 앞으로 남은 한 달은 개발팀 중심으로 진행될텐데, 항상 함께 하는 팀원들에게 감사함을 가지면서 협업을 이어가고 싶다.

### **2. 팀원들과 함께 즐기는 것도 중요하다**

- 함께 종합프로젝트를 하는 마지막날이었기 때문에, 일과가 끝나고 회식자리를 마련했다.
- 프로젝트와는 관계없는 잡담부터, 프로젝트 중 느꼈던 솔직한 생각들까지, 다양한 대화를 나눌 수 있었다. 특히 디자인 팀의 서연님과는 집 방향이 같아서, 돌아가는 길에 오랫동안 이야기할 수 있었다.
- 회의 중에는 잘 할 수 없었던 대화도 많이 할 수 있었고, 팀원들이 어떤 사람인지 더 깊이 알 수 있었던 것 같다. 함께 일하는 기간이 끝났기 때문에 더 편하게 이야기할 수 있었던 부분도 있지만, 이런 기회를 프로젝트 초반부터 많이 가졌더라면 어땠을까 하는 아쉬움도 남았다.
- 남은 기간 개발 팀원들과 프로젝트를 진행하면서, 어려움도 있을 것이고 시간적으로도 촉박하겠지만, 그래도 중간중간 같이 이야기하고 웃을 수 있는 시간을 많이 만들면서 즐겁게 진행하고 싶다.

<br>

## Problem

### **1. 프로젝트 세팅을 해본 경험이 부족하다**

- 이번 주 수업을 통해, 프로젝트에 앞서 AWS 관련 설정해야 될 요소들을 배웠다. 그동안 이런 것들을 직접 세팅해 본 경험이 많이 없었다는 것을 느꼈다.
- 직접 경험을 하면서만 얻을 수 있는 지식들이 분명히 있다고 생각한다.
- 평소 여유가 있을 때 의식적으로 시도해보려는 노력을 하지 않으면, 막상 실전이 되었을 때 더욱 부담이 되고 힘들어진다는 것을 알 수 있었다.

### 2. 커밋 관련하여 실수를 했다

- 커밋 메시지를 작성하던 중, 형식에 맞지 않게 작성한 부분이 있었다.
- 커밋 메시지를 수정하는 과정에서 실수를 하는 바람에, 커밋되지 않은 변경 사항이 날아가버렸다.
- 다행히 IDE의 로컬 히스토리를 통해 복구할 수 있었지만, 계획했던 것보다 작업 시간이 훨씬 길어졌고, 새벽 늦게까지 잠을 자지 못했다.

<br>

## Try

### **1. 직접 해보면서 익숙해지자**

- 나중에 써야될 때 해보자는 마음가짐으로는, 막상 써야할 때 제대로 하지 못할 수 있다.
- 실전에서는 실수가 치명적이기 때문에, 경험 부족으로 주저하거나, 잘하는 다른 사람에게 의존하는 소극적인 태도가 되기 싶다.
- 시간적 여유가 될 때는, 꼭 지금 해봐야하는 작업이 아니더라도 직접 실습해보면서 경험을 쌓아두자.

### 2. 커밋 전에 조금 더 꼼꼼하게 확인하도록 하자

- 사실 총 두 번의 실수를 했다. 처음에는 커밋 메세지를 잘못 작성했고, 그것을 수정하는 과정에서 커밋하지 않는 변경 사항을 날려버렸다.
- 두 번 중 한 번만이라도 좀 더 신중하게 작업했더라면, 겪지 않아도 되었을 시행착오였다.
- 커밋은 할 때는 간단하고 쉽지만, 돌이키는 것은 어렵다. 확인에 더 많이 시간과 노력을 기울여 신중하게 해야겠다.
- 커밋 전에 확인해야 할 체크리스트를 만들어서 스스로 점검해보자.

# 3. 학습내용

## VPC

### **서브넷(Subnet)**

- **Public Subnet**
    - 인터넷과 통신 가능
    - IGW(Internet Gateway)를 통해 외부와 연결됨
- **Private Subnet**
    - 인터넷과 직접 통신 불가
    - 일반적으로 DB나 민감한 리소스를 배치
    - 보안을 위해 더 많이 사용됨 → IP 대역을 더 많이 할당함 (최소 2배)
- AWS는 기본적으로 리소스를 private하게 설정

<br>

### **EC2에 접근하기 위한 조건**

1. **pem 키 (Private key)**: SSH 접속 시 필요
2. **Public IP 주소**: 외부에서 접근하기 위해 필요
3. **IGW (Internet Gateway)**: VPC에 할당되어 있어야 인터넷 접속 가능
4. **Security Group (SG)**: EC2 수준의 방화벽 설정

<br>

### **방화벽 보안**

- **Security Group (SG)**
    - 인스턴스 단위 방화벽
    - 기본적으로 모든 포트 차단, 필요한 포트를 허용해야 함
- **NACL (Network ACL)**
    - 서브넷 단위 방화벽
    - 기본적으로 모든 포트 허용, 필요한 포트를 차단해야 함 (반대 개념)

<br>

## EC2 인스턴스 타입

### **인스턴스 타입 명명 규칙**

예: `t4g.micro`

- `t`: 범용 인스턴스 타입 (cpu/memory 비율이 균형잡힘)
- `4`: 세대 수 (숫자가 높을수록 최신)
- `g`: ARM 기반 Graviton 프로세서
- `micro`: 가장 작은 사양 (저비용)

<br>

## AMI (Amazon Machine Image)

- EC2 인스턴스를 생성할 때 사용하는 OS 이미지
- OS, 설정, 애플리케이션이 포함된 스냅샷

<br>

## 라우팅 테이블(Route Table)

- 서브넷과 IGW의 연결 정의
- 예시:
    - `local → 10.0.0.0/16` (같은 VPC 내부 통신 허용)
    - `igw-id → 0.0.0.0/0` (인터넷 전송을 IGW로)

<br>

## S3 (Simple Storage Service)

### **기본 개념**

- **오브젝트 스토리지**: 파일을 객체 형태로 저장
- **버킷(Bucket)**: S3에서 파일을 담는 공간
    - 버킷 이름은 전 세계적으로 유일해야 함 (global unique)
- **오브젝트(Object)**: 버킷에 저장되는 실제 파일
    - 동일 버킷 내에서는 이름이 유일해야 함
    - 같은 이름 업로드 → 덮어쓰기

<br>

### **버전 관리 (Versioning)**

- 동일 이름의 파일도 여러 버전 저장 가능
- 저장 공간과 비용 증가 주의

<br>

### **S3의 특징**

- 리전(region) 단위 서비스 (VPC는 아님)
- 최소 3개의 AZ(가용 영역)에 중복 저장
- 모든 오브젝트는 고유 URL로 접근 가능

<br>

### **Presigned URL**

- 미리 인증된 접근 URL
- 일정 기간 동안만 유효
- 제한된 사용자에게 업로드/다운로드 권한 부여

<br>

### **S3의 비용**

- 저장된 데이터의 용량
- 다운로드 양 (업로드는 무료)
- 리전 간 전송 시 네트워크 비용 발생
    - 단, 같은 리전의 EC2 ↔ S3 전송은 무료

<br>

### **업로드 관련 제한**

- 버킷 자체는 용량 제한 없음
- 개별 오브젝트는 사이즈 제한 존재
    - 대용량 파일은 분할 업로드 또는 압축 필요

<br>

### **CRUD에서의 Update**

- Update의 개념이 존재하지 않음
- 동일 이름으로 새 버전 업로드
