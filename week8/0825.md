## 작업 과정에서 배운 것

### 1. 브라우저의 특성 고려하기

일요일 오후에 프론트엔드 태승님에게 Nchan 연결에 문제가 있다는 연락을 받았다. Nchan 연결 자체는 잘 되는데 그 상태로 기존의 다른 HTTP API 요청을 하면 pending 상태로 멈추는 현상이 있었다. 

프로젝트의 중심 기능이기도 하고, 발표 주제로도 생각하고 있었던 부분이기 때문에, 그 문제를 수정하기 위해 많은 시간을 쏟아부었다. 예상되는 원인으로는 세션 락과 동기적 메세지 전송 방식이 있었고, 그 부분들을 위주로 수정에 들어갔다. 프론트엔드 팀원들도 각자 해야할 작업이 있기 때문에, 연결 작업으로 붙잡아둘 수는 없었다. 다음날(오늘) 만나서 직접 확인해보고 연결 작업을 해보기로 했다. 중요한 기능에 문제가 생겼는데, 그 원인을 정확히 파악하지도 못한 채 기다려야 해서 답답했다.

오늘 에티버스에 와서 다시 연결 작업에 도전했다. 어제 문제의 원인으로 추측했던 부분이 맞아서 무사히 연결되기를 바랐지만 똑같은 현상이 발생했다. 요청 자체가 pending 되니 서버 로그도 남지 않아서 단서를 찾기도 어려웠다.

한참 찾아본 끝에 원인을 찾을 수 있었다. 브라우저에서 동일 Origin에 대한 연결을 최대 6개까지만 허용하고 있었던 것이다. 프론트엔드에서 연결 작업을 하면서 3가지 Role을 동시에 테스트해보신다고 창을 3개 띄워서 작업하고 계셨다. 각 Role별로 웹소켓과 Nchan, 총 6개의 연결이 이미 이루어져 있는데, 추가로 api 요청을 보내려고 하니 일곱 번째 연결이 되어 pending 되었던 것이다. 

서비스 자체의 문제라기보다는, 브라우저의 특성을 잘 이해하지 못했기 때문에 발생한 문제였다. 전혀 예상치 못한 단순한 부분에서 문제가 발생한 것이라, 그동안 복잡하게 꼬아서 생각했던 것이 조금은 허무하게 느껴졌다.

그래도 이번 경험을 통해 세션 락이나 비동기적 전송 같은, 실시간 통신에서 중요한 부분을 다지고 넘어갈 수 있었다. 이번 문제의 원인은 아니었지만, 언젠가 다른 상황에서 충분히 문제가 될 수 있는 부분들이었다. 의도치 않게 깊이 있게 살펴볼 기회를 가진 것이 오히려 다행이라는 생각도 들었다.

## 어려웠던 점

### 1. 프로젝트의 규모가 커질수록 원인 파악이 어려웠다

새로운 영역에 계속 도전하다 보니, 문제가 생겼을 때 정확히 어디에서 발생한 것인지 파악하기가 힘들었다. 이미 익숙한 영역에 새 기능이 덧붙여진 것이라면 기존 부분은 어느 정도 안심하고 넘어갈 수 있을 텐데, 모든 것이 새로 배우는 영역이다 보니 구현했던 코드 전체를 처음부터 검토해야 했다.

또, 프론트엔드 연결 과정에서 발생한 에러는 로컬 환경에서 그대로 재현하기가 어려웠다. 원격 인스턴스, 브라우저, 프론트엔드 애플리케이션 등 결과에 영향을 주는 변수가 많아, 동일한 조건에서 실행하기가 쉽지 않았다. 프론트엔드 팀원들이 에러 상황을 알려줘도 상황을 정확하게 파악하기에는 한계가 있었다. 그렇다고 내가 직접 재현해볼 수 있는 것도 아니니 없으니 문제의 정확한 원인을 잡아내기 힘들었다. 결국 증상만 듣고 가능한 원인을 추측해 예방 차원에서 수정할 수밖에 없었다. 이 점이 가장 어려웠다.

# 3. 학습내용

## 세션 락 (Session Lock)

- **세션(Session):** 웹 애플리케이션에서 클라이언트별 상태를 서버에 저장하기 위한 공간
- **세션 락(Session Lock):** 여러 요청이 동일한 세션 객체를 동시에 수정하려 할 때, 데이터 불일치를 방지하기 위해 서버가 해당 세션에 동기화 잠금(Lock)을 거는 메커니즘

### **동작 원리**

- 웹 애플리케이션 서버는 세션에 접근하는 요청이 들어오면, 세션 객체를 보호하기 위해 내부적으로 `synchronized` 락을 걺
- 하나의 세션에 대해 동시에 처리할 수 있는 요청은 1개뿐
    - 나머지 요청은 락이 해제될 때까지 대기
- 따라서 같은 사용자가 여러 탭/브라우저에서 동시에 요청을 보내면, 직렬화(serialized)되어 처리됨

### **장점**

- 세션 객체의 무결성을 보장
- 같은 사용자 세션을 공유하는 요청 간에 데이터 꼬임이 발생하지 않음

### **문제점**

- **병목 현상** : 긴 작업을 수행하는 요청이 세션 락을 점유하면, 다른 요청들이 대기하게 되어 응답 지연이 발생
- **동시성 저하** : 한 세션에서 여러 요청을 동시에 빠르게 처리할 수 없음
- **예상치 못한 블로킹** : 프론트엔드에서 비동기로 보낸 여러 요청이 서버에서 순차적으로 처리되면서, 사용자 입장에서는 반응이 느리게 보일 수 있음

### **해결 / 완화 방법**

1. **세션에 불필요한 데이터 저장하지 않기**
    - DB나 캐시(Redis)에 분리해서 저장하고, 세션에는 최소한의 인증/식별 정보만 저장
2. **세션 접근 최소화**
    - 동시 요청이 많은 API에서는 세션을 아예 사용하지 않거나, 읽기 전용으로만 접근
3. **Stateless 설계**
    - JWT 같은 토큰 기반 인증을 사용해 서버 상태(세션)에 의존하지 않도록 설계하면 세션 락 문제 자체를 피할 수 있음
4. **비동기 요청 설계 고려**
    - 같은 세션으로 동시에 요청을 보내는 경우를 줄이거나, 요청 간 순서를 제어하는 로직을 클라이언트/서버에 추가

## 비동기화 (Asynchronization)

- 어떤 작업이 시작된 후, 그 작업이 끝날 때까지 기다리지 않고 다른 작업을 동시에 진행할 수 있도록 처리하는 방식
- 요청을 보낸 주체(스레드, 함수, 사용자)는 즉시 제어권을 돌려받고, 작업 결과는 Callback, Promise/Future, Event 등을 통해 나중에 전달됨

### **동기화(Synchronous)와 비교**

- **동기화(Sync)** : 요청 → 작업 실행 → 결과 반환까지 순차적으로 진행, 결과를 받을 때까지 블로킹됨
- **비동기화(Async)** : 요청 → 작업 실행(백그라운드) → 즉시 제어권 반환 → 이후 결과가 준비되면 알림/콜백으로 전달

### **특징**

1. **논블로킹(Non-blocking)** : 한 작업이 지연되어도 다른 작업을 멈추지 않음
2. **병렬성(Parallelism)** 과의 차이
    - 비동기는 결과를 기다리지 않고 넘겨주는 방식
    - 병렬성은 실제로 여러 CPU/스레드에서 동시에 실행되는 것.
    - 다른 개념이지만 함께 사용되는 경우가 많다.
3. **응답성 향상** : 특히 I/O(네트워크, 파일 입출력, DB 요청 등)에서 대기 시간을 줄이는 데 효과적

### **장점**

- CPU 자원을 효율적으로 사용 가능
- 대기 시간이 많은 I/O 작업에서 성능과 응답성 개선 가능
- 동시 사용자 수가 많은 서비스에서 확장성(Scalability) 강화 가능

### **단점 / 주의사항**

- 코드 흐름이 직관적이지 않아 디버깅이 어려움
- 동시성 문제(공유 데이터 접근 충돌)가 발생할 수 있음
- 작업의 완료 순서가 보장되지 않기 때문에, 제어 흐름을 잘 설계해야 함
