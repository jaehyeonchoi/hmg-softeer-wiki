테스트 및 QA 작업이 많다보니, 뭔가 커다란 작업을 병행하기 힘들었다. 중간 중간에 뜨는 시간을 활용하기 위해서 위키 작성을 하기로 했다.

그동안 실시간 동행 공유 기능을 구현하면서 거쳐왔던 과정이나, 개선해보려고 노력했던 부분에 대해서 정리할 수 있었다. 개발을 하면서 중간 과정을 회고에 꾸준히 기록하기는 했지만, 매일 매일 다른 문서에 적다보니 내용이 파편화되었던 문제가 있었다. 이번에 하나의 문서로 아티클을 작성하면서 전체 흐름을 한 번에 살펴볼 수 있어서 좋았다. 

발표 자료를 만들 시간도 충분하지 않기 때문에 이번에 작성하는 아티클이 사실상 발표 시나리오의 역할을 할 수 있도록 최대한 충실하게 작성해봐야겠다.

## 어려웠던 점

### 1. 문제가 있을 때 정확한 원인이 어디인지 파악하기 어려웠음

어제 회고에서도 적었던 내용이지만, 오늘도 QA 중 발생한 문제를 찾기가 어려웠다.

실시간 위치 공유 기능을 테스트해 보던 중, 도우미의 웹소켓 연결이 자꾸 해제되는 문제가 있었다.

문제의 원인을 금방 찾을 수 없어 태승님과 함께 꽤 오랫동안 해결에 매달렸다. 원인은 리액트의 기본 설정과 서버 구현 방식이었다.

리액트는 기본적으로 요청을 보낼 때 동일한 요청을 두 번 보내도록 설정되어 있다고 한다. 웹소켓 연결을 요청할 때도 동일한 요청이 연달아 두 번 보내졌는데, 서버는 이미 연결된 동행-사용자 롤에 대해 다시 연결 요청이 들어오면 기존 연결을 해제하도록 되어 있었다. 동일한 세션에서 재요청이 들어왔기 때문에 기존 연결과 새로운 연결이 같은 연결로 인식됐고, 기존 연결을 해제하는 동작이 새로운 연결까지 해제해 버린 것이다.

그동안 브라우저에서 테스트하면서 동일 세션으로 연달아 연결 요청을 보낼 일이 없었기 때문에 문제가 드러나지 않았다. 실제 서비스 로직상으로는 일어나기 어려운 상황이기는 했지만, 명백한 구현상의 오류였기에 수정했다.

실시간 통신 기능을 구현하면서 여러 차례 느끼고 있지만, 통신 과정에 개입하는 요소들이 많다보니 다른 기능에 비해 문제가 발생했을 때 원인을 찾기 어려웠다. 오늘도 설마 리액트 때문에 문제가 발생할 것이라고는 상상도 하지 못했다. 그래도 덕분에 쉽게 드러나지 않던 서비스의 허점을 찾을 수 있어서 다행이라는 생각도 들었다.

# 2. 회고

## Keep

### **1. 직접 디바이스를 들고 움직여보면서 테스트한 것**

- 기능 구현과 API 관련 QA 작업이 마무리되었다.
- 가장 중요하면서도 문제가 생길 확률이 높은 대시보드 기능을 집중적으로 테스트해보기로 했다.
- 위치 공유 기능이 실제로 잘 작동하는지 확인하는 것이 중요하기 때문에 직접 각자의 스마트폰을 들고 밖으로 나가서 시험해보았다.
- 실제로 움직이면서 테스트를 해보니, 어느 부분에서 문제가 일어나고 있는지도 빨리 찾을 수 있었고, 사용자의 입장에서 어떤 점이 불편한지, 어떤 점을 개선하면 좋을지도 체감할 수 있었다.
- 남은 시간이 많지는 않지만, 이런 테스트 경험을 최대한 많이 하면서 개선할 부분들을 찾아나가고 싶다.

<br>

## Problem

### **1. 직접 디바이스를 들고 테스트를 하기에 한계가 있음**

- 앞서서 직접 디바이스를 들고 테스트를 하면서 느꼈던 이점들을 적기는 했지만, 그와는 반대로 불편했던 점도 있었다.
- 직접 사람이 나가서 테스트를 해야했는데, 동행에 관계된 사용자의 롤이 3개이기 때문에, 여러 팀원들이 동시에 나가야 했고, 또 직접 걸어서 이동하는 상황을 만들어야 해서 금방 끝나는 작업도 아니었다.
- 결국, 최소 3명의 개발자가 다른 작업을 하지 못하고, 테스트에만 장시간 매달려 있어야 하는 문제가 있었다.
- 가뜩이나 작업 시간이 모자른 상황에서 매번 이런 식으로 테스트를 할 수는 없겠다는 생각이 들었다.

<br>

## Try

### **1. 직접 야외로 나가지 않고도 테스트를 할 수 있는 방법을 찾아보자**

- 조이스틱이나 경로 입력을 통해 GPS 정보를 조작할 수 있는 애플리케이션이 있다는 것을 알게 되었다.
- 해당 애플리케이션을 사용한다면, 팀원들이 직접 야외로 나가지 않고도 위치 이동을 테스트해보는 것이 가능할 것 같다.
- 위치 이동을 이런 식으로 가상으로 재현해보는 것은 금요일에 있을 부스 시연에서도 유용하게 활용될 수 있을지 모른다. 적용할 수 있는지 한 번 알아보자.

# 3. 학습내용

## @Async (Spring 비동기 실행)

- Spring에서 메서드를 백그라운드 스레드에서 비동기 실행하도록 해주는 어노테이션

<br>

### **동작 원리**

- `@EnableAsync`를 사용해 애플리케이션에 비동기 기능을 활성화
- `@Async`가 붙은 메서드는 호출 시 즉시 실행되지 않고, Spring이 관리하는 스레드풀(Executor) 에 작업이 제출됨
- 호출한 쪽은 결과를 기다리지 않고 즉시 반환
    - 해당 메서드는 별도의 쓰레드에서 백그라운드로 실행됨
- 내부적으로는 프록시 기반(AOP 방식) 으로 동작
    - 같은 클래스 내부에서 자기 메서드를 호출하면 비동기 처리가 되지 않음

<br>

### **장점**

- **응답 속도 향상:** 시간이 오래 걸리는 작업을 요청 흐름에서 분리해, 사용자가 빠르게 응답을 받을 수 있음
- **시스템 처리량 증가:** 여러 작업을 병렬로 처리할 수 있어, 동시 요청에 더 유연하게 대응할 수 있음
- **핸들러 안정성 확보:** 웹소켓, SSE 등 빠른 응답이 중요한 환경에서 블로킹 작업을 분리할 수 있음

<br>

### **문제점**

- **트랜잭션이 전파되지 않음:** 호출한 쪽에 트랜잭션이 걸려 있어도, 비동기 메서드에는 적용되지 않음
    - 지연 로딩 실패나 커밋 전 데이터 조회 문제 등이 발생할 수 있음
- **컨텍스트 전파 불가:** 보안 인증 정보(SecurityContext)나 로깅 컨텍스트(MDC) 등은 기본적으로 새 스레드에 전파되지 않음
    - 누가 요청했는지, 어떤 흐름에서 실행됐는지 알 수 없음
- **self-invocation 미적용:** 같은 클래스 내에서 `this.asyncMethod()`처럼 자기 메서드를 호출하면 비동기로 실행되지 않음
- **풀 과부하 가능성:** Executor 설정을 잘못하면, 스레드 과다 생성으로 인해 DB 커넥션 고갈 등 전체 서비스에 영향을 줄 수 있음

<br>

### **해결 / 완화 방법**

1. **프록시를 통한 호출 유지**
    - 비동기 메서드는 다른 클래스(다른 빈) 에 분리하거나, 자기 자신을 주입받아 프록시를 거치도록
2. **트랜잭션 경계 명확화**
    - 트랜잭션이 필요한 경우에는 비동기 메서드에 직접 `@Transactional`을 붙이고, 엔티티 전체가 아닌 식별자(ID)만 전달해서 내부에서 다시 조회하도록
3. **컨텍스트 수동 전파**
    - 보안 정보가 필요한 경우 `DelegatingSecurityContextAsyncTaskExecutor` 사용
    - 로깅 정보(MDC)는 `TaskDecorator`를 이용해 복사 및 초기화
4. **스레드풀 설계**
    - 작업 성격에 맞게 풀을 분리(`cpuPool`, `ioPool` 등)하고, core/max/queue 설정은 DB 풀, 외부 API 제한 등에 맞춰 보수적으로 설계
5. **예외 및 실패 대응**
    - 반환값을 `CompletableFuture`로 지정하고, `whenComplete`, `handle` 등으로 예외를 직접 처리
    - 외부 API 호출이 포함된 경우 재시도, 백오프, 서킷 브레이커 등의 안정화 전략을 함께 고려
