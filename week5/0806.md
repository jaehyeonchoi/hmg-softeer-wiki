# 1. 리뷰

## 오늘 한 작업

### 종합프로젝트

- 고객 사이드
    - 동행 내역 상세 Service 및 DAO 생성 / 테스트 코드 작성
    - 결제 및 완료 Service 및 DAO 생성 / 테스트 코드 작성

## 작업 과정에서 배운 것

### 1. 사용자 관점에 치우친 분석을 했던 것 같다

도메인별로 어떤 데이터가 필요할지 고민하면서 ERD와 엔티티를 설계했다. 사용자에게 어떤 데이터가 보여져야 하는지를 중심으로 생각하여, 그에 맞는 필드들을 찾아나갔다.

그런데 실제로 구현에 들어가보니, 사용자에게는 드러나지 않아도, 구현을 위해 내부적으로 필요한 값들이 많이 있었다. 설계 과정에서 그런 영역까지 충분히 고려했다고 생각했는데, 당장 구현을 해야하는 입장이 되어보니 놓치고 있던 부분들이 보이기 시작했다.

누락되어 있던 부분들을 중간중간 반영해야 하다보니 코드에 수정 사항이 많이 생겼고, 자연스럽게 개발 속도도 더뎌졌다.

앞으로 설계를 할 때는 단순히 겉으로 드러나는 데이터 뿐만이 아니라, 내부에서의 동작까지도 더 깊이 있게 생각해봐야겠다고 느꼈다.

<br>

## 어려웠던 점

### 1. 리포지토리와 서비스 역할 분리

리포지토리에서는 DB 입출력만 담당하고, 서비스에서 데이터를 가공하는 구조로 가고 싶었다. 

처음에는 각 도메인별 리포지토리에서 데이터를 가져온 뒤, 파사드 서비스에서 조합하려고 했다. 하지만 쿼리 횟수가 불필요하게 많아지는 문제가 있었다. QueryDSL의 Fetch Join을 통해 필요한 데이터를 한 번에 가져오도록 수정했다.

리포지토리에서 아예 응답 DTO의 형태로 조회해서 데이터를 가져오고 싶었는데, 일부 필드들은 단순히 읽어오는 것을 넘어, 값을 변환해줘야 할 필요가 있었다. 리포지토리 내부에 거기까지 처리하려다 보니, 서비스 레이어는 리포지토리 호출 외에 할 일이 없어졌고, 역할의 구분이 모호해졌다.

다시 변환 로직을 서비스 쪽으로 분리하려고 했다. 이번에는 리포지토리에서 쓰던 Tuple, Q클래스 등의 데이터타입이 서비스 레벨까지 올라와서 사용되는 문제가 있었다.

이 문제에 대한 해결방법으로는 플랫 DTO를 만들거나, IN 쿼리를 사용하는 등의 방식이 있다고 한다. 조금 더 조사를 해보고, 우리 프로젝트에 가장 적합한 구조로 개선해볼 계획이다.

# 2. 회고

## Keep

### **1. 집 가는** 길에 회고를 쓰기

- 요즘 집에 가는 길에 지하철에서 스마트폰 메모장으로 회고 초안을 쓰고 있다.
- 집에 와서 회고를 쓰려고 하면, 피곤하기도 하고 시간도 오래 걸린다. 집에 가는 길에 작성하면, 방금까지 작업을 하던 참이었기 때문에 기억도 선명하고 더 막힘없이 써지는 것 같다.
- 작업을 하던 중에 막히는 부분이 있으면 집 가는 길에 계속 그 생각이 난다. 억지로 기분 전환하는 것보다, 아예 회고를 쓰면서 ‘뭐가 어려웠는지’, ‘어디가 문제였는지’, ‘앞으로 어떻게 해볼지’를 생각해보니까 오히려 기분이 더 개운해지는 느낌이다.
- 이동시간이라는 것이 쉬고 싶다고 푹 쉴 수 있는 시간도 아니기 때문에, 이 정도의 가벼운 활동을 하는 것이 더욱 알차게 보낼 수 있는 방법인 것 같다.

<br>

## Problem

### **1.** 도구에 대한 적응이 필요하다

- 소프티어 과정에 참여하면서 맥북을 처음으로 사용해봤다. 윈도우와는 여러가지 면에서 은근히 다른 점이 많아 어색했다.
- 작업량이 점점 많아지면서, 조작이 미숙하다는 점이 더욱 치명적으로 다가오는 것 같다.
- 개발을 위해 고민하는 시간을 빼놓더라도, 코드를 작성하는 과정에서부터 시간 소모가 있다보니 작업 속도가 더욱 느려진다.

### 2. 소통에 모호한 부분이 있다

- 아침 저녁으로 팀내에서 스크럼을 하면서, 지금까지 수행한 내용과 앞으로 수행할 내용을 공유하고 있다.
- 스스로 공유했던 내용을 돌이켜보면서, 듣는 사람들에게 과연 제대로 전달되었을까 하는 생각이 들었다.
- 직접 작업을 하고 있는 나에게는 당연하게 머릿속에 있는 내용이지만, 간접적으로 듣는 사람들에게는 와닿지 않을 수도 있겠다고 생각했다.

<br>

## Try

### **1.** 단축키나 유용한 팁을 익혀둬야겠다

- 단축키를 새로 찾아보고 익히는 것에도 시간이 걸려서, 그냥 직접 타이핑을 하거나 마우스로 조작하는 일이 많았다.
- 하지만 잠깐이라면 모를까, 이렇게 긴 시간동안 사용해야 하는 장비라면 지금부터라도 단축키를 익히는 것이 속도가 더 빠르겠다는 생각이 든다.
- 굳이 단축키를 찾아보고 써보는 것이 처음에는 오히려 느릴 수도 있겠지만, 장기적으로 봤을 때는 더 효율적일 것이다.
- 쉬는 시간에 주변 사람들이 작업하는 모습을 구경하면서, 좋아보이는 팁이 있으면 물어보고 배우는 것도 좋을 것 같다.

### 2. 명확한 의사소통을 하자

- 이것, 저것과 같은 대명사나, ‘저번에 말씀드렸던’과 같은 불명확한 표현들을 나도 모르게 사용하고 있는 것 같다. 다소 번거롭더라도 대상을 정확하게 지칭할 수 있는 표현을 사용하도록 하자.
- 내가 알고 있는 용어나 배경이 모두에게 익숙하지는 않을 수도 있으니, 처음 듣는 사람들도 이해할 수 있도록 풀어서 말하거나, 부연 설명을 덧붙여보자.
- 내 할 말을 하는 것도 중요하지만, 상대가 제대로 이해하고 있는지 확인하는 것도 중요하다. 상대의 반응을 살피고, 문제가 없는지 먼저 가볍고 물어보는 타이밍을 가져보자.

# 3. 학습내용

## IN 쿼리

- SQL에서 특정 컬럼의 값이 주어진 여러 값 중 하나와 일치하는 경우를 조건으로 지정하는 구문
- 여러 개 중 하나에 해당하는 데이터를 필터링할 때 사용

### 예시

```sql
SELECT * FROM users
WHERE id IN (1, 3, 5);
```

→ `id`가 1, 3, 5인 사용자만 조회

### 특징

- 복수 조건 비교를 간결하게 표현 가능
- 내부 값이 많을수록 `OR` 조건문보다 가독성과 성능이 좋을 수 있음
- 서브쿼리와 함께 사용 가능
    
    ```sql
    SELECT * FROM orders
    WHERE user_id IN (SELECT id FROM users WHERE status = 'active');
    ```
    

### 활용

- **다건 조회**: 특정 ID 리스트에 해당하는 레코드를 조회할 때
- **쿼리 최적화**: `OR` 조건이 많아질 경우 `IN`으로 대체해 성능 향상 가능
- **DTO나 ID 리스트 기반 조회:**
    - ex. `List<Long> ids` 를 기반으로 QueryDSL에서 `where user.id.in(ids)`

### QueryDSL에서 `IN` 조건 사용 예시

### 1. 기본적인 `IN` 조건

```java
List<Long> ids = List.of(1L, 3L, 5L);

List<User> users = queryFactory
    .selectFrom(user)
    .where(user.id.in(ids))
    .fetch();
```

### 2. 문자열 리스트 `IN` 조회

```java
List<String> statuses = List.of("WAITING", "ACCEPTED");

List<Application> result = queryFactory
    .selectFrom(application)
    .where(application.status.in(statuses))
    .fetch();
```

### 3. 서브 쿼리와 함께 사용

```java
QUser user = QUser.user;
QOrder order = QOrder.order;

List<Order> orders = queryFactory
    .selectFrom(order)
    .where(order.user.id.in(
        JPAExpressions
            .select(user.id)
            .from(user)
            .where(user.status.eq(Status.ACTIVE))
    ))
    .fetch();
```

### 4. DTO와 함께 사용하는 경우 (플랫 DTO로 ID → 엔티티 조회)

1차 조회:

```java
// ID 리스트만 조회
List<Long> recruitIds = queryFactory
    .select(recruit.id)
    .from(recruit)
    .where(recruit.status.eq(OPEN))
    .fetch();
```

2차 조회:

```java
// ID 리스트 기반으로 연관 데이터 한 번에 조회
List<Recruit> result = queryFactory
    .selectFrom(recruit)
    .leftJoin(recruit.patient).fetchJoin()
    .leftJoin(recruit.location).fetchJoin()
    .where(recruit.id.in(recruitIds))
    .fetch();
```

## Flat DTO

- 계층적 구조를 가지는 여러 엔티티나 객체의 정보를 하나의 평평한 구조(flat structure)로 담아 전달하는 DTO
- 중첩 없이 단일 객체에 필요한 필드를 모두 담은 형태의 DTO

### 특징

- **구조**: 중첩된 객체 없이 모든 필드를 하나의 평면 구조로 가짐
- **목적**: 복잡한 연관관계를 단순하게 표현하여 쿼리 최적화 및 직관적 응답 전달을 가능하게 함
- **성능**: join과 함께 한 번의 쿼리로 모든 필드를 가져오므로 N+1 문제 방지에 효과적

### 예시

**엔티티 구조**

```java
class Recruit {
    Long id;
    Patient patient;
    Location location;
}

class Patient {
    String name;
}

class Location {
    String address;
}
```

**플랫 DTO**

```java
class RecruitFlatDto {
    Long recruitId;
    String patientName;
    String locationAddress;
}
```

- 중첩 없이 단일 객체에 모든 정보가 평평하게(flat) 담겨 있음

### 장점

- 단일 쿼리로 조인하여 모든 데이터 조회 가능 → 성능 향상
- 구조가 단순해 클라이언트에 전달하기 쉬움
- QueryDSL에서 DTO 직접 매핑하기 편함

### 단점

- 계층 구조를 표현할 수 없음 (재사용 어려움)
- 필드 수가 많아지면 DTO가 너무 커질 수 있음
- 여러 도메인의 데이터가 섞여 있어 역할이 모호해질 수 있음
