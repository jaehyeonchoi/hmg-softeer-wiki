## 작업 과정에서 배운 것

### 1. 팀원들과 어려운 점에 대해서 많이 이야기하기

작업 과정에서 겪고 있는 어려움에 대해 팀원들에게 많이 공유하고 있다.

성훈님은 방향성을 잡기 어려운 부분에 대해 질문 드렸을 때, 같은 백엔드 팀원으로서 문제에 대한 자신의 생각을 명확하게 말씀해주셔서 많은 도움을 받고 있다. 내가 생각했던 방식과 다른 방식을 이야기하실 때도 많은데, 문제를 바라보는 시각을 넓힐 수 있어서 좋았다.

프론트엔드 팀원들과도 스크럼 시간이나, 회의 시간을 통해 현재 겪고 있는 난관에 대해 이야기하고 있다. 사실 처음에는 서로 다른 파트이기도 해서 단순한 상황 공유의 차원에서 공유했던 건데, 예상치도 못한 방향에서 해결의 실마리가 나올 때가 많았다. 백엔드에서 겪고 있던 어려움을 프론트엔드에서는 훨씬 쉽게 해결할 수 있다던가, 혹은 그 반대의 경우도 있었다.

각자 아는 것도 다르고, 가지고 있는 능력도 다르기 때문에, 혼자서는 해결하기 힘들었을 문제도, 팀원들과 함께라면 또 다른 방식으로 극복할 수 있다는 것을 배웠다. 앞으로도 한 팀으로서 서로 돕고 도움받으며 목표를 향해 나아가고 싶다.

## 어려웠던 점

### 1. DB에서 JSON 타입 컬럼 처리

이번 프로젝트에서는 PostgreSQL을 도입할 예정이었기 때문에, JSON 타입 컬럼을 활용한 데이터 저장 및 조회를 염두에 두고 코드를 작성했다. 

아직 PostegreSQL와 연결이 되지 않아서 로컬 H2를 연결하여 개발하고 있었는데, JSON 타입 컬럼의 값을 제대로 조회하지 못하는 문제가 있었다. `JsonUtils`를 사용해 객체를 JSON으로 직렬화/역직렬화하는 로직을 구현했는데, 로직 자체에는 문제가 없어보였고, 단위 테스트에서도 분명 이상이 없었다.

원인을 찾기 위해 DB 저장 과정을 살펴본 결과, H2가 JSON 데이터를 저장할 때 문자열 내부에 이중 따옴표("")를 한 번 더 감싸고 에스케이프 처리를 한다는 점을 알 수 있었다. 쿼리에서 따로 저장 포맷을 설정해야 일반적인 문자열의 형태로 저장할 수 있었다.

DB들 사이의 차이점을 미처 파악하지 못해서 발생했던 시행착오였다. 가능하면 처음부터 개발 환경을 제대로 세팅하고, 만약 그러지 못했다면 임시로 사용할 환경의 특성을 잘 알고 있어야겠다.

# 2. 회고

## Keep

### **1. 리팩토링을 작업 중간중간 미리 적용하고 있다**

- 기능을 무작정 빠르게 구현하기보다는, 리팩토링을 병행하며 코드의 품질을 높이는 데 집중하고 있다.
- 필요한 기초 클래스들을 도메인별로 사전에 만들어두고, 반복적으로 쓰이는 로직은 공통 유틸 클래스로 분리함으로써 재사용성과 유지보수성을 높이고 있다.
- 코드 리뷰 과정에서 팀원들이 쉽게 이해할 수 있도록 네이밍과 구조에 신경쓰고 있다.
- 초반에는 리팩토링에 시간이 더 소요되기도 했지만, 지금 다져놓은 기반이 향후 더 빠르고 안정적인 개발로 이어질 것이라고 생각한다.

<br>

## Problem

### **1. 회고를 쓸 시간이 부족하다**

- 작업에 열중하다보면 회고를 위해 시간을 따로 내기가 쉽지 않다.
- 할 일이 많을수록 회고는 나중으로 미루게 되는데, 그러다 보면 중요했던 고민이나 통찰들을 잊어버리게 된다.
- 작업 중에 고민하고 느꼈던 점이 분명히 있었는데, 당시에는 미처 적지 못하고 작업에 몰두하다가, 나중에 쓰려고 하면 생각이 잘 안 나는 경우가 있다.
- 무슨 내용이었는지 고민하다보니 오히려 시간이 더 걸리게 된다.

### 2. 발표에 대한 고민

- 프로젝트 개발도 중요하지만, 결국 마지막에 그것을 보여주는 것은 역시 발표인 것 같다.
- 팀의 강점과 차별화된 부분을 잘 드러내기 위해서도 평소부터 의식적으로 ‘어떻게 설명할 것인가’를 고민해야 한다.
- 내용이 아무리 좋아도 그것을 전달하는 능력이 부족하면 아무 의미가 없다.

<br>

## Try

### **1. 작업 중에 느낀 점을 바로바로 메모하자**

- 프로젝트 초반에는 회고를 염두에 두고 메모를 잘 했는데, 최근에는 작업에 몰두하면서 그 습관을 놓친 것 같다.
- 작업을 하면서 있었던 이슈, 생각했던 점, 잘했던 점을 그때그때 한 문장씩이라도 메모를 남겨두자.
- 회고 작성은 물론, 나중에 발표 준비를 위해서도 귀중한 자산이 될 것이다.

### 2. 발표에 대한 준비를 일상 속에서 해보자

- 내가 하고 있는 작업이나 프로젝트에 대해 많이 생각해보자. 단순히 생각에서 그치지 않고 그것을 누군가에게 설명한다는 마음으로 내용을 체계화해보자.
- 단순히 “일을 했다”는 사실보다는, “왜 그렇게 했는지”, “그 선택이 어떤 영향을 미쳤는지”를 설명해보자.
- 일상적으로 팀원이나 다른 사람에게 내 작업을 요약해서 설명하는 훈련을 해두면, 발표 준비도 훨씬 수월해질 것이다.

# 3. 학습내용

## 수업 관련 내용

### 인증 및 접근

| 항목 | 설명 |
| --- | --- |
| **Access Key / Secret Access Key** | AWS API 호출 시 필요한 자격 증명 (IAM 사용자에게 발급) |
| **.pem 키** | SSH로 EC2 서버에 접근하기 위한 비공개 키 (EC2 인스턴스 생성 시 다운로드) |
| **scp 명령어** | SSH 기반으로 EC2에 파일 업로드/다운로드 |
| **ARN (Amazon Resource Name)** | AWS 리소스를 전 세계에서 유일하게 식별하는 이름 |

<br>

### 서버리스(Serverless) 서비스

서버 인프라를 직접 운영·관리하지 않고, 코드 실행에 집중하는 서비스

### 대표 서비스

- **Lambda** (서버리스 컴퓨팅)
- **S3** (서버리스 저장소)
- **DynamoDB** (서버리스 NoSQL DB)

### 서버리스의 특징

- 서버는 존재하지만, 사용자가 관리할 필요 없음
- 무제한 확장, 자동 성능 조절
- 사용한 만큼 과금

| 항목 | 서버리스 (Lambda, S3, DynamoDB) | 서버 기반 (EC2, RDS 등) |
| --- | --- | --- |
| 서버 관리 | 사용자가 직접 관리하지 않음 | 사용자가 직접 관리 (설정, 패치, 유지보수 등) |
| 성능 설정 | 제한적 (메모리 단위로 설정) | 상세하게 설정 가능 (CPU, RAM, IOPS 등) |
| 비용 | 사용한 만큼 과금 (초 단위) | 인스턴스 시간 단위로 과금 |
| 유연성 | 높음 (자동 확장) | 제한적 (Auto Scaling 직접 설정) |
| 영속성 | 일반적으로 상태를 유지하지 않음 | 인스턴스가 꺼지지 않는 한 유지됨 |

<br>

### AWS Lambda 정리

### 핵심 개념

- **핸들러(handler)**:
    
    함수의 진입점 → `handler(event, context)`
    
    - `event`: 트리거를 통해 전달되는 데이터
    - `context`: 실행 시간, 리소스 정보 등 메타데이터
- **실행 제한**
    - 최대 실행 시간: 15분
    - 메모리 설정: 128MB~10GB, CPU는 비례
    - 시간 초과 시 → 메모리 조정 or 코드 개선

### 스토리지

- 로컬 저장소 없음 → 함수 종료 시 모든 데이터 사라짐
- 임시 저장 공간: `/tmp` 디렉토리 (최대 512MB)
- 영속 저장 필요 시:
    - S3, RDS, DynamoDB, CloudWatch Logs 등 외부 리소스 사용

### 콜드 스타트 / 웜 스타트

- **콜드 스타트**: 새로운 환경에서 함수 처음 실행 → 느림
- **웜 스타트**: 기존 실행 환경 재사용 → 빠름
    - 환경을 공유하기 때문에, 전역 리소스 사용 시 주의 필요

### 권한 관리

- Lambda는 IAM Role 기반으로 리소스에 접근
    - Lambda에 S3, CloudWatch 등 리소스 접근 권한 부여 필요
- 호출자(Lambda를 트리거하는 주체)와
    
    Lambda가 호출하는 리소스 → 각각 권한 관리 필요
    

### 적절한 사용 사례

- 간단한 작업 자동화
- 이벤트 기반 처리(S3 업로드 시 자동 실행 등)
- 백엔드 API 구성 (API Gateway + Lambda)
- 단기성, 비동기 작업 처리
