## 작업 과정에서 배운 것

### 1. 버전 확인을 철저히 하기

이번 프로젝트에서 여러 기술들을 도입하면, 버전 호환성의 중요성을 느꼈다.

`BaseEntity`에서 Soft Delete를 구현하기 위해서 몇몇 어노테이션들을 사용했는데, 실제 DB 상에서 확인을 해보니 의도대로 작동하지 않는 것을 확인할 수 있었다. 알고 보니 일부 어노테이션이 deprecated 되어 더 이상 지원하지 않는 것이 문제였다.

또한 QueryDSL을 통해 복잡한 조회 쿼리를 작성하는 과정에서 GroupBy 관련 메서드를 사용했는데, 이 또한 현재 프로젝트에서 사용 중인 버전에서는 지원되지 않는 방식이었다. 

처음부터 알고 있었더라면 빠르게 포기하고 다른 방법을 알아봤을텐데, 전혀 모른 채 기능을 구현하고 있었다. 테스트를 해보는 시점에서나 알게 되어, 결국 그 동안 개발에 쏟았던 시간은 모두 물거품이 되었다.

이런 버전 관련 문제는 컴파일 시에는 잡히지 않는 경우도 많아서, 더더욱 알아차리기 힘들었다.

앞으로는 도입 예정인 기술이 프로젝트에 적용할 수 있는지 먼저 확인하고, 만약 지원하지 않는다면 조기에 다른 방향으로 전략을 세우려는 자세를 가져야겠다.

<br>

## 어려웠던 점

### 1. QueryDSL

기존에 단순한 JPA 방식으로 데이터를 조회하다 보니, 리스트 형태로 가져온 각 항목에 대해 추가적인 데이터가 필요한 상황에서 N + 1 문제가 발생했다. 쿼리 횟수를 줄이기 위해 QueryDSL을 도입하여 개선해보고자 했다. 

문법이 익숙하지 않아서 시행착오가 많았다. 

QueryDSL 자체도 익숙하지 않았지만, 조회한 데이터를 원하는 형태로 가공하는 과정에서 `Stream`, `Collectors`등 다양한 자바 문법이 섞어들어서 어려웠다. 특히, 특정 기준에 따라 한 묶음으로 만들어 개수나 비율 같은 수치를 구해야 하는 상황에서 group by 연산을 사용하는 것이 어려웠다.

리스트 형식으로 데이터를 조회해야 하는 부분이 있는데 각 항목에 대해 다시 한 번 더 데이터를 조회해야 되는 상황이 있었다. 리스트에 한 번, 각 요소에 대해서도 한 번 더 쿼리를 보내야 해서 N + 1 문제가 발생할 수 있었다.

쿼리 횟수를 줄이기 위해서 기존 쿼리 요청 로직에 QueryDSL을 적용하여 개선해보고자 했다.

문법이 익숙하지 않아서 시행착오가 많았다. QueryDSL 자체도 익숙하지 않았지만, QueryDSL로 조회한 데이터를 원하는 형태로 가공하는 과정에서 사용한 stream 문법까지 섞이니 더욱 어려웠다.

특히, 특정 기준에 따라 한 묶음으로 만들어 개수나 비율 같은 수치를 구해야 하는 상황이 있었는데, group by 연산을 하는 것이 어려웠다.

하지만 여러 번 시도하고 예제를 찾아보며 조금씩 익숙해지자, 오히려 복잡한 데이터를 한 번의 쿼리로 깔끔하게 처리할 수 있다는 점에서 큰 장점을 느낄 수 있었다. 이번 프로젝트를 통해 QueryDSL를 많이 사용해보면서 더 능숙하게 쓸 수 있을 만큼 익숙해져야겠다.

# 2. 회고

## Keep

### **1. 기획/디자인 팀들과의 지속적인 소통**

- 점심시간에 기획/디자인 팀원들과 함께 식사하며, 자연스럽게 프로젝트에 대한 이야기를 나눌 수 있었다.
- 이제는 서로 다른 주제로 새로운 미션을 하고 있지만, 이전에 함께한 종합 프로젝트에 대한 피드백을 주고받거나, 생각을 물어볼 수 있는 분위기가 여전히 유지되고 있다.
- 꼭 식사 시간 뿐만이 아니라, 활동 중에 남는 시간에도 가끔씩 찾아오셔서 프로젝트 상황을 구경하다 가시고는 한다.
- 바쁜 와중에도 프로젝트에 꾸준히 관심을 가져주는 모습이 감사했다.
- 기획/디자인 팀원 쪽에서 새 미션에 대한 조언을 구하거나 설문조사를 요청할 때도, 종합프로젝트 슬랙을 통해 서로에 도움을 주고 있다.
- 팀원들 모두 각자의 자리에서 힘내고, 마지막까지 잘 마무리했으면 좋겠다.

<br>

## Problem

### **1. 프로그램 요소들 간의 경계가 모호해지는 지점이 생기고 있다**

- 전체적으로 계층 구조(Controller → Facade → Service → Repository 등)를 따르고 있지만, 실제 구현에 들어가다 보면 도메인마다 필요한 계층 수나 구성 방식이 약간씩 달라진다.
- 어떤 계층에서는 할 일이 많고, 어떤 계층에서는 거의 역할이 없는데, 그것이 도메인별로 각기 다르다.
- 네이밍에서 도메인 개념이 정확히 드러나지 않거나, 오해의 소지가 있는 이름들이 생기고 있다.
    
    정보를 모두 담으려면 이름이 너무 길어지고, 줄이면 중복되거나 모호한 이름이 되곤 한다.
    
- 팀원들 사이에서도 구조와 이름이 헷갈리는 일이 있었다. 개발과 유지보수 시 혼란을 줄 수 있기 때문에 개선이 필요하다.

### 2. 수면 시간이 점점 늦어지고 있다

- 밤에 작업을 하다 보면 막히는 부분이 생기는데, "지금 해결해야 마음이 편하다"라는 생각에 계속 붙잡고 있는 경우가 많다.
- 해결이 될 때까지 계속 작업을 하다보면, 어느새 새벽 시간이 되어 있기도 한다.
- 이런 습관이 누적되다 보면 다음 날의 집중도나 컨디션에도 영향을 준다. 한 두 시간 더 하려고 하다가, 오히려 다음날을 하루 종일 피곤한 상태로 보내게 되는 것 같다.

<br>

## Try

### **1. 명확한 설계 기준을 세우고 끝까지 지키자**

- 프로젝트 초기에 정한 설계 기준(계층 구조, 네이밍 규칙, 책임 분리 등)을 최대한 지키려는 자세가 필요하다.
- 개발을 하다 보면, 규칙을 약간 벗어나는 것이 더 간편하거나 빠르게 느껴질 때도 있다. 하지만 그런 선택이 쌓이다보면, 결국 구조가 무너지게 되고 팀원 간 커뮤니케이션에도 혼란을 가져온다.
- 네이밍의 경우, 큰 범위에서 작은 범위로 점차 세분화되는 체계적인 방식을 채택해 일관성 있게 관리하자.

### 2. 수면 시간에 대한 ‘마지노선’을 정하고 지키자

- “아무리 늦어도 이 때까지는 잠들어야 한다”는 시간을 정해두고 그 전에는 반드시 잘 준비를 마치도록 하자.
- 조금 남았거나, 막히고 답답한 부분이 있더라도 다음 날을 위해 손을 뗄 줄도 알아야 한다. 작업을 적절한 타이밍에 맺고 끊는 연습을 하자.
- 하루를 좋은 컨디션으로 유지할 수 있도록 신경 쓰자.

# 3. 학습내용

## N + 1 문제

- 데이터베이스 연동 시 자주 발생하는 비효율적인 쿼리 문제로,
- 1번의 쿼리로 N개의 데이터를 조회한 후, 각 N개의 데이터에 대해 추가로 또 다른 쿼리를 각각 실행하면서 총 N + 1번의 쿼리가 실행되는 상황

## 예시

```
[User] 1 --- N [Post]
```

한 명의 유저는 여러 개의 게시글을 가질 수 있습니다.

### 잘못된 예

```java
List<User> users = userRepository.findAll();  // 1번 쿼리

for (User user : users) {
    List<Post> posts = postRepository.findByUser(user);  // N번 쿼리
}
```

- `User` 조회: 1번
- `Post` 조회: 유저 수만큼 추가 쿼리 (예: 유저가 10명 → 총 10번)
- 총 **1 + 10 = 11번의 쿼리 실행**

### 문제

- 불필요한 쿼리 호출 횟수 증가
- 데이터베이스 연결 비용 증가 및 성능 저하
- 특히 데이터 수가 많아질수록 쿼리 횟수가 기하급수적으로 늘어남
    - 대규모 트래픽/데이터 상황에서는 심각한 병목 현상이 발생할 수 있음

## 해결 방법

### 1. **Fetch Join (JPA)**

```java
@Query("SELECT u FROM User u JOIN FETCH u.posts")
List<User> findAllWithPosts();
```

- User와 Post를 한 번의 쿼리로 조인(fetch) 하여 가져옴
- 쿼리 횟수는 1번으로 줄어듦

### 2. **EntityGraph 사용 (JPA)**

```java
@EntityGraph(attributePaths = {"posts"})
List<User> findAll();
```

- 연관된 엔티티를 미리 fetch 하도록 설정

### 3. **Batch Size (Hibernate)**

- `@OneToMany(fetch = LAZY)` 관계에서 `hibernate.default_batch_fetch_size` 옵션을 활용
- LAZY 로딩은 유지하면서 batch로 묶어 한 번에 처리

```
spring.jpa.properties.hibernate.default_batch_fetch_size=100
```

### 4. **QueryDSL로 직접 조인**

```java
queryFactory
  .selectFrom(user)
  .join(user.posts, post).fetchJoin()
  .fetch();
```
