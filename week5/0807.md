## 작업 과정에서 배운 것

### 1. 통합 테스트 작성의 이점

첫번째 스프린트를 마무리하면서 그동안 구현한 부분들에 대해 통합테스트를 작성했다.

지금까지는 클래스별 단위 테스트를 작성하고 로컬 DB에 연결해서 수동으로도 테스트해봤다. 하지만 그런 방식에는 한계가 있었다.

단위 테스트에서는 계층들이 서로 연결되어 있기 때문에 실제 데이터 흐름을 반영하기 어려웠다. 모킹을 사용하다 보니 단순한 내부 연산이나 계층간의 데이터 이동만 검증할 수 있었다.

수동 테스트에서는 실제 DB를 연결하여 실제 서비스 동작을 확인할 수 있어서 좋았지만, 매번 요청을 직접 만들어서 확인해야했다. 또한 다양한 테스트 케이스들을 매번 기억해서 수행하기가 번거로웠다.

통합 테스트 코드를 작성하면서는 DDL로 샘플 데이터셋을 미리 정의해 두고, 테스트 실행 시 로컬 DB에 자동으로 데이터를 삽입하도록 했다. 이를 통해 다양한 테스트 케이스를 명시적으로 문서화할 수 있었고, 테스트 실행 시 모든 케이스를 한 번에 검증하면서 문제 지점을 빠르게 찾을 수 있었다.

또한 테스트 코드를 작성하다 보니 더 많은 예외 케이스를 떠올릴 수 있었고, 그 과정에서 기존 코드의 잘못된 부분이나 예외 처리가 부족했던 부분을 보강할 수 있었다.

<br>

## 어려웠던 점

### 1. 영속성 컨텍스트

통합 테스트 코드를 작성할 때 있었던 일이다.

동행 신청 취소 기능을 검증하려고 했다. 동행 신청을 취소했을 때, 해당 신청을 소프트 딜리트 처리하기로 했기 때문에, 취소 후에 다시 조회하면 나오지 않아야 했다. 하지만 취소 후에도 해당 신청이 그대로 조회됐다.

처음에는 소프트 딜리트 구현에 문제가 있다고 생각했다. 하지만 DB에 반영된 결과를 확인해보니 의도대로 동작하고 있었다.

원인은 영속성 컨텍스트였다. 신청을 취소하고 다시 조회하는 과정이 하나의 영속성 컨텍스트 내에서 처리되기 때문에, 취소 전에 조회한 객체를 새로 쿼리하지 않고 그대로 참조한 것이다. 소프트 딜리트 상태는 바뀌었어도 쿼리를 새로 보내지 않으니 삭제가 반영되지 않은 것처럼 보였던 것이다.

결국 구현 로직에는 아무 문제가 없었지만, 테스트 코드를 잘못 구성한 탓에 로직에 문제가 있다고 착각할 뻔했다. 잘못된 테스트 코드는 없느니만 못하다는 것을 실감할 수 있었다. 앞으로는 검증 방식에 문제가 없는지 항상 주의해야겠다고 생각했다.

# 2. 회고

## Keep

### **1. 공통 요소들을 미리 정의해둔 덕분에 이후 작업이 수월해졌다**

- 고객 사이드 개발을 진행하면서 유틸리티 클래스와 커스텀 에러를 미리 만들어 두었다.
- 또한 공통적인 요소들을 클래스나 메서드로 분리해 리팩토링했다.
- 이 과정에서 고객 사이드의 작업량이 예상보다 많아졌고, 일정이 약간 지연되기도 했다.
- 하지만 고객 사이드 후반부와 도우미 사이드 개발을 시작하면서, 그동안 했던 작업이 헛되지 않았음을 느낄 수 있었다.
- 하지만 고객 사이드 후반부와 도우미 사이드 개발을 시작하면서, 그동안의 작업이 헛되지 않았음을 실감했다.
- 처음에는 시간이 더 걸리고 힘들더라도, 장기적으로 보면 탄탄하게 작업하는 것이 훨씬 효율적이라는 점을 깨달았다.

<br>

## Problem

### **1. 오래 앉아 있는 작업으로 인한 신체적 부담**

- 최근 거의 하루 종일 노트북 앞에 앉아 있다.
- 앉아 있는 시간이 길어지고, 피곤하다 보니 자세가 흐트러져 허리와 등에 뻐근함이 생긴다.
- 신체적 불편이 쌓이면서 집중력도 떨어지는 것을 느낀다.

### 2. 정보 갱신이 밀리니까 일이 더 많아진다

- 작업 중 코드를 수정하다 보면, ERD나 문서 등에도 수정 사항이 생긴다.
- 하지만 작업에 몰두하다 보면 수정 내용을 즉시 반영하지 못하는 경우가 많다.
- 나중에 작업이 끝난 뒤 확인하면, 반영해야 할 내용이 한꺼번에 쌓여 있어 또 하나의 큰 작업이 된다.
- 수정 사항이 쌓일수록 전부 기억하기 어려워지고, 최악의 경우 일부가 누락되어 서비스와 문서 간의 일관성이 깨질 수 있다.

<br>

## Try

### **1. 바른 자세를 유지하자**

- 작업 시간의 양도 중요하지만 질도 중요하다.
- 의식적으로 바른 자세를 유지하며 작업하자.
- 작업 시간이 너무 길어질 때는 한 번씩 끊어가자. 잠시 머리도 식히고 스트레칭도 하면서 리프레쉬하는 시간을 가지자.

### 2. 이슈가 생겼을 때 바로바로 갱신하자

- 코드에 수정 사항이 발생하면, 관련 문서도 바로 갱신하자. 즉시 처리하면 대부분 큰 부담이 아니다.
- 만약 문서 작업량이 많아 코딩 흐름이 끊길 것 같다면, 최소한 수정해야 할 문서와 파트를 기록해 두고 이후에 빠르게 반영하자.

# 3. 학습내용

## **영속성 컨텍스트 (Persistence Context)**

### **정의**

- JPA(Java Persistence API)에서 엔티티(Entity)를 영구 저장하기 위해 엔티티를 관리하는 환경
- `EntityManager`가 관리
- 엔티티와 데이터베이스 사이의 중간 계층 역할

### **주요 특징**

1. **1차 캐시(First-Level Cache)**
    - 영속성 컨텍스트는 엔티티를 ID 기준으로 1차 캐시에 저장함
    - 동일한 ID의 엔티티를 여러 번 조회해도, DB에 재조회하지 않고 캐시에서 반환함
2. **엔티티 동일성 보장**
    - 같은 영속성 컨텍스트 내에서는 동일한 엔티티를 여러 번 조회해도 같은 객체 인스턴스를 반환함
3. **변경 감지(Dirty Checking)**
    - 영속 상태의 엔티티 필드 값이 변경되면, 트랜잭션 커밋 시점에 자동으로 변경 사항을 감지하고 DB에 반영함
    - `flush()` 과정에서 변경된 필드만 UPDATE SQL로 반영됨
4. **쓰기 지연(Write-Behind)**
    - `persist()`를 호출해도 즉시 DB에 INSERT 하지 않고, 쓰기 지연 SQL 저장소에 모아 두었다가 `flush()` 시 한 번에 실행함
5. **플러시(Flush)**
    - 영속성 컨텍스트의 변경 내용을 DB에 반영하는 동작
    - 트랜잭션 커밋 시 자동 호출되며, 수동으로도 `flush()` 가능함

### **생명 주기**

1. **비영속 (Transient)** — 영속성 컨텍스트와 전혀 관계 없는 상태
2. **영속 (Persistent)** — 영속성 컨텍스트에 저장되어 관리되는 상태
3. **준영속 (Detached)** — 영속성 컨텍스트에서 분리된 상태
4. **삭제 (Removed)** — 영속성 컨텍스트와 DB에서 삭제 예정인 상태

### **EntityManager 주요 메서드**

- **persist(Object entity)** : 엔티티를 영속성 컨텍스트에 저장해 영속 상태로 만든다.
- **find(Class<T> entityClass, Object primaryKey)** : 기본 키로 엔티티를 조회한다. (1차 캐시 우선)
- **remove(Object entity)** : 영속 상태의 엔티티를 삭제 상태로 만든다.
- **merge(Object entity)** : 준영속 상태의 엔티티를 영속성 컨텍스트에 병합한다.
- **flush()** : 변경 내용을 DB에 반영한다.
- **clear()** : 영속성 컨텍스트를 초기화해 모든 엔티티를 준영속 상태로 만든다.
- **close()** : EntityManager를 종료한다.
