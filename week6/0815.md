## 작업 과정에서 배운 것

### 1. 다른 팀원의 진행 상황을 살펴보기

작업을 하다 보면 지쳐서 집중이 흐트러질 때가 있다. 그럴 때 그냥 혼자 쉬기보다는, 다른 팀원들이 어떤 작업을 하고 있고 어떤 대화를 나누는지 관심을 가지는 것이 도움이 되었다.

같은 프로젝트이기는 하지만 내가 머리 쓰고 있던 영역과는 다른 부분이기 때문에, 작업의 연장선이라기보다는 약간의 기분 전환 겸 즐거운 마음으로 볼 수 있었다. 팀원들이 지금 어떤 지점에서 고민을 하고 있는지도 알 수 있었고, 이야기를 들으면서 내 생각을 말하거나 때로는 의외로 좋은 아이디어를 건네줄 수도 있었다.

스크럼 시간에 작업 상황을 항상 공유하고 있기는 하지만, 시시각각 겪고 있는 고민들을 생생하게 엿보는 것은 또 다른 경험이었다. 수동적으로 전달받는 것보다 직접 묻고 듣는 과정에서 궁금증도 해소되고, 우리 프로젝트에 대해 더 깊게 이해할 수 있게 되었다. 앞으로도 틈틈이 팀원들의 작업을 살펴보고 싶다고 생각했다.

## 어려웠던 점

### 1. API 연동 작업

프론트엔드 팀원들은 원격 DB 상태를 직접 확인하거나 수정할 수 없어서, 테스트를 위한 샘플 데이터가 필요할 때마다 백엔드에 요청해야 했다. 중간 단계가 하나 더 생기다 보니 하고 있던 작업의 흐름이 끊기기도 했고, 필요한 데이터를 직접 만들지 못하기 때문에 원하는 내용을 전달하는 과정에서 착오가 생기기도 했다.

연동 작업 초기에는 정상 응답 처리 위주로 진행하다 보니 큰 불편이 없었지만, 예외 처리를 본격적으로 다루면서 어려움이 나타났다. 스웨거에서는 정상 응답 정의는 손쉽게 할 수 있었지만, 에러 코드 정의는 지원되지 않아 별도로 공유해야 했다.

연동 작업을 좀 더 편리하고 효율적으로 수행할 수 있는 방식이나 도구가 있을지 알아보고 싶어졌다. 이번 프로젝트는 어느덧 막바지로 다가가고 있기 때문에 적용해보기 어려울지도 모르지만, 다음 기회를 위해서라도 공부해보면 도움이 될 것 같다.

# 3. 학습내용

## AtomicReference

- 하나의 객체 참조를 원자적으로(atomic) 읽고, 쓰고, 교체할 수 있게 해주는 Java 클래스
- 동시성 환경에서 안전하게 객체 레퍼런스를 관리할 때 사용

### 필요한 이유

- 멀티스레드 환경에서 `T` 타입의 객체를 `volatile` 변수로만 두면 읽기/쓰기는 원자적이지만,
    
    읽고 → 조건 확인 → 교체 같은 복합 작업은 원자적이지 않음
    
- 예를 들어, `if (ref == oldValue) { ref = newValue; }` 같은 연산은
    
    두 스레드가 동시에 실행하면 경쟁 조건(race condition)이 생길 수 있음
    
- `AtomicReference`는 이런 복합 연산도 CAS(Compare-And-Set) 방식으로 안전하게 처리

### 주요 특징

- 제네릭 타입 지원 → `AtomicReference<MyClass>`처럼 특정 객체 타입 지정 가능
- 내부적으로 `volatile`로 참조를 저장하고, CAS를 활용해서 원자적 연산 수행
- 락(lock)을 쓰지 않고도 안전한 교체 가능 → 성능 좋음
- `null`도 저장 가능

### 주요 메서드

| 메서드 | 설명 |
| --- | --- |
| `get()` | 현재 참조값 반환 |
| `set(value)` | 참조값을 새 값으로 설정(단순 교체) |
| `getAndSet(value)` | 현재 값을 반환하고, 새 값으로 교체 |
| `compareAndSet(expected, update)` | 현재 값이 `expected`면 `update`로 교체하고 true 반환, 아니면 false |
| `lazySet(value)` | 비동기적으로 참조값 교체(성능 최적화용, 즉시 반영 보장 X) |

### 예시

```java
import java.util.concurrent.atomic.AtomicReference;

public class Example {
    private static AtomicReference<String> ref = new AtomicReference<>("초기값");

    public static void main(String[] args) {
        // 현재 값 읽기
        System.out.println(ref.get()); // 초기값

        // 값 교체
        ref.set("새 값");
        System.out.println(ref.get()); // 새 값

        // 조건부 교체 (CAS)
        boolean success = ref.compareAndSet("새 값", "교체 성공");
        System.out.println(success);   // true
        System.out.println(ref.get()); // 교체 성공
    }
}
```

- `compareAndSet`은 현재 값이 기대한 값일 때만 교체하므로, 경쟁 상태를 안전하게 처리할 수 있음

## 클로저(Closure)

- 함수가 자신이 선언될 당시의 환경(변수, 상태)을 기억하고, 그 환경에 접근할 수 있는 기능
- 함수 + 그 함수가 실행될 때 필요한 외부 변수들을 묶어놓은 것
- 람다(익명 함수)는 클로저를 만들 수 있는 대표적인 방법 중 하나
- 람다가 만들어질 때, 람다 안에서 참조하는 외부 변수를 캡처(capture)해서 람다 객체 안에 저장
- 이후 람다가 호출될 때, 원래의 스코프가 사라졌어도 이 저장된 값을 사용할 수 있음

### Java에서의 클로저

- Java 람다나 익명 클래스도 클로저를 지원
    - 단, 캡처되는 외부 변수는 final 또는 effectively final이어야 함
- **final**: 한 번 값이 정해지면 변경 불가
- **effectively final**: 코드상에 `final`을 안 붙여도, 값이 한 번만 할당되고 이후 변경되지 않는 변수

### **예시**

```java
public class ClosureExample {
    public static void main(String[] args) {
        String greeting = "Hello"; // effectively final

        Runnable r = () -> {
            System.out.println(greeting + " World");
        };

        r.run(); // "Hello World"
    }
}
```

- 람다가 만들어질 때 `greeting` 변수를 캡처
- 나중에 실행해도 `greeting` 값을 기억하고 있음

### 캡처 방식

Java 람다는 변수의 값을 직접 복사하는 게 아님

- **기본형**이면 값 자체를 복사
- **객체 참조형**이면 참조(주소)를 복사해서 저장

즉, 객체라면 람다 실행 시점에 해당 객체의 메서드 호출, 상태 변경도 가능

```java
AtomicReference<String> ref = new AtomicReference<>("A");

Runnable r = () -> {
    ref.set("B"); // ref 참조는 클로저에 저장돼 있음
};

r.run();
System.out.println(ref.get()); // "B"
```

### 장점

- 변수를 저장하는 추가 클래스 없이 람다 안에서 외부 변수를 사용할 수 있음
- 나중에 실행할 코드(콜백, 이벤트 핸들러 등)에 당시 상태를 함께 묶어 전달 가능
- 비동기 프로그래밍, 이벤트 기반 프로그래밍에서 유용
