# 1. 리뷰

## 오늘 한 작업

### 종합프로젝트

- S3 Presigned URL 연결
- 통합 테스트 코드 갱신
- 데이터셋 만들기
- Swagger 쿠키 인증 설정

<br>

## 작업 과정에서 배운 것

### 1. 구현을 했다고 내 지식이 되는 것은 아니다

S3 연동 및 Presigned URL 연결 작업을 마친 뒤, 코드 리뷰를 하면서 성훈님께 구현 내용을 설명드렸다. 대략적인 흐름은 이해하고 있다고 생각했지만, 막상 설명하려니 세부적인 부분에서 깊이가 부족하다는 것을 느꼈다.

레퍼런스 코드를 참고하며 구현했는데, “이렇게 작성하면 동작하는구나” 정도로만 이해하고 넘어갔다. 코드 한 줄 한 줄이 어떤 의미를 갖는지까지는 파악하지 못했던 것 같다. 디테일한 질문을 받았을 때 제대로 대답해드리지 못해서 아쉬움이 남았다.

내가 구현한 부분이라고 자신 있게 말하기 위해서는 단순히 동작하는 코드를 작성하는 것을 넘어서 더 깊은 이해가 필요하다는 것을 느꼈다. 새로운 기술을 사용하면서 남이 해놓은 것을 그냥 따라하는 것으로 끝내지 않고, 코드 하나하나 뜯어보면서 이해하려는 노력이 필요할 것 같다.

<br>

## 어려웠던 점

### 1. 데이터 샘플 만들기

통합 테스트 수행과 프론트엔드 API 연동을 위해 DB에 넣을 데이터셋을 만들었다. 이전에는 DB 연동만 있었기에 DB에 데이터만 넣으면 됐지만, 이제는 S3에 이미지까지 관리해야 해서 예시 이미지도 준비해야 했다.

문제는 데이터들이 독립적이지 않고 서로 상태값과 연관 관계로 밀접하게 연결되어 있다는 점이었다. 예를 들어, 아직 매칭되지 않은 동행 신청에는 리뷰나 리포트가 존재해서는 안 된다. 그러나 이런 규칙은 DB 제약 조건으로 강제되지 않고, 서비스 로직에서만 관리되는 규칙이다. 그렇다 보니 DDL로 데이터를 직접 넣을 때는 이러한 조건들을 일일이 확인해야 했다.

그래도 요즘은 생성형 AI를 통해, 한 줄 소개나 동행 메모 내용 같은 텍스트들은 만들 수 있어서 다행이었다. 직접 만들어야 했다면 몇 배 이상 시간이 들었을 것 같다.

다양한 상황을 테스트할 수 있는 데이터 샘플을 만들어야 해서 어려웠다. 우리 프로젝트도 연관 관계가 단순한 편은 아니지만, 실무에서는 훨씬 복잡한 서비스도 많을텐데 데이터 샘플을 어떻게 만들고 관리하는지 궁금해졌다.

# 2. 회고

## Keep

### **1. 작업을 더 효율적으로 하기 위한 작업**

- API 명세에 대한 관리를 Swagger를 통해서 하고 있었다.
- 인증을 클라이언트 쿠키에 세션 ID를 담는 방식으로 구현했는데, Swagger에서는 기본적으로 쿠키 정보를 반영할 수 없어 더 이상 Swagger를 통해 API를 확인해 볼 수 없게 되었다.
- 예전에 Swagger에서 JWT 인증을 연동했던 경험이 떠올라, 쿠키 기반 인증 방법을 찾아보니 가능한 방법이 있었다.
- 로그인 요청을 통해 세션 ID를 쿠키로 받은 뒤, 해당 세션 ID를 Swagger 인증에 적용하면 이후 API 요청을 자유롭게 수행할 수 있었다.
- 프로젝트 기능 자체와는 직접적인 관련이 없지만, 앞으로의 개발 과정에서 API 확인과 테스트를 훨씬 편하고 효율적으로 할 수 있을 것 같다.

<br>

## Problem

### **1. 병렬적으로 할 수 없는 작업들도 있다**

- 작업을 하다 보면, 다른 사람의 작업이 끝나야만 진행할 수 있는 경우가 있다.
- 프로젝트가 진행될수록 구성 요소 간의 관계가 복잡하고 밀접해지기 때문에, 이런 의존성이 있는 작업이 늘어나고 있다.
- 기다려야 하는 시간이 자잘하게 자주 발생하고, 그 사이에 할 일이 없는 순간이 생겨 작업 밀도가 낮아지는 것 같다.

<br>

## Try

### **1. 작은 작업들을 많이 찾아두자**

- 프로젝트 초반 계획에서는 주로 큰 단위의 작업 위주로만 일정을 세웠던 것 같다.
- 프로젝트를 진행하면서, 기존 코드 개선, 피드백 반영 등 처리해야 할 작은 일들이 조금씩 쌓이고 있다. 이런 작은 작업들을 생각날 때마다 백로그 이슈로 남겨두어야겠다.
- 기다려야 하는 상황이라서 당장 해야할 일이 없을 때, 이렇게 금방 끝낼 수 있는 작업들을 하나씩 해나가면 시간을 더 효율적으로 쓸 수 있을 것이다.

# 3. 학습내용

## S3

- Amazon S3(Simple Storage Service)
- AWS가 제공하는 객체 스토리지(Object Storage) 서비스
- 데이터를 파일(객체) 단위로 저장
    - 각 객체는 버킷(Bucket) 안에 저장됨
- 높은 내구성(99.999999999%, 11 nines)과 확장성을 제공
    - 전 세계 어디서나 HTTP/HTTPS로 접근 가능

### **주요 특징**

| 구분 | 설명 |
| --- | --- |
| **저장 방식** | 객체(Object) 단위 저장 — 각 객체는 데이터(파일 본문), 메타데이터, 고유 키(Key)로 구성 |
| **버킷(Bucket)** | S3의 최상위 디렉토리 개념. 객체를 그룹화하며, 버킷 이름은 전 세계에서 유일해야 함 |
| **확장성** | 무제한 크기의 데이터를 저장 가능 (객체당 최대 5TB) |
| **내구성 & 가용성** | 여러 AZ(Availability Zone)에 자동 복제 |
| **접근 제어** | IAM Policy, Bucket Policy, ACL(Access Control List)로 세밀한 권한 관리 |
| **접근 방식** | HTTP/HTTPS API, AWS SDK, CLI 등을 통한 접근 |
| **스토리지 클래스** | 사용 패턴에 따라 비용 최적화 가능 (예: Standard, Intelligent-Tiering, Glacier 등) |

### **동작 구조**

1. **버킷 생성** — 저장소 생성
2. **객체 업로드** — 파일 + 메타데이터 + 키 저장
3. **객체 접근** — URL 또는 API로 접근
4. **권한 관리** — 공개/비공개 설정, IAM & 정책 적용
5. **버전 관리(Optional)** — 파일 변경 이력 저장 가능

### **장점**

- **확장성 무제한** — 데이터 크기와 관계없이 저장 가능
- **내구성 높음** — 데이터 손실 위험 거의 없음
- **유연한 접근 제어** — IAM, 버킷 정책, ACL 지원
- **다양한 통합 서비스** — EC2, Lambda, CloudFront 등과 연동 쉬움
- **비용 효율성** — 스토리지 클래스 변경 가능

### **단점 및 고려 사항**

- 데이터 전송량이 많을 경우 네트워크 비용 발생
- 지연 시간(latency)이 로컬 디스크 대비 느림 → DB 저장소로는 부적합
- 실시간 수정보다 읽기/쓰기(업로드/다운로드) 중심 작업에 적합
- 객체 단위 업데이트 불가 → 변경 시 전체 파일 재업로드 필요

### **주요 사용 사례**

- 정적 웹사이트 호스팅
- 이미지 / 동영상 CDN 원본 저장소
- 백업 및 아카이브
- 빅데이터 분석용 원본 데이터 저장
- 로그 데이터 저장 및 분석

## Presigned URL

- S3 객체에 접근할 수 있는 임시 서명된 URL
- S3 버킷/객체가 비공개여도, 해당 URL을 가진 사람은 일정 시간 동안만 업로드(Write) 또는 다운로드(Read) 가능
- AWS SDK나 CLI를 사용해서 서버에서 생성 → 클라이언트에 전달 → 클라이언트가 직접 S3에 접근

### **동작 원리**

1. 서버(백엔드)에서 AWS Credentials로 S3 객체에 대한 요청(다운로드/업로드)에 서명(Signature) 생성
2. 이 서명 정보와 만료 시간, 요청 메서드(PUT/GET 등)가 URL에 포함됨
3. 클라이언트가 이 URL을 사용해 AWS 인증 없이 S3에 직접 요청
4. URL이 만료되면 접근 불가

### **장점**

| 장점 | 설명 |
| --- | --- |
| **보안성** | AWS 인증 키를 클라이언트에 노출하지 않음 |
| **직접 업로드/다운로드** | 서버를 거치지 않고 S3와 직접 통신 → 서버 부하 감소 |
| **만료 시간 설정** | 몇 초 ~ 최대 7일까지 유효 시간 지정 가능 |
| **권한 제어** | URL마다 특정 작업(읽기/쓰기)만 허용 가능 |

### **활용 예시**

- **파일 다운로드**: 사용자 인증 후, 해당 파일만 임시로 접근 가능하게 제공
- **파일 업로드**: 대용량 파일 업로드 시, 서버를 거치지 않고 바로 S3에 저장
- **이미지 업로드 API**: 프론트엔드에서 S3에 바로 PUT 요청 가능
- **1회성 접근**: 비공개 문서를 공유할 때, 일정 시간 뒤 자동 차단

### **주의 사항**

- **만료 시간**: 너무 길게 설정하면 보안 리스크 증가
- **버킷 정책과 충돌**: 버킷 정책에서 IP 제한 등을 걸면 Presigned URL도 영향을 받음
- **URL 유출 위험**: Presigned URL이 노출되면 만료 전까지 누구나 접근 가능
- **객체 키 노출**: URL에 Key가 포함되므로 민감한 파일 이름은 난독화 권장
