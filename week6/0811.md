## 작업 과정에서 배운 것

### 1. 일관성 있는 구조의 중요성

프로젝트 구현을 하면서, 전체 구조에서 일관성을 유지하는 것을 목표로 하고 있다. 도메인은 다르더라도 계층 구조나 DTO 형태 등 전체적인 형식은 공유하도록 하고 있다.

하지만 구현을 하다보면, 도메인의 특성 상 예외적인 구조가 필요하다거나, 다른 도메인에서 처리하던 방식을 잊어버려서, 기존과는 다른 방식으로 구현하는 상황이 생긴다. 처음에는 대수롭지 않게 넘기기 쉽지만, 구현량이 점점 쌓이면서 그 차이를 체감하고 있다.

구조가 통일되어 있으면 다른 도메인에서 작업한 내용 그 자체를 레퍼런스로 사용할 수 있다. 코드를 그대로 재사용하지는 않더라도, 이전에 만들어둔 형식과 똑같이 작업할 수 있다는 것은 큰 이점이었다. 작업 속도도 빨라지고 실수도 줄일 수 있었다.

반면에 구조가 어긋난 부분들은 뒤로 갈수록 관리하기 힘들어졌다. 전체적인 구조를 손봐야할 때, 형식이 일관된 부분은 한 번만 고민하면 그 다음부터는 반복 작업만 하면 되었다. 그러나 구조가 다른 부분은 매번 새로운 고민을 해야했다.

일관된 구조는 단순히 가독성면에서만 좋은 것이 아니라, 개발 및 유지보수에서도 큰 이점을 가져다 준다는 것을 다시 한 번 몸소 느낄 수 있었다.

<br>

## 어려웠던 점

### 1. S3와 Presigned URL

사용자가 등록한 이미지를 S3에 저장하고 Presigned URL로 접근하도록 구현하기로 했다. S3를 다뤄보는 것은 처음이라, 초기 세팅이나 권한 설정에서 시간이 많이 걸렸다.

가장 고민했던 부분은 프론트엔드에게 Presigned URL을 어떻게 전달할지 하는 문제였다.

처음에는 응답 DTO에 Presigned URL을 직접 담아 넘기는 방식을 떠올렸다. 단순하기도 하고 프론트에서 사용하기에도 직관적이라는 장점이 있었다. 하지만 각 도메인 서비스가 URL 생성 로직과 S3 관련 의존성을 품게 되어 의존성이 퍼지고, URL 만료·재발급 같은 정책이 여러 곳에 분산된다는 문제가 있었다. 이미지가 포함된 모든 도메인에 S3와의 의존성이 생기는 것이 부적절하다고 생각했다. 

그래서 다른 방식을 고민했다. 이미지 아이디 기반의 URL을 프론트에 넘기고, 프론트가 그 URL로 GET 요청을 보내면 서버에서 아이디로 이미지를 조회해 Presigned URL을 생성한 뒤 리다이렉트하는 방식이다. 이러면 도메인 서비스에서 S3 의존성을 제거하고, Presigned URL을 생성하고 제공하는 역할을 한 곳으로 모을 수 있었다.

역할 분리와 장기 유지보수를 우선해 아이디 기반 리다이렉트 방식을 선택했다. 이미지 관련 로직을 한 곳에서 관리하면서, 도메인 간의 역할 구분을 깔끔하게 유지할 수 있어 만족스러웠다.

### **1. 프론트엔드 팀원들과의 조율**

- 그동안은 FE/BE 사이에서 서로에게 직접적으로 영향을 주는 단계는 아니었기 때문에 기본적인 내용들만 논의했다.
- 이제 API 연동 시점이 다가오면서 프론트엔드와의 조율이 중요해지고 있다.
- Presigned URL 관련된 부분을 개발하면서는 프론트 작업에도 큰 영향을 줄 수 있기 때문에, 설계 단계에서부터 프론트 팀원들과 충분히 논의하면서 작업했다.
- 여러 구현 방식을 놓고 의견을 나누었다. 프론트 분들이 중요하게 생각하시는 포인트를 귀담아 듣고, 걱정하고 계신 부분에 대해서 어떻게 해결할 수 있을지 말씀드렸다. 내가 생각하는 방식으로도 우려하시던 지점들을 문제 없이 처리할 수 있었고, 의견을 통일할 수 있었다.
- 그동안은 백엔드 팀원들 간의 소통이 주가 되었었는데, 이번 조율을 통해 프론트 분들이 어떤 부분을 중요하게 생각하시는지 새롭게 이해할 수 있었다. 나에게는 더더욱 낯선 영역이기 때문에 좋은 공부를 할 수 있었다.
- 앞으로도 백엔드는 물론, 프론트엔드와의 소통에서도 많이 배워가고 싶다.

# 3. 학습내용

## SQL vs NoSQL

- **정의**
    - **SQL(관계형)**: 고정 스키마, 테이블/행/열, 조인·트랜잭션 강점
    - **NoSQL(비관계형)**: 유연한 스키마, 문서/키값/컬럼/그래프 등 모델 다양, 수평 확장 용이
- **차이 요약**

| 구분 | SQL | NoSQL |
| --- | --- | --- |
| 데이터 모델 | 테이블(정규화) | 문서·키값·컬럼패밀리·그래프 |
| 스키마 | 사전 정의(엄격) | 유연/스키마리스 |
| 질의 | 표준 SQL | DB별 API/쿼리(MQL 등) |
| 트랜잭션 | ACID 기본 | 보통 파티션/문서 단위 ACID |
| 일관성 | 강한 일관성 선호 | 최종 일관성 옵션 흔함 |
| 확장 | 수직(샤딩 가능) | 수평(샤딩/파티셔닝) 강점 |
| 적합 용도 | OLTP·집계·관계형 | 초고트래픽·비정형·캐시/세션 |
- **적합 상황**
    - **SQL**: 강한 정합성·복잡 조인·안정 스키마
    - **NoSQL**: 대규모 트래픽·자주 바뀌는 스키마·저지연 키값·그래프 탐색

<br>

## ACID (트랜잭션 4특성)

- **Atomicity**: 전부 성공/전부 실패(롤백)
- **Consistency**: 제약·규칙 만족 상태만 유지. *(CAP의 C와 다름)*
- **Isolation**: 동시 실행 ≈ 순차 실행 결과
- **Durability**: 커밋 후 장애에도 결과 보존(로그/복구)

<br>

## CAP (분산 트레이드오프)

- **정의**: 네트워크 분할(P) 상황에서 **C(강한 일관성)** 또는 **A(가용성)** 중 선택
- **CP**: 정확성 우선, 분할 시 일부 요청 차단(예: ZooKeeper/etcd)
- **AP**: 응답 우선, 최종 일관성(예: Cassandra/Dynamo 계열)
- **주의**: 현실 시스템은 P를 포기 불가 → 분할 시 CP 또는 AP

<br>

## SQL 실행 논리 순서

1. **WITH(CTE)**
2. **FROM**
3. **ON**
4. **OUTER JOIN 보정**
5. **WHERE**
6. **GROUP BY**
7. **HAVING**
8. **SELECT** *(윈도우 함수도 이 시점, DB별 차 있음)*
9. **DISTINCT**
10. **ORDER BY**
11. **LIMIT/OFFSET**
- **자주 헷갈리는 포인트**
    - WHERE는 SELECT보다 먼저 → 별칭 사용 불가
    - WHERE(그룹 전) vs HAVING(그룹 후)
    - 윈도우 함수는 보통 ORDER BY 전에 평가

<br>

## 인덱스

- **개념**: 컬럼 일부를 정렬/구조화해 검색·정렬 가속. 조회↑ / 쓰기↓, 공간 사용↑
- **대표 종류**
    - **B-Tree(기본)**: =, 범위, 정렬 전천후
    - **Hash**: 정확 일치 전용
    - **GIN(PG)**: JSONB/배열 포함·전문검색(역색인)
    - **GiST/SP-GiST(PG)**: 공간/범위/KNN
    - **BRIN(PG)**: 대용량 시계열(순차성↑)
    - **Unique/Composite/Partial/Functional/Covering(INCLUDE)**: 제약·최적화 목적
- **필요한 대표적인 상황**
    1. 선택도 높은 WHERE
    2. JOIN 키(FK 포함)
    3. WHERE+ORDER BY 조합
    4. 빈번한 GROUP BY/DISTINCT
    5. 커서 기반 페이지네이션
    6. 유니크 보장
    7. 활성 행만(Partial)
    8. 함수/표현식 조건(Functional)
    9. 전문검색·부분문자(pg_trgm)
    10. JSON/배열 키(GIN)
    11. 공간/근접(GiST)
    12. 초대용량 시계열(BRIN)
- **만들기에 부적절한 상황**
    - 작은 테이블, 선택도 낮은 컬럼 단독, 쓰기 빈번 컬럼, 중복 인덱스, `LIKE '%abc'`(특수 인덱스 필요)
- **설계 요령**
    - **쿼리 먼저**(WHERE/ORDER/JOIN 키 확정) → 복합 인덱스 왼쪽부터 선별력 높은 순서
    - 자주 쓰는 조회는 Covering 고려
    - EXPLAIN(ANALYZE)로 검증, 슬로우쿼리/pg_stat_statements 모니터링

<br>

## MySQL `EXPLAIN` 주요 컬럼

- **type(중요)**: `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL(풀스캔)`
- **key**: 실제 사용 인덱스 / possible_keys: 후보
- **rows**: 예상 스캔 행 수 / filtered: 필터링 비율(%)
- **Extra**: `Using index`(커버링), `Using temporary`/`filesort`(임시/정렬 발생) 등
- **팁**: `type=ALL` + `Using filesort/temporary` → 인덱스 재설계 필요 가능성↑

## PostgreSQL `EXPLAIN / ANALYZE` 해석

- **Node Type**: Seq/Index/Bitmap Scan, Nested/Hash/Merge Join, Sort, Aggregate 등
- **cost**(추정), **rows**(추정), **width**
- **ANALYZE**: 실제 시간/행/loops, Buffers/I/O, 병렬/메모리/디스크 스필 여부
- **팁**
    - 예상 rows ↔ 실제 rows 괴리 크면 통계/인덱스/쿼리 구조 점검
    - 대형 테이블 `Seq Scan`이면 고선택도 조건 인덱스 고려
    - `Index Only Scan`은 커버링 성공 신호

<br>

## 트랜잭션

- **정의**: 여러 SQL을 하나의 **원자적 단위**로 묶어 커밋/롤백
- **수명**: 시작 → SQL들 실행 → COMMIT 또는 ROLLBACK
    
    JDBC 기본 `auto-commit=true` → 보통 끄고 단위 제어
    
- **격리 수준 & 현상**

| 수준 | 특징 |
| --- | --- |
| READ UNCOMMITTED | Dirty Read 허용(거의 안 씀) |
| READ COMMITTED | Dirty 방지, Non-repeatable/Phantom 가능(PG 기본) |
| REPEATABLE READ | Non-repeatable 방지, Phantom은 구현 의존(MySQL InnoDB 기본) |
| SERIALIZABLE | 모든 현상 방지(충돌 시 재시도 필요) |
