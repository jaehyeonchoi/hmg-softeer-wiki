## 작업 과정에서 배운 것

### 1. 현직자 멘토링 소감

현대자동차에서 일하고 계신 현직 개발자분들께 프로젝트 관련 질문을 드리고 피드백 받을 수 있는 시간을 가졌다.

처음에는 딱딱한 분위기일까 봐 다소 긴장했지만, 편안하고 유쾌하게 말씀해주셔서 부담 없이 질문을 드릴 수 있었다.

협업 과정에서 어려움을 느끼거나 확신이 없었던 부분(예를 들면, 테스트 진행 방식, 데이터 샘플 생성, 문서화, 정규화/반정규화, 외래키 및 제약조건 사용 등)에 대해 현업에서는 어떻게 하고 계시는지 궁금해서 여쭤보았다.

우리가 학생 때 배웠던 원칙들을 현업에서는 여러 가지 이유로 생각보다 철저하게 지키고 있지는 않다는 것을 알 수 있었다. 성능이나 유연함, 관리 용이성 등을 훨씬 더 중요하게 생각하고 있다고 하셨다. 제약조건 등의 관리를 인프라스트럭쳐 레벨이 아니라 서비스 레벨에서 관리하는 추세로 많이 바뀌고 있다고 말씀해주셨다.

그 외에도 실무에서 어떤 식으로 협업을 진행하고 계신지도 이야기해주셨다. 개발자들 사이의 스타일 차이가 있을 때 어떤 식으로 대처하고 계신지 들을 수 있었다. 현업 이야기를 들으면서 공부도 많이 되었고, 동기부여도 얻을 수 있어 정말 귀중한 시간이었다. 이런 식으로 현업의 목소리를 들을 수 있는 기회를 많이 찾아봐야겠다고 생각했다.

## 어려웠던 점

### 1. 프론트엔드와 S3 연결

프론트엔드와 API 연결 작업을 진행하고 있다.

S3 관련 부분은 내가 맡았던 부분이기 때문에 프론트엔드 팀원들과 지속적으로 이야기하고 있다.

초반에 로그인 문제와 CORS 문제가 겹쳐서 작업이 어려웠다. 응답이 정상적으로 오지 않을 때, 원인이 정확히 무엇인지 쉽게 찾을 수 없었다. 로그인 문제와 CORS 문제가 조금 해소되고 나서야 정말로 S3와 관련된 원인에만 집중할 수 있었다.

다른 API보다 연결이 훨씬 힘들었다. Presigned URL을 발급받고, 이미지를 업로드하고, 업로드한 이미지를 조회하기까지 절차가 여러 단계있었고, 각 단계별로 요구하는 데이터의 종류도 많았다. 

또 클라이언트-서버 간의 통신은 로그를 직접 확인할 수 있었지만, 클라이언트-S3 간의 통신에서 발생하는 문제들은 로그를 확인하는 데 한계가 있어서 원인을 정확하게 찾기가 더 힘들었다.

처음 부딪힌 문제는 MD5 검증이었다. Presigned URL 발급 후, 실제 업로드 이미지가 사전에 허가된 이미지와 동일한지 확인하기 위해 MD5 해시를 사용했는데, 해시 문자열 표현 방식이 다양해서 일치하는지 확인해야 했다.

다음으로 S3 버킷에 설정된 CORS 정책도 확인했다. 프론트엔드의 IP 주소를 허용해두고 있었는데, 중간에 IP 주소를 변경한 것이 누락되어 있었다. 해당 내용을 새로 반영했다.

그래도 여전히 403 Forbidden 에러가 발생했다. 원인은 prefix 설정이었다. IAM 정책에서 허용된 경로 하위에만 업로드가 가능했는데, 프론트엔드의 요청에는 임의의 잘못된 prefix가 지정되어 있었다.

입력 데이터들을 하나하나 제대로 확인하지 못했던 것이 원인이었던 것 같다. 값들을 처음부터 끝까지 일일이 맞춰보는 과정을 거쳤다면 원인을 더 빠르게 찾을 수 있었을 것 같다. 

또 어떤 값들이 필요한지는 공유했지만, 그 값들이 무슨 의미를 가지는지, 왜 필요한지에 대한 전달은 부족했던 것 같다. prefix 값에 대해 좀 더 자세히 설명드렸다면 이런 문제를 미리 막을 수 있었을 것이라는 아쉬움이 남았다. 서로에게 필요한 게 무엇인지 공유하는 것만으로는 부족하다는 것을 깨달았다. 그것이 왜 필요한지 이해시키고, 이해하려는 노력까지 이뤄져야 진정한 협업이 가능하다는 것을 느꼈다.

## Keep

### **1. 팀원들과 힘을 합쳐 문제를 극복하기**

- API 연동 과정에서 여러 가지 문제가 발생했지만, 그때마다 원인과 해결 방법을 함께 논의했다.
- 문제마다 프론트엔드에서 해결할 수 있는 방법도 있고, 백엔드에서 처리할 수 있는 방법도 있었다.
- 서로가 바쁘다는 것을 잘 알고 있기 때문에, 어느 한쪽에서 처리해도 상관없는 경우에는 더 빠르고 간단하게 해결할 수 있는 쪽에서 자발적으로 나서서 작업을 맡고 있다.
- 자잘한 문제를 하나하나 해결해나가면서 하나의 팀이라는 것을 다시 한 번 실감하고 있다.

## Problem

### **1. 기술적으로 깊게 파고들 주제가 고민된다**

- 기본적인 CRUD API 개발을 마무리하고, 이제 프로젝트의 핵심 기능인 대시보드 개발에 착수하려 한다.
- 처음에는 실시간 위치 및 상태 공유 분야에서 기술적인 도전을 해 볼 수 있을 것이라고 생각했는데, 막상 개발에 들어가려니 생각보다 피상적인 부분이 많다는 느낌을 받았다.
- 여러 분야에서 얕게 다뤄볼 수 있는 요소는 많지만, 발표 관점에서 인상적인 임팩트를 주기는 부족함이 있어 보였다.
- 새로운 기술을 도입해보고 싶어도, 프로젝트 주제와의 연관성과 필요성을 설득하기 어려운 경우가 많았다.

## Try

### **1. 도전해볼 만한 주제를 조금 더 생각해보자**

- 본격적인 작업에 들어가기 전, 도전해볼 만한 주제를 최대한 많이 발견하고 리스트업하자. 꼭 실제로 해보지는 않더라도 지식과 선택지를 갖춰두는 것이 좋다.
- 우리 프로젝트의 특성을 고려하여 어떤 기능이나 성능 개선이 필요할지 고민해보자.
- 깊이가 얕아보인다고 생각한 문제들도 막상 들어가서 개발하다 보면 의외로 복잡하거나 새로운 문제가 생겨날 수 있다. 고민이 너무 길어지면 반드시 필요한 기본 작업부터 시작해서 진행 속도를 유지하고 아이디어를 얻어보자.

### 1정규형 (1NF)

- 모든 속성 값이 **원자값(Atomic Value)**이어야 함
- 하나의 칸(컬럼)에 여러 값이 들어가면 안 됨
- 중복되는 컬럼 구조 제거

### 2정규형 (2NF)

- 1NF 만족 + 부분 함수 종속 제거
- 복합키(Composite Key)인 경우, 기본키 일부만으로 결정되는 비기본키 속성이 없어야 함
- 기본키가 단일키라면 1NF 만족 시 자동으로 2NF 만족

### 3정규형 (3NF)

- 2NF 만족 + 이행 함수 종속 제거
- 기본키가 아닌 속성이 또 다른 비기본키에 의존하면 안 됨

<md>

### **NoSQL이 수평 확장에 유리한 이유**

- **스키마 유연성**: 데이터 구조 변경이 자유로워, 노드 간 스키마 동기화 부담이 적음
- **자동 샤딩(Sharding)**: 키/해시 기반으로 데이터가 여러 노드에 자동 분배
- **최종 일관성 모델 지원**: 모든 노드 동기화를 기다리지 않고 응답 → 확장성↑
- **복제 내장**: Replica Set, Multi-Master 구조로 읽기 부하 분산
- **노드 증설 용이**: 노드 추가 시 데이터 자동 재분배, 확장·축소가 쉬움

<br>

### **CAP 정리**

- **C (Consistency)**: 모든 노드가 같은 시점에 같은 데이터 보장
- **A (Availability)**: 모든 요청이 항상 응답
- **P (Partition Tolerance)**: 네트워크 단절(Partition)에도 동작 유지
- 세 가지를 동시에 완벽하게 만족 불가 → 분산 시스템은 P는 필수 → C와 A 중 선택
- **CP**: Strong Consistency (강력 일관성) → 최신 값을 보장할 수 없으면 응답 안함
- **AP**: Eventual Consistency (최종 일관성) → 알고 있는 최신 값으로 무조건 응답

<br>

### **PACELC**

- CAP 정리를 확장한 개념
- 네트워크 분리(Partition) 시 AP vs CP 선택
- 네트워크 정상 시에도 Latency(지연) vs Consistency(일관성) 사이의 선택 필요
- **의미**:
    - **PA/EL**: Partition 시 Availability 우선, Else Latency 우선
    - **PC/EC**: Partition 시 Consistency 우선, Else Consistency 우선

<br>

### **카디널리티(Cardinality) vs 셀렉티비티(Selectivity)**

**카디널리티 (Cardinality)**

- 컬럼에 있는 고유 값(Unique Value)의 개수
- 값의 다양성(Distinct count)을 나타냄
- 예: 성별 컬럼 → 카디널리티 낮음(남/여 2개), 주민번호 컬럼 → 카디널리티 높음(거의 전부 다름)

**셀렉티비티 (Selectivity)**

- 전체 데이터 중 특정 조건으로 조회되는 비율
- 셀렉티비티 = (조회 결과 건수) / (전체 건수)
- 예: 전체 1,000명 중 남성만 검색 → 500/1000 = 0.5 (50%)
- 인덱스 효율성 평가 시 사용 → 셀렉티비티 낮을수록(=조건이 희귀할수록) 인덱스 효율 ↑
