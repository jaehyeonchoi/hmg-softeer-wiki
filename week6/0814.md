## 작업 과정에서 배운 것

### 1. 현직자 멘토링을 듣고 나서 느낀 점

어제와는 또 다른 형식과 주제로 멘토링을 진행했다.

어제는 팀별로 따로 시간이 주어져서 프로젝트와 관련된 주제로 대화했었는데, 오늘은 백엔드 인원들 전체가 함께 멘토링을 진행했다. 현직자 분들이 앞에 나와서 우리들이 적었던 질문들에 대해 하나하나 대답해주셨다.

어제는 팀별로 진행하다보니까 우리 팀의 질문만 들어볼 수 있었는데, 오늘은 백엔드 모두가 적었던 질문들을 모아서 답변을 해주셨기 때문에 내가 했던 질문 외에도 다양한 내용을 들어볼 수 있어서 좋았다. 어제보다 시간이 훨씬 여유 있어서 질문도 충분히 드릴 수 있었다.

현대/기아자동차의 ICT 부서에서 어떤 식으로 업무를 진행하는지 들을 수 있었고, 회사원으로서 가져야 할 마인드셋에 대해서도 많은 조언을 들을 수 있었다.

선배 개발자로서 도움이 되는 이야기들을 많이 해주셔서 감사했다. 특히, 개발 실력만큼이나 중요한 커뮤니케이션, 협업, 책임감 등에 대한 현실적인 조언이 인상 깊었다.

또한, 현직자 세 분이 저마다 다른 스타일과 관점을 가지고 계셔서, 어떤 방식이 정답이라기보다 다양한 접근이 가능하다는 점도 느낄 수 있었다. 여러 가지 관점의 말씀을 들어볼 수 있어서 좋았다.

## 어려웠던 점

### 1. DTO 재사용

API 응답용 DTO를 구성할 때, 여러 API에서 제공해야 하는 데이터의 조합이 거의 동일했다. 필드 한두 개 정도만 다르고 대부분 동일한 데이터를 전달해야 하는 상황이 많았다.

이 경우, 각 API마다 DTO를 따로 만들면 중복 코드가 지나치게 많아지고, 유지보수 시 여러 파일을 모두 수정해야 하는 비효율이 생겼다.

그래서 공통되는 필드를 묶어 하나의 DTO로 만들고, 그것을 다른 DTO에서 필드처럼 재사용하거나, 아예 필요한 필드를 모두 포함시키되 사용하지 않는 필드는 `null`로 처리하는 식으로 구성했다.

덕분에 거의 유사한 클래스 생성을 줄이고 코드량도 줄일 수 있었지만, 사용하지 않는 데이터가 응답에 포함되기도 하고, 어떤 필드가 필수인지 아닌지 구분이 애매해지는 문제가 있었다. 예외 상황인지 아닌지를 판단하는 과정도 조금 복잡해졌다.

정확히 필요한 데이터만 담은 DTO를 따로따로 만들어야 할지, 정확하지는 않지만 좀 더 범용적인 DTO를 만들어 재사용을 해야 할지 결정하기가 어려웠다.

# 2. 회고

## Keep

### **1. 깔끔한 코드를 작성하기 위해 노력한 점**

- 코드를 작성하면서 일관적이지 않거나 비효율적인 부분을 발견할 수 있었다.
- 수정하려고 하니, 엔티티 레벨에서부터 통합 테스트 레벨까지 전 계층에서 수정 사항이 발생했다.
- 프로젝트가 작동하는 데에는 아무런 문제가 없는 영역이고 귀찮은 작업이기도 했지만, 개선한 코드가 명백하게 더 좋은 코드라는 확신이 있어 작업을 진행했다.
- 좋은 코드를 작성하는 것에 대충 타협하기 않고 최선을 다한 스스로에게 칭찬해주고 싶다.

<br>

## Problem

### **1. 챌린지 주제에 대한 고민**

- 어제부터 프로젝트 챌린지 주제에 대해 고민하고 있다.
- 처음에는 예상되는 성능 문제에 대해서 개선 방식을 생각해보고, 여러 방식을 비교해서 더 나은 방식을 찾아보려고 했다.
- 하지만 Dangle님께 상담을 받으면서 별로 좋지 않은 방식이라는 것을 알 수 있었다. 실제로 발생한 문제를 해결하는 것이 아니라, 미리 문제 상황을 가정하고 출발하는 것도 좋지 않았고, 나중에 정말로 해결해야 할 심각한 문제가 발생했을 때, 해결할 시간이 부족해질 수도 있다는 것이 또 하나의 이유였다.

<br>

## Try

### **1. 일단 기능을 완벽하게 구현하는 것을 우선으로 하자**

- 프로젝트를 마무리할 때까지 발생할 수 있는 문제들에 대해 너무 안일하게 생각했던 경향이 있는 것 같다.
- 확실히 프론트엔드와의 연결 작업도 남아있고, 가장 중요한 실시간 위치/상태 공유도 남아있기 때문에 우여곡절없이 마무리할 수 있을 거라는 보장이 없다.
- 발표 주제에 너무 연연하지 말고, 일단 프로젝트를 완성도 있게 완성하는 것을 우선으로 하자.
- 개발이 일단락된 후에 보강할 부분을 찾아보면서 챌린지 요소를 찾아보자.

## CORS (Cross-Origin Resource Sharing)

- 다른 출처(origin) 간의 리소스 공유를 가능하게 해주는 웹 보안 정책
- 기본적으로 웹 브라우저는 보안상의 이유로 다른 origin의 리소스 요청을 제한
- CORS는 서버가 적절한 HTTP 헤더를 통해 이러한 요청을 허용해줄 수 있도록 해줌

### 용어 정리

- **Origin**: 프로토콜 + 도메인 + 포트 번호로 구성
    - 예: `https://example.com:443`
- **Same-Origin Policy (SOP)**: 기본적으로 브라우저는 동일 출처가 아닌 경우 요청을 제한함

### CORS 요청 유형

- **Simple Request**: 자동으로 CORS preflight를 거치지 않는 요청 (`GET`, `POST`(단순 폼 데이터), `HEAD` 등)
- **Preflight Request**: `OPTIONS` 요청을 먼저 보내 서버가 실제 요청을 허용하는지 확인

### 주요 헤더

- `Access-Control-Allow-Origin`: 허용할 Origin (예:  또는 특정 도메인)
- `Access-Control-Allow-Methods`: 허용할 HTTP 메서드 (예: `GET, POST, PUT`)
- `Access-Control-Allow-Headers`: 허용할 커스텀 헤더 목록
- `Access-Control-Allow-Credentials`: 쿠키 등 자격 증명 포함 여부 (`true` 설정 필요)

### Spring Boot에서 CORS 설정

```java
@Configuration
public class WebConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**") // 모든 경로에 대해
                .allowedOrigins("http://localhost:3000", "https://my-frontend.com") // 허용할 origin
                .allowedMethods("GET", "POST", "PUT", "DELETE")
                .allowedHeaders("*")
                .allowCredentials(true);
    }
}
```
