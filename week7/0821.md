## 작업 과정에서 배운 것

### 1. 보안 관리의 중요성

다른 파트에서 AWS 관련 사고가 있었다는 소식을 들었다.

AWS IAM 액세스 키가 포함된 파일이 GitHub에 올라가면서, 누군가가 이를 악용해 고비용 인스턴스를 다수 생성했다고 한다. 다행히 사건이 조기에 발견되어 생성된 인스턴스와 문제가 된 GitHub 파일을 신속하게 삭제할 수 있었지만, 그 과정에서 모든 팀의 AWS 권한이 일시적으로 정지되는 일이 발생했다.

사고 내용을 들으면서, 누구에게나 일어날 수 있는 일이라고 생각했다. 나는 평소에 보안 문제를 철저히 점검하면서 작업했는지 스스로 돌아보게 되었다. 단지 운이 좋아서 지금까지 사고가 없었던 것이지, 언제든 비슷한 실수를 저지를 수 있었겠다는 생각이 들었다. 작은 부주의가 어떤 결과를 불러일으킬 수 있는지 경각심을 가지고, 보안적으로 조심스럽게 다뤄야 하는 것들이 무엇이 있는지 항상 명심해야겠다.

<br>

## 어려웠던 점

### 1. 원격에서의 실행 문제

웹소켓 통신의 기본 구조를 구현하고 로컬에서 테스트했을 때는 정상적으로 작동했다. 원격에서도 제대로 작동하고 있는지 확인해보고 싶어서 배포해서 실행해보려고 했다.

그런데 제대로 작동하지 않는 문제가 있었다. 

코드가 문제인 것인지, 저번처럼 원격 서버의 nginx 설정이 문제인 것인지 파악하기 위해서 여러 가지 가능성을 점검했다.  예상되는 부분을 하나씩 확인하면서 많은 시간을 쏟았지만, 문제는 여전히 해결되지 않았다. 아무리 생각해봐도 문제의 원인을 알 수가 없었다.

한참을 씨름한 끝에 발견한 원인은, 허무하게도 IAM 권한 문제로 배포 자체가 안되고 있었다는 것이다. 배포 과정에서 액세스 키를 사용하는 부분이 있었는데, 그 단계에서 오류가 나면서 새로운 코드가 아예 서버에 반영되지 않았던 것이다.

그동안 자동 배포에서 문제가 있었던 적이 한 번도 없어서 당연히 성공했을 것이라고 생각했던 것이 화근이었다. 너무나도 기초적인 부분을 확인하지 않아서 시간을 그렇게 허비했다고 생각하니 황당하고 허무했다. 등잔 밑이 어둡다는 말처럼 문제의 원인을 찾을 때는 방심하기 쉬운 정말 단순한 부분부터 출발해야 한다는 것을 뼈저리게 느낄 수 있었다.

# 2. 회고

## Keep

### **1. 너무 늦지 않은 시기에 결단을 내린 것**

- 기존 SSE 기반 구현을 과감히 포기하고, 웹소켓으로 실시간 통신을 다시 개발하기로 결정했다.
- 이미 동작하던 SSE 기능과 그동안 쏟아온 시간이 아쉽기는 했지만, 프로젝트의 특성을 고려하면 합리적인 선택이었다.
- 오히려 이 문제를 가지고 조금이라도 더 고민을 했더라면, 그때는 정말로 웹소켓 기능을 개발하기 위한 시간이 부족했을지도 모른다. 지금 시점에서 빠르게 방향을 바꾸고 도전하기로 한 것이 잘한 선택이었다고 생각한다.
- 이 선택에 후회가 없도록 남은 기간 최선을 다해 구현을 마무리해보자.

<br>

## Problem

### **1. 내일 있을 데모로 인해 원격 서버에 웹소켓 기능을 적용하기 어렵다**

- 내일 데모 활동을 한다고 한다.
- 이미 SSE 통신으로 프론트엔드와 연결해둔 상태이기 때문에, 지금 시점에서 급하게 웹소켓을 연결해보기는 어렵다.
- 로컬에서 개발하면서 기능이 잘 작동하는지 확인해보고는 있지만 한계가 있다. 원격 서버 환경에서 제대로 작동하는지 확인해봐야 제대로 구현했다고 확신할 수 있을 것 같다.
- 프론트엔드와의 연결까지는 당장 힘들더라도, 최소한 원격 서버에서 웹소켓 API를 테스트해보고 싶었지만 기존 코드와 충돌이 생길 수 있어 쉽지 않은 상황이다.

<br>

## Try

### **1. SSE와 웹소켓 모두 대응 가능한 구조로 확장하기**

- SSE와 웹소켓 두 가지 기능 모두 정상적으로 작동하도록 구현해두자.
- 프론트엔드 입장에서도 SSE를 사용하든, 웹소켓을 사용하든 같은 형태로 데이터를 주고 받을 수 있어야 전환 작업이 수월하다.
- 서버 내부적으로도 SSE 통신일 때도, 웹소켓 통신일 때도, 정상적으로 작동하도록 확장성 있는 구조로 만들어두자. 기능을 확장하더라도 기존 기능이 망가지지 않도록 데이터를 다루는 방식을 통일시켜두자.

# 3. 학습내용

## Nginx 서버 블록 (Server Block)

- Nginx에서 특정 도메인 또는 요청을 처리하기 위한 설정 단위
- 하나의 Nginx 인스턴스에서 여러 웹사이트(가상 호스트)를 동시에 운영할 수 있도록 지원

### 주요 특징

1. **도메인/포트별 분리**
    - `server_name`, `listen` 지시어를 통해 어떤 요청을 처리할지 구분
    - 예: `server_name example.com;`, `listen 80;`
2. **요청 처리 규칙 설정**
    - `location` 블록을 통해 경로별 라우팅 규칙을 지정 가능
    - 예: `/api` 요청은 백엔드로 프록시, `/static`은 정적 파일 제공
3. **리버스 프록시**
    - 서버 블록에서 `proxy_pass` 지시어를 활용해 백엔드 애플리케이션 서버로 요청을 전달 가능
    - 흔히 Spring Boot, Node.js 같은 애플리케이션 서버 앞단에 배치되어 사용됨
4. **보안/성능 관리**
    - SSL 인증서 적용(`listen 443 ssl;`), HTTP → HTTPS 리다이렉션 설정 가능
    - 캐싱, 압축(gzip), 버퍼링(proxy_buffering) 같은 성능 관련 설정도 서버 블록 단위에서 지정 가능

### 기본 구조 예시

```
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /static/ {
        root /var/www/html;
    }
}
```

### 용도

- **도메인별 웹사이트 운영**: `example.com`, `test.com`을 각각 다른 서버 블록으로 설정
- **환경 분리**: 개발용/운영용 서버를 동일한 Nginx에서 다른 블록으로 구분
- **리버스 프록시 게이트웨이**: API 서버, 웹소켓 서버 등 여러 서비스를 Nginx 한 곳에서 통합 라우팅
