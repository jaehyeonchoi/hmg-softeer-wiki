## 작업 과정에서 배운 것

### 1. 다른 팀원들과 발표 주제 이야기하기

이번 주에도 스쿼드 세션 시간을 가졌다. 다들 개발 막바지라서 정신없이 바빴지만, 마지막 스쿼드 세션인만큼 알차게 이야기를 주고 받았다.

개발 진행 상황에 대한 공유도 했지만, 역시 다들 발표를 앞두고 있다보니 주제 선정에 대한 관심이 가장 높았다. 서로 자신이 생각하고 있는 주제에 대해서 공유했다. 다들 이미 주제를 확정했을 줄 알았는데, 의외로 아직 결정하지 못한 분들도 있었고, 정했더라도 방향을 잡지 못해 고민하는 경우도 많았다. 나 또한 확신이 없는 부분이 있어서, 지금까지 구상해온 내용과 앞으로 도전해보고 싶은 부분들을 털어놓았다.

내 입장에서는 이미 충분히 고민해 더 확장할 부분이 없다고 생각했는데, 다른 사람들이 듣기에는 의문이 들거나 더 발전시킬 여지가 있어 보였던 모양이다. 피드백을 받으면서 생각해볼 거리가 많았다. 예전에도 발표 주제에 대해 다른 팀과 이야기하면서 많은 아이디어를 얻었는데, 이번에도 마찬가지였다. 특히 이번에는 이미 구현 단계에 들어간 내용을 바탕으로 피드백을 받다 보니, 아이디어가 훨씬 구체적이고 퀄리티가 높았다.

아이디어를 떠올리는 단계에서 뿐만이 아니라 실제로 구현을 하고 있는 단계에서 영감을 얻을 수 있는 부분이 분명히 있었고 오히려 더 유익하다는 생각도 들었다. 나 혼자 헤쳐나가야 하는 일이라는 생각보다는 많은 사람들과 의견을 주고 받으면서 더 좋은 방향을 찾아보는 것이 훨씬 더 의미 있다는 것을 느낄 수 있었다.

## 어려웠던 점

### 1. 시연 중에 디비 문제로 서버 터짐

데모 활동을 하면서 지금까지 개발해온 서비스를 직접 시연했다. 전날부터 QA를 반복하며 문제를 찾아 고쳤기 때문에 자신이 있었다. 실제 시연 초반에는 문제 없이 잘 돌아갔다. 하지만 진행 도중 서버가 갑자기 다운되는 사건이 발생했다.

데모 활동을 한창 진행하던 중에 발생한 문제라서 당황스러웠다. 해결하느라 남은 시간은 거의 제대로 데모 활동을 진행할 수 없었다. 원인은 DB 커넥션이 제대로 정리되지 않고 있던 것이었다. 그동안 프로젝트를 진행하면서 DB 커넥션이 쌓이고 쌓이다가 커넥션 풀이 가득 차면서 서버가 터진 것이다. 데모 중에 무언가를 잘못 조작하면서 발생한 것이라고 생각했는데, 그런 것이 아니라 사실은 언제 터졌어도 이상하지 않았을 문제가 하필이면 딱 데모 활동을 하던 시기에 일어났던 것이었다. 

어떻게 보면 지금 문제가 발생한 것이 다행이라는 생각이 들었다. 끝까지 문제가 생기지 않고 있다가 실제 발표를 해야 할 때 문제가 발생하면 돌이킬 수 없었을 것이기 때문이다. 문제가 발생하지 않는 것이 꼭 좋은 것이 아니라는 걸 느낄 수 있었다. 발표 전까지 서비스를 테스트해보면서 최대한 많은 문제를 찾아내야겠다고 생각했다.

# 2. 회고

## Keep

### **1. 즐길 수 있는 걸 하고, 하고 있는 걸 즐기자**

- 그동안 발표 주제를 두고 "어떤 게 더 의미 있을까, 어떤 게 더 인상 깊을까"라는 고민만 깊어졌다. 그 과정에서 정작 내 관심사와 공부하고 싶은 방향은 뒷전으로 밀려났던 것 같다.
- 발표도 프로젝트도 결국엔 그 결과가 아니라, 과정에서 내가 얼마나 성장했는지가 중요한 것이라는 생각이 들었다. 남이 어떻게 볼지 신경쓰지 말고, 내가 관심이 있고, 내가 진심으로 개선해보고 싶은 문제에 뛰어들어보는 것이 성장할 수 있는 밑거름이 될 것이라고 생각했다.
- 위치 정보 메세지 통신 횟수를 줄이기 위해 유효성을 검증하고 유의미한 데이터 갱신에만 브로드캐스팅해주는 기능을 구현하고 있는데, 정말로 해보고 싶었던 부분이었고, 덕분에 어렵지만 즐겁게 수행할 수 있었다.
- 내가 해결해보고 싶다고 생각한 문제에 임할 때의 마음가짐이 다른 때와는 다르다는 것을 실감했다. 해보고 싶은 것을 주체적으로 찾아나서며 많이 배우고 싶다.

# 3. 학습내용

## Jackson

- 자바 객체와 JSON 간의 변환을 지원하는 대표적인 라이브러리
- Spring Boot에서 기본적으로 사용됨

**주요 개념**

- **직렬화(Serialization)** : 자바 객체 → JSON 문자열 변환
- **역직렬화(Deserialization)** : JSON 문자열 → 자바 객체 변환

**주요 클래스/도구**

- `ObjectMapper` : 가장 핵심적인 클래스
    - `readValue()`, `writeValueAsString()` 등을 통해 객체와 JSON 간 변환 수행
- `JsonNode` : 계층적 JSON 데이터를 트리 구조로 다룰 수 있는 자료형.

**주요 애노테이션**

- `@JsonProperty` : JSON 필드명과 자바 필드명을 매핑
- `@JsonIgnore` : 특정 필드를 JSON 변환 시 제외
- `@JsonFormat` : 날짜/시간 포맷 지정
- `@JsonInclude` : null 값 혹은 특정 조건에 따라 직렬화 여부 제어

**활용 예시**

- DTO 응답을 다룰 때 Jackson 설정을 적절히 활용하면, API 응답 형식을 일관성 있게 유지 가능
- 대규모 서비스에서는 `ObjectMapper`를 직접 커스터마이징해(예: `SerializationFeature`, `DeserializationFeature` 설정) 전역적으로 포맷/규칙을 통일

## 컨텍스트 경로 (Context Path)

- 웹 애플리케이션이 서버 내에서 접근 가능한 기본 경로(prefix)
- 하나의 서버에 여러 애플리케이션을 배포할 때, 각 애플리케이션을 구분하기 위해 사용

**Spring Boot에서의 동작**

- 기본값 : `/` (루트 경로)
- 변경 방법 : `application.properties` 또는 `application.yml`에서 설정
    
    ```yaml
    server:
      servlet:
        context-path: /api
    
    ```
    
- 위 설정을 적용하면, 기존 `/users` 엔드포인트가 `/api/users`로 변경됨

**활용 예시**

- `/api` : REST API 전용 서버일 경우
- `/serviceA`, `/serviceB` : 동일 서버에 여러 서비스를 띄울 경우
- `/admin` : 관리자 페이지와 일반 사용자 페이지를 구분할 경우

**주의사항**

- 컨텍스트 경로가 바뀌면 모든 엔드포인트 URL이 바뀌므로, 클라이언트 쪽(API 호출부)도 함께 수정해야 함
- 운영 환경에서는 보안(접근 제한)이나 서비스 구분을 위해 반드시 지정하는 경우가 많음
