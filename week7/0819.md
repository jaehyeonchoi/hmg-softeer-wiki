## 작업 과정에서 배운 것

### 1. 원격 서버에서 SSE 실행하기

SSE 기능 구현을 마무리하고 프론트엔드와의 연동 작업을 시작했다.

그런데 로컬에서는 정상적으로 작동했던 SSE 기능이 원격 환경에서 문제가 있었다. 연결이 되지 않거나, 되더라도 즉시 닫혀버리는 현상이 있었다. 코드에 문제가 있나 싶어서 로컬 환경에서 다시 확인해보니 정상적으로 작동했다. 로컬과 원격의 차이가 문제인 것으로 추측하고 정확한 원인을 찾아보았다.

로컬과는 달리 원격에서는 브라우저가 개입하기 때문에 그것이 원인이지 않을까 생각했다. 처음으로 생각해본 것은 초기 스냅샷 전송이었다. 현재 동행의 상태값이나 롤에 따라서는 SSE가 연결되자마자 전송되는 데이터가 없을 수도 있다. 브라우저에 따라서는 SSE 연결 직후 들어오는 이벤트가 없으면 자동으로 연결을 정리해버리는 경우가 있다고 했다. 그래서 연결하자마자 무조건 연결 성공에 대한 이벤트를 전송해주기로 했다. 하지만 그럼에도 문제 상황에는 전혀 변화가 없었다.

조사를 더 해보면서 프록시로 사용 중인 Nginx의 기본 설정이 문제일 수 있겠다는 생각이 들었다. SSE는 적은 양의 데이터를 짧은 주기로 전송하는데, Nginx에서는 응답들을 버퍼링/압축하다가 한 번에 보내는 것이 기본 설정이기 때문에 SSE를 일반 HTTP처럼 다뤄서 연결에 실패하거나, 성공해도 금방 끊겨버리는 현상이 있었던 것이다. Nginx의 설정을 바꿔주었다. SSE 관련 URL에 전용 설정으로 버퍼링/압축/캐싱 등을 수행하지 않도록 수정해두었다. 그 결과 SSE가 정상적으로 수행되었다.

그동안 Nginx 관련한 문제가 한 번도 없었고, 수정된 적도 없기 때문에 Nginx가 문제의 원인일 것이라고는 생각도 못했다. Nginx와 SSE 특성에 대한 숙련도가 부족했기 때문에 발생한 이슈였다. 일반 HTTP 통신을 편하게 만들어주는 설정이 SSE에는 치명적으로 작용할 수 있다는 것을 간과하고 있었다.

## 어려웠던 점

### 1. 외부 요소가 늘어날수록 어려워지는 테스트

개발을 하다 보니 서비스에 붙는 외부 요소가 점점 많아지고 있다.

처음에는 그래봐야 DB 정도였지만, 개발이 진행될수록 S3, Redis 등 구성 요소들이 하나둘 추가되었다. 그만큼 테스트도 점점 어려워졌다. 초기에는 로컬 환경에서 단순히 코드만 검증해도 정상 작동을 어느 정도 보장할 수 있었는데, 외부 요소가 붙으면서는 정상적으로 연동되고 있는지, 예상치 못한 문제는 발생하지 않는지 확인해야 할 부분이 훨씬 많아졌고, 테스트의 난이도도 높아졌다.

특히 원격 환경에서는 이러한 복잡성이 더 크게 다가온다. 로직 흐름 중 어디에서 문제가 발생했는지 바로 확인하기 어렵고, 로그 출력도 제한적이기 때문이다. 로컬에서는 당연하게 되던 작업이 원격에서는 여러 요소가 얽혀 실패하거나 예기치 않은 동작을 만들어내곤 한다. 이번 경험을 통해, 외부 요소가 늘어날수록, 단순 기능 검증을 넘어서 환경 전반을 고려한 접근이 필요하다는 것을 느꼈다.

앞으로는 코드 위주의 테스트에만 의존하지 않고, 실제 배포 환경과 최대한 유사한 환경에서 테스트를 수행해보려는 노력이 필요할 것 같다. 얼핏 접한 내용이지만, Testcontainers와 같이 DB, Redis, S3 같은 외부 요소들을 도커 컨테이너로 띄워서 테스트 환경을 구축할 수 있는 방법이 있다고 한다. 여유가 된다면, 실제 환경과 가까운 조건에서 테스트하는 것에도 도전해보고 싶다.

# 2. 회고

## Keep

### **1. 팀원들이 이해할 수 있게 문서로 정리하기**

- 성훈님께서 혼자 개발하신 부분에 대해서 다른 팀원들이 이해하기 쉽도록 문서를 남겨주셨다. 읽고나서 내가 한 부분이 아니지만 어떤 식으로 구현되었고, 어떻게 동작하고 있는지 쉽게 이해할 수 있었다.
- 사실 역할 분담을 하다보면, 우리 프로젝트임에도 불구하고 잘 모르는 영역이 생길 수 밖에 없다. 코드 리뷰 등의 활동을 통해 작업 내용을 공유하고는 있지만 코드 외의 부분에 대해서는 한계가 있다.
- 이런 식으로 문서를 남겨놓으면 다른 팀원들에게 정보 공유도 되고, 스스로도 작성하면서 더 깊게 이해를 할 수 있게 된다. 좋은 협업 방식이라고 생각해서 문서 작업을 병행하고 있다.
- 앞으로도 담당한 개발 부분에 대한 기록과 설명을 틈틈히 남겨두면서 팀원과 스스로에게 도움이 되는 자료로 만들고 싶다.

<br>

## Problem

### **1. 할 일이 약간 붕 떠버린 느낌이 든다**

- API와 실시간 대시보드 기능까지 개발이 완료되면서 당장 급하게 처리해야 할 일들이 모두 끝나버렸다. 프론트엔드 팀원들의 요청 사항에 대한 대응, 문서화, 챌린지 요소 탐색 정도의 작업을 수행하고 있다.
- 그 전까지는 당장 처리해야 할 일들이 쌓여있는 느낌이라 시간에 쫓기는 느낌이 있었는데, 긴장감이 약간 풀린 것 같다. 하지만 오히려 지금이 가장 중요한 시기이다. 시간을 효율적으로 사용하기 위한 고민이 다시 한 번 필요할 것 같다.

<br>

## Try

### **1. 목표를 명확하게 정하고 할 일을 능동적으로 찾자**

- 프론트엔드 연동 작업에서 발생하는 요청 사항 말고도 프로젝트 구현에 문제가 있는 부분이 분명히 있을 것이다. 요청 사항을 기다리기만 하지 말고, 스스로 개선할 부분을 찾고 미리 수정해보자.
- 문서화, 챌린지 요소 탐색 등은 시간 제한을 정해두지 않으면 한없이 늘어지기 쉬운 작업이다. 언제까지는 반드시 끝낸다는 계획을 세워두고 스스로에게 압박감을 줄 필요도 있다.

# 3. 학습내용

## 리버스 프록시 (Reverse Proxy)

- 클라이언트가 서버에 직접 요청을 보내는 대신, 중간에서 요청을 받아 적절한 서버로 전달하고 응답을 클라이언트에게 반환하는 서버
- 클라이언트 입장에서는 실제 서버의 존재를 알 수 없고, 리버스 프록시만 보임

### 주요 특징

1. **중계 역할**
    - 클라이언트 요청을 받아 내부 서버(원 서버, Origin Server)에 전달
    - 서버 응답을 받아 다시 클라이언트로 전달
2. **클라이언트는 실제 서버를 모름**
    - 요청을 어디로 전달했는지 감춰져 있기 때문에 보안·구조적 이점이 있음
3. **대표적인 구현체**
    - Nginx, Apache HTTP Server(mod_proxy), HAProxy 등이 있음

### 주요 활용 목적

1. **로드 밸런싱 (Load Balancing)**
    - 여러 대의 서버로 트래픽을 분산시켜 성능과 가용성을 향상
2. **보안 강화**
    - 실제 서버의 IP나 구조를 감추어 직접적인 공격을 방지
    - SSL 종료(SSL Termination)를 수행해 HTTPS 처리 부담을 줄임
3. **캐싱 (Caching)**
    - 정적 자원을 리버스 프록시가 캐싱하여 서버 부하 감소, 응답 속도 향상
4. **압축 및 최적화**
    - 데이터 압축, 응답 최적화를 통해 네트워크 효율성을 높임
5. **인증 및 접근 제어**
    - 프록시 단계에서 인증을 수행하거나 특정 요청을 차단 가능
6. **프로토콜 변환**
    - HTTP → HTTPS, WebSocket → HTTP/2 등 서로 다른 프로토콜 간 변환을 지원

### 포워드 프록시(Forward Proxy)와 비교

| 구분 | **포워드 프록시** | **리버스 프록시** |
| --- | --- | --- |
| 대상 | 클라이언트 앞에 위치 | 서버 앞에 위치 |
| 목적 | 클라이언트의 요청을 외부 서버로 전달 (클라이언트 IP 감춤) | 외부 요청을 내부 서버로 전달 (서버 IP 감춤) |
| 사용 예 | 회사 내부망에서 인터넷 접속 제한, 우회 | 로드 밸런싱, 보안, 캐싱 |
| 클라이언트 인식 | 클라이언트가 프록시 사용을 인지 | 클라이언트는 리버스 프록시 존재를 모름 |
