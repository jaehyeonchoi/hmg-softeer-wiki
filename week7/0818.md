## 작업 과정에서 배운 것

### 1. 백엔드 개발이 마무리되었다고 끝이 아니다

백엔드 API 개발이 일차적으로 완료되었기 때문에 어느 정도 한숨을 돌리고 있었다. 단위 테스트와 통합 테스트도 어느 정도 진행했기 때문에 프론트엔드와의 연동도 수월하게 될 것이라고 생각했다.

하지만 실제로 연결을 진행하면서 예상보다 많은 수정 사항이 나왔다. 필요했던 필드를 빠뜨린 경우도 있었고, 프론트엔드 로직 상 의도했던 파라미터 구조로는 비효율적이거나 요청을 보내기 어려운 경우도 있었다.

비즈니스 로직과 테스트 코드가 어느 정도 완성된 상태였기 때문에, 작은 수정이라도 코드 전반에 미치는 영향이 이전보다 크게 느껴졌다. 단순 개발만큼이나 연결 작업의 난이도가 높다는 것을 다시 한 번 깨달을 수 있었다.

그럼에도 불구하고 연동 과정에서 그동안 놓쳤던 부분을 발견하고 개선할 수 있었다는 점은 큰 수확이었다. 특히 외부 인스턴스와 연관성이 깊어 테스트 코드만으로는 검증하기 어려웠던 부분을, 프론트엔드와의 실제 연결을 통해 보완할 수 있었다. 대시보드처럼 실시간성이 중요한 기능은 여러 기기에서 동시 테스트하는 것이 필요하기 때문에, 빠르게 연동 작업을 마무리하고 충분히 검증해보고 싶다.

## 어려웠던 점

### 1. SSE 다중 연결

SSE 기본 구조를 처음 설계할 때는 도우미가 서버에 실시간 위치를 공유하면, 서버가 고객에게 전달해주는 최대한 단순한 구조를 가정했다. 동행 하나 당 SSE 연결이 하나만 필요했기 때문에 `Map` 구조로 동행 ID를 key, `SseEmitter`에 대한 참조를 value로 하여 저장했다. Emitter에 대한 참조는 원자적으로 관리하는 것이 중요했기 때문에 `AtomicReference`를 사용하여 읽기/쓰기/교체 작업을 원자적으로 처리할 수 있도록 했다.

하지만 개발 진행 상황에 여유가 생기면서, 기획 단계 때 의도했던대로 동행 하나에 대해 고객/도우미/환자 총 3명의 사용자가 실시간 정보를 공유할 수 있도록 구현하기로 했다. 동행 하나당 최대 3개의 `SseEmitter`를 관리해야 하므로 기존 맵을 이중구조로 확장했다. 사용자의 `Role`을 Enum으로 정의하여 관리했고, 외부 맵에서는 동행 ID를, 내부 맵에서는 `Role` Enum 값을 key로 사용하여 Emitter를 저장했다.

서비스 로직에서는 `Role`에 따른 분기를 통해, 각 Role마다 공유할 수 있는 데이터와 공유받을 수 있는 데이터를 제한해주었다. 또한 Emitter의 생명주기 및 동행의 진행상태에 따라서 SSE 연결을 해제하고 참조를 정리하도록 했다.

# 2. 회고

## Keep

### **1. 구현한 코드를 정리하고 설명하기**

- 주말부터 SSE 관련 기능을 구현해왔다.
- 일요일 밤에는 성훈님과 코드 리뷰 시간을 가지며 SSE 구현 내용을 설명드렸다. 특히 `AtomicReference` 부분은 구현 과정에서도 어려웠던 부분이라, 설명 전에 코드를 다시 훑어보며 준비했지만 막상 말로 풀어내려니 쉽지 않았다. 머릿속에는 개념이 있었지만, 듣는 사람이 이해하기 쉬운 언어로 바꾸는 노력이 부족했던 것 같다.
- 쉽게 설명하지 못한다는 건 결국 나 스스로도 완전히 소화하지 못했다는 의미일 수 있다. 리뷰 후에 다시 코드를 복습하며 주석과 네이밍을 다듬어 이해하기 쉽게 정리했다.
- 오늘은 SSE 기능을 확장한 뒤 변경 사항을 다시 성훈님께 설명드렸는데, 어제보다 훨씬 깔끔하고 명확하게 전달할 수 있었다. 설명하는 능력이 아직 부족하다는 것을 느끼지만, 점점 나아지고 있다는 점에서 만족스러웠고 앞으로도 더 연습하고 싶다.

<br>

## Problem

### **1. 이슈에 대한 문서화가 부족한 것 같다**

- 발표 자료는 마지막 주에 준비하면 된다고 생각했는데, 예상보다 이른 시점에 제출해야 한다는 소식을 들었다.
- 주말에 시간을 내어 발표 자료를 작성한다 해도, 그 전에 참고할 수 있는 문서가 미리 정리되어 있지 않으면 어려움이 있을 것 같다.
- 회고에는 매일의 작업 내용, 공부한 내용, 어려웠던 점 등을 기록하고 있지만, 이를 프로젝트 문서로 정리해두는 작업은 부족했다는 점을 깨달았다.

<br>

## Try

### **1. 문서화 작업도 병행하자**

- 실시간 대시보드 구현이 어느 정도 마무리되었기 때문에, 개발 일정에 쫓기는 상황은 아니다.
- 이제는 생긴 시간적 여유를 활용해 중간중간 문서화 작업에 힘써야겠다.
- 문서화와 함께 발표 자료 구성을 미리 고민해둔다면, 막판에 급히 준비하지 않고도 훨씬 완성도 높은 발표를 할 수 있을 것이다.

# 3. 학습내용

## Redis Insight

- Redis에서 제공하는 공식 무료 GUI 툴
- Redis 서버를 쉽게 탐색, 모니터링, 관리할 수 있도록 도와줌
- 단순한 CLI(`redis-cli`) 사용보다 직관적인 시각화 제공

### 주요 기능

**(1) 데이터 탐색 및 관리**

- Redis에 저장된 Key-Value 데이터를 브라우저처럼 탐색 가능
- Key 검색, 필터링, TTL 확인
- Key Value를 직접 조회, 편집, 삭제 가능
- 다양한 데이터 구조 지원 → String, List, Set, Hash, Sorted Set, JSON 등

**(2) 성능 모니터링**

- Redis 서버의 실시간 메트릭 시각화 제공
    - CPU 사용량, 메모리 사용량
    - 네트워크 트래픽, 연결된 클라이언트 수
    - 명령어 호출 빈도 (Command Stats)
- 특정 시간대별 성능 추이 그래프 확인 가능

**(3) 쿼리 분석**

- Redis에 실행된 명령어 통계 확인 가능
- 어떤 명령어가 가장 많이 실행되는지, 어느 정도의 리소스를 차지하는지 파악 가능
    - 성능 병목 지점 분석에 유용

**(4) Redis 모듈 지원**

- RedisJSON, RedisTimeSeries, RediSearch 등 추가 모듈 데이터도 시각화 가능
- 예: RedisJSON으로 저장된 JSON 문서를 트리 형태로 조회

**(5) 보조 기능**

- Key TTL 설정/변경
- Pub/Sub 메시지 구독 확인
- 백업/복구 관리

### 장점

- 직관적 UI로 사용하기 쉬움
- 실시간 성능 모니터링 가능
- 다양한 데이터 구조를 시각적으로 확인 가능

### 단점 / 유의사항

- GUI 기반이므로 대규모 운영 환경에서는 CLI나 자동화된 모니터링 도구(Prometheus, Grafana 등)보다 느릴 수 있음
- 운영 환경에서 직접 수정/삭제 같은 작업을 할 경우 데이터 손상 위험이 있을 수 있으므로 주의 필요
