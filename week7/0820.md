# 1. 리뷰

## 오늘 한 작업

### 종합프로젝트

- 프론트엔드 연결 작업 중 요청 사항 대응
- S3 관련 문서화
- 대시보드 웹소켓 통신

<br>

## 작업 과정에서 배운 것

### 1. 확장성 있는 기술을 선택하기

서버에서 클라이언트에게 실시간 위치 정보를 전송해주어야 했다. 여러 가지 방식들이 있었고 무엇으로 구현할지 고민이었다. 마지막에 남았던 두 가지 선택지가 SSE와 웹소켓이었다.

결정하던 당시 상황에서는 도우미가 서버에게 위치 정보를 갱신하면 서버가 고객에게 전달해주는 단방향 방식이었다. 기획 단계에서는 양방향 통신까지도 고려했었으나 개발 기간이 부족할 것 같아 범위를 축소했었다. 단순한 통신 구조를 위해 웹소켓까지 사용하는 것은 오버 엔지니어링이라는 생각이 들어 SSE로 구현하였다. 프론트엔드와 연결 작업까지 무사히 마무리되었다.

하지만 생각보다 API 개발 및 연결 작업이 수월하게 진행되면서 시간적인 압박이 사라졌고, 프론트엔드 쪽에서는 재사용할 수 있는 컴포넌트들도 많을 것으로 예상되면서, 처음 기획대로 기능이 다시 확장되었다. 이제는 도우미와 환자가 서로의 위치 정보를 공유받을 수 있고, 고객은 도우미와 환자 모두의 정보를 전달받아야 했다. 사실상 양방향에 가까운 통신 구조가 되면서, SSE를 선택했었던 이유가 다소 희석되었다.

그러던 중, 실시간 위치 공유를 시연해보는 과정에서 공유 주기 5초가 너무 길다는 의견이 나오면서 1초로 단축하게 됐다. 사용자가 자신의 위치 정보를 갱신할 때는 HTTP 요청을 사용하고 있었는데 1초마다 계속 HTTP 요청을 보내야 하는 상황이 된 것이다. 이미 웹소켓을 사용하는 것이 더 적절하게 느껴지는 상황에서 굳이 SSE로 개발해야만 했던 논리를 찾기 어려웠다. 근거를 제시할 수 없는 기술 선택은 좋지 않다고 생각했다. 팀원들과 고민하며 상의한 끝에 실시간 정보 공유 기능을 웹소켓으로 전환하기로 결정했다.

결과론적인 이야기이긴 하지만, 지난주에 SSE와 웹소켓 사이에서 고민하던 당시 다른 선택을 했더라면 어땠을까 하는 생각이 들었다. SSE를 적용하기 위해 시간을 많이 투자하기도 했고, 앞으로 챌린지 요소를 도전해보려면 시간이 부족한 것이 사실이다. 기능이 확장될 가능성을 간과하고 확장성이 떨어지는 방식을 선택했던 것에 아쉬움이 남았다.

<br>

## 어려웠던 점

### 1. 발표 주제 선정하기

이번에 가장 고민이 많았던 부분은 발표 주제였다.

개발 전에는 처음 다뤄보는 영역이라 당연히 어렵고 도전적인 부분이 많을 것이라 생각했다. 하지만 막상 개발을 해놓고 보니, 단순히 “처음 해봐서 어려웠다” 라는 것만으로는 기술적인 챌린지라고 말하기 부족하지 않을까 하는 의문이 들었다. 이미 널리 알려진 기술을 적용했을 뿐, 내가 스스로 깊게 고민한 부분은 많지 않았다는 생각이 들었다.

발표 주제로 삼고 싶은 아이디어들은 몇 가지 있지만, 그것이 충분히 의미가 있을지 걱정된다. 나에게는 새로운 시도이자 개선점이라 생각되지만, 그 분야에 익숙한 사람들에겐 너무 당연하게 여겨지는 내용일 수도 있기 때문이다.

주변 이야기를 들어보니 나만의 고민은 아니었다. 발표 주제를 고를 때 누구나 겪는 흔한 고민 같았다. 결론적으로 다른 사람들을 의식하기보다는 내가 가장 흥미롭게 파고들었던 주제를 발표하는 것이 가장 좋지 않을까 생각했다. 이미 많은 사람들이 도전해본 영역에서 정말 새로운 주제를 찾기는 쉽지 않다. 내가 진심으로 관심을 가지고 몰입했던 내용을 공유하는 것이 더 설득력 있고 자연스러울 것이라는 생각이 들었다.

# 2. 회고

## Keep

### **1. 프로젝트에 대해 많이 이야기하고 다니기**

- 밤에 남아서 작업을 하기 전에 다른 팀 사람들과 함께 저녁을 먹었다.
- 식사를 하면서 프로젝트에 대해 이야기했다. 발표 주제에 고민이 있어 내가 담당하고 있는 부분에 대해 이야기했다.
- 프로젝트 경험이 풍부한 분들도 있고 개념을 잘 아는 분들도 있어서, 개선하거나 도전해볼 만한 영역에 대해 다양한 피드백을 들을 수 있었다. 그 중 몇 가지는 정말 흥미롭게 다가왔다.
- 우리 팀 내에서는 프로젝트에 대해 자주 이야기하지만, 이미 너무 오랜 시간 집중했던 작업이다보니 새로운 시각이 나오기는 어렵다.
- 외부 시각에서 바라본 피드백이 매우 유익했다. 앞으로도 프로젝트에 대해 더 많이 소통하며 새로운 아이디어를 얻어보는 활동을 해야겠다.

<br>

## Problem

### **1. 웹소켓으로 전환하기에 시간이 빠듯하다**

- 기존에 SSE로 구현했던 실시간 동행 상태 공유 기능을 웹소켓 기반으로 전환하기로 결정했다.
- 그러나 코드 프리즈까지 일주일도 남지 않은 상황에서 새로운 기술을 적용해야 한다. 게다가 발표 주제로 삼을 수 있는 챌린지까지 도전해야 한다.
- 나 혼자만의 일이 아니라 프론트엔드 연동, 테스트 시간 확보까지 고려해야 하므로 부담이 크다.
- 최대한 빠르고 안정적으로 기능을 완성하기 위한 전략이 필요하다.

<br>

## Try

### **1. 남은 개발 기간을 효율적으로 활용하자**

- 남은 기간이 길지 않은 만큼, 시간을 효율적으로 사용하는 것이 더욱 중요해졌다.
- 급할 수록 돌아가라는 말처럼, 웹소켓 개발에 들어가기 전에 충분히 알아보는 시간을 가지자. 괜히 무턱대고 개발에 들어갔다가 시행착오를 겪게 되는 것이 시간을 더 많이 잡아먹는다. 기본 지식도 쌓아두고 추후의 확장성에 대한 고민도 하면서 방향성을 잡아두자.
- 기존에 SSE로 만들어 둔 통신 구조에서 활용할 수 있는 부분이 분명히 있을 것이다. 처음부터 다시 개발하려고 하지 말고, 지금 구조에서 좋은 부분은 최대한 유지하면서 작업량을 줄일 수 있는 방향을 찾아보자.

<br>

# 3. 학습내용

## WebSocket vs. SSE

### 1. WebSocket

- HTTP 핸드셰이크 이후 서버와 클라이언트 사이에 양방향 통신이 가능한 지속 연결(persistent connection)을 맺는 프로토콜
- **특징**
    - **양방향(full-duplex)**: 서버 ↔ 클라이언트 모두 자유롭게 메시지를 보낼 수 있음
    - **프로토콜**: ws:// 또는 wss:// (보안)
    - **데이터 형식**: 텍스트, 바이너리 모두 전송 가능
    - **성능**: 한 번 연결하면 헤더 오버헤드 없이 지속적으로 데이터 교환 → 고빈도 메시지에 적합

<br>

### 2. SSE (Server-Sent Events)

- HTTP 기반의 단방향 이벤트 스트리밍
    - 서버가 클라이언트에게만 데이터를 전송
- **특징**
    - **단방향(server → client only)**: 클라이언트에서 서버로는 일반 HTTP 요청 필요
    - **프로토콜**: http:// 또는 https:// (일반 HTTP/1.1)
    - **데이터 형식**: 텍스트(EventStream 형식) 전용
    - **자동 재연결 지원**: 연결 끊기면 브라우저가 자동 재시도(기본 제공)
    - **브라우저 친화적**: EventSource API로 쉽게 구현 가능

<br>

### 장단점 비교

| 구분 | WebSocket | SSE |
| --- | --- | --- |
| **통신 방식** | 양방향 | 단방향 (Server → Client) |
| **데이터 형식** | 텍스트 + 바이너리 | 텍스트(EventStream)만 |
| **프로토콜** | ws://, wss:// (HTTP 업그레이드 후 별도 프로토콜) | 기존 HTTP/1.1 사용 |
| **연결 관리** | 수동 구현 필요 (재연결, heart-beat 등) | 브라우저 기본 제공 (자동 재연결) |
| **성능/효율** | 고빈도·저지연 통신에 적합 (게임, 채팅 등) | 저빈도·단순 push에 적합 (알림, 주식 가격 등) |
| **서버 부하** | 연결당 리소스 사용 많음 (특히 scale-out 시) | HTTP 기반이라 상대적으로 가벼움 |
| **보안/방화벽** | 일부 환경에서 차단될 수 있음 (특히 ws://) | 일반 HTTP라 방화벽 친화적 |
| **브라우저 지원** | 거의 모든 브라우저 지원 | 대부분 지원하지만 IE 구버전은 미흡 |
| **구현 난이도** | 복잡 (핸드셰이크, 프레임 관리, 에러 처리 등 필요) | 간단 (EventSource 객체로 바로 사용 가능) |
