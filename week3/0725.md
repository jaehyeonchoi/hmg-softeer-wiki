## 작업 과정에서 배운 것

### 1. 함수형 인터페이스 사용

이번 미션에서는 함수형 인터페이스를 처음으로 본격적으로 사용해보았다. 함수형 인터페이스를 사용하면 메서드를 값처럼 다룰 수 있어서, 실행할 로직을 람다식으로 외부에서 주입할 수 있다.

예를 들어, 사용자 정보를 수정하는 기능에서는 닉네임 변경, 비밀번호 변경, 프로필 이미지 변경 등 서로 다른 세부 동작이 존재한다. 전에는 이들을 서로 다른 메서드로 따로 구현했기 때문에, DB 및 트랜잭션에 관련된 코드가 중복되어 존재하는 문제가 있었다. 

하지만 함수형 인터페이스를 도입하면서, 공통된 처리 흐름을 하나의 템플릿으로 정의하고, 세부 동작만 함수형 인터페이스로 전달하는 방식으로 코드를 리팩토링했다.

덕분에 코드의 재사용성을 높이고, 핵심 처리 흐름과 세부 처리 로직을 더 명확하게 분리할 수 있었다.

<br>

### 2. 사용자를 믿지 말자

버그 데이 활동을 통해, 다른 사람이 구현한 웹사이트를 직접 테스트하고 버그를 찾아보는 경험을 했다. 그동안 미션을 수행하면서 고민했던 부분들을 떠올려가며 버그를 찾아냈다. 굉장히 재미있는 활동이었지만, 한편으로는 전혀 고려하지 않았던 영역들이 많다는 것에 놀라기도 했다.

특히 단순히 형식에 맞지 않는 입력으로 인한 에러 뿐만 아니라, 의도적으로 잘못된 경로나 조작된 입력값을 전달함으로써 시스템을 망가뜨리거나, 내부 정보를 빼내는 행위까지 직접 해볼 수 있었다. 예외 처리의 중요성을 더욱 생생하게 느낄 수 있었다.

이 경험을 통해, 정상적인 흐름을 잘 처리하는 것만으로는 충분하지 않다는 것을 실감했다. 모든 사용자가 개발자의 의도대로 서비스를 사용하지는 않으며, 심지어는 악의적인 목적을 가지고 서비스를 공격하는 사용자도 있다. 이 사실을 항상 염두에 두고 개발해야겠다는 생각을 했다.

단순한 유효성 검사를 넘어서, 여러 가지 보안 문제에 대해 더 공부해야겠다는 교훈을 얻었다.

<br>

## 어려웠던 점

### 1. 추상화와 이해하기 쉬운 코드

클린 코드를 작성하는 데 있어 가장 중요하게 생각하는 것 중에 하나는 코드의 가독성이다.

단순히 하나의 클래스나 메서드가 깔끔하게 보이는 것을 넘어서, 프로젝트 전체의 구조를 직관적으로 이해할 수 있는 코드를 작성하고 싶다는 생각을 항상 하고 있다.

이번 미션에는 평소보다 추상화를 더욱 적극적으로 적용해보려고 노력했다. 공통된 특성을 인터페이스로 정의하기도 하고, 함수형 인터페이스를 통해 처리 로직을 외부에서 주입하도록 하기도 했다. 불필요하게 중복되는 코드를 줄이고, 유지보수성을 끌어올릴 수 있었다.

하지만 그와 동시에 잃는 것도 있었다. 추상화 수준이 높아지면서 코드를 이해하기는 오히려 더 어려워졌다는 느낌이 들었다.

예를 들어 람다식으로 로직을 넘기는 방식이나, 한 클래스가 여러 추상 클래스나 인터페이스를 동시에 구현하는 구조는 처음 보는 사람에게는 이해하기 어려울 수도 있다. 당장 나부터도 다른 사람의 코드를 리뷰하면서 그 부분이 가장 힘들었다.

이것이 추상화의 어쩔 수 없는 트레이드오프인지, 아니면 단순히 내가 아직 추상화에 익숙하지 않아서인지 조금 더 공부하고 싶어졌다. 추상화를 적절하게 활용하면서도 가독성이 좋은 코드를 작성하기 위해, 더 많은 연습이 필요하겠다고 느꼈다.

## Keep

### **1. 같은 고민을 가지고 있는 사람들과 이야기하기**

- 꼭 소프티어 과정이 아니더라도, 같은 분야를 공부하고 취업 활동을 하고 있는 사람들이다 보니, 고민과 생각의 결이 비슷했다.
- 서로 어떤 고민을 하고 있는지, 어떻게 헤쳐 나가고 있는지를 이야기하면서 많은 공감을 할 수 있었다. 내가 몰랐던 정보들도 많이 배울 수 있었다.
- 앞으로도 진로나 공부 방식 같은 다양한 주제로 자주 소통하면서, 함께 성장해나가고 싶다.

### 2. 겪은 문제를 다른 사람에게 가르쳐주기

- 버그 데이 활동을 하면서, 이전에 겪었던 연속된 슬래시 문제를, 다른 사람의 코드에도 테스트해봤다.
- 많은 코드에서 예외 처리가 되어있지 않았고, 서비스가 비정상적으로 작동하는 경우가 많았다.
- 해당 에러에 대해서 나에게 물어보는 사람들도 있었다. 내가 이전에 겪고 해결해본 문제였기 때문에, 문제의 원인과 해결 방법에 대해서 자세히 설명해줄 수 있었다.
- 내 경험이 다른 사람에게 도움이 될 수 있어 기뻤다. 문제를 공유하고 설명하는 과정에서 나도 한 번 더 복습할 수 있었다.

# 3. 학습내용

## 함수형 인터페이스 (Functional Interface)

### 정의

- 단일 추상 메서드 인터페이스 (Single Abstract Method, SAM)
- 인터페이스 내에 `default` 또는 `static` 메서드는 추가로 포함될 수 있으나, 추상 메서드는 하나만 존재해야 함
- `@FunctionalInterface` 애너테이션을 사용하면 컴파일러가 이를 검사해줌

```java
@FunctionalInterface
public interface MyFunction {
    void apply();  // 단 하나의 추상 메서드
}
```

### 목적 및 활용

- 람다 표현식 또는 메서드 참조의 대상으로 사용
- 콜백 처리, 전략 전달, 간단한 동작 위임 등에 자주 사용
- 불필요한 익명 클래스 생성을 줄이고 코드의 간결성과 가독성 향상

### 자바 표준 함수형 인터페이스 (java.util.function 패키지)

| 인터페이스 | 설명 |
| --- | --- |
| `Runnable` | 인자와 반환값이 없는 실행 코드 |
| `Supplier<T>` | 인자 없이 `T` 타입 결과 반환 |
| `Consumer<T>` | `T` 타입 인자를 받고 반환값 없음 |
| `Function<T,R>` | `T`를 받아 `R`을 반환 |
| `Predicate<T>` | `T`를 받아 boolean 반환 (조건 검사) |
| `BiFunction<T,U,R>` | 두 인자를 받아 `R` 반환 |

### 사용 예시

```java
@FunctionalInterface
public interface UserUpdater {
    void update(User user, HttpRequest request);
}
```

```java
UserUpdater updater = (user, request) -> {
    user.setNickname("newNick");
}

UserUpdateExecutor.execute(req, updater, "/mypage");
```

```java

private void updateUserInfo(User user, HttpRequest request) {
    String newNick = request.getParameter("nickname");
    if (newNick != null && !newNick.isBlank()) {
        user.setNickname(newNick);
    }
}

UserUpdateExecutor.execute(req, this::updateUserInfo, "/mypage");
```

### `@FunctionalInterface` 어노테이션

- 해당 인터페이스가 함수형 인터페이스임을 명시적으로 선언
- 컴파일 타임에 두 개 이상의 추상 메서드가 정의될 경우 에러 발생
- 생략 가능하지만, 의도를 명확히 드러내기 위해 사용하는 것이 권장됨

### 장점

- 코드 간결성 (익명 클래스 제거)
- 동작 전달 (함수형 프로그래밍 스타일)
- 재사용성과 가독성 향상
- 전략 패턴, 이벤트 리스너, 콜백 처리에 유리

<br>

## 인터페이스 vs 추상 클래스

| 항목 | 인터페이스 (`interface`) | 추상 클래스 (`abstract class`) |
| --- | --- | --- |
| **목적** | 기능(행동)의 계약을 정의 | 공통된 속성과 동작의 틀을 제공 |
| **상속 구조** | 다중 구현(다중 인터페이스 구현 가능) | 단일 상속만 가능 |
| **멤버 구성** | - `public static final` 상수<br>- `public abstract` 메서드 (기본)<br>- Java 8부터 `default`, `static` 메서드 포함 가능 | - 필드<br>- 생성자<br>- `abstract`/일반 메서드 모두 포함 가능 |
| **생성자** | 생성자 정의 불가 | 생성자 정의 가능 |
| **접근 제한자** | 모든 멤버는 암시적으로 public (명시적 작성 권장) | 다양한 접근 제어자 사용 가능 (private, protected 등) |
| **상속 키워드** | `implements` 키워드 사용 | `extends` 키워드 사용 |
| **사용 시점** | 클래스 간 **기능의 계약(규약)**이 필요할 때 | 클래스 간 공통 로직 또는 필드 공유가 필요할 때 |
| **기본 구현 제공 여부** | (Java 8+) `default` 메서드를 통해 일부 구현 가능 | 일부 메서드만 추상으로 정의, 나머지는 기본 구현 제공 가능 |
| **상속 제한** | 하나의 클래스는 여러 인터페이스 구현 가능 | 하나의 클래스만 추상 클래스로부터 상속 가능 |

<br>

## Decorator 패턴

- 객체에 추가적인 책임(기능)을 동적으로 부여할 수 있도록 설계된 패턴
- 상속을 사용하지 않고, 런타임에 유연하게 기능을 확장할 수 있는 구조를 제공

### 구조 (GoF 기준)

| 구성 요소 | 설명 |
| --- | --- |
| **Component** | 기본 기능을 정의한 인터페이스 혹은 추상 클래스 |
| **ConcreteComponent** | 기본 기능을 실제로 구현한 클래스 |
| **Decorator** | `Component`를 구현하며, `Component`를 포함하는 클래스 (기능 위임) |
| **ConcreteDecorator** | 추가 기능을 부여하는 데코레이터 클래스. `Decorator`를 상속하거나 확장함 |

### UML 구조

```
        ┌────────────────┐
        │  Component     │◄──────────────────────┐
        └────────────────┘                       │
                 ▲                               │
                 │                               │
      ┌─────────────────────┐        ┌─────────────────────┐
      │ ConcreteComponent   │        │     Decorator       │
      └─────────────────────┘        └─────────────────────┘
                                            ▲
                                            │
                                ┌─────────────────────┐
                                │ ConcreteDecorator   │
                                └─────────────────────┘
```

### 예제 (Java)

```java
// Component
public interface Coffee {
    String getDescription();
    int cost();
}

// ConcreteComponent
public class BasicCoffee implements Coffee {
    public String getDescription() { return "Basic Coffee"; }
    public int cost() { return 3000; }
}

// Decorator
public abstract class CoffeeDecorator implements Coffee {
    protected Coffee coffee;
    public CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }
}

// ConcreteDecorator
public class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }
    public String getDescription() {
        return coffee.getDescription() + ", Milk";
    }
    public int cost() {
        return coffee.cost() + 500;
    }
}

public class WhipDecorator extends CoffeeDecorator {
    public WhipDecorator(Coffee coffee) {
        super(coffee);
    }
    public String getDescription() {
        return coffee.getDescription() + ", Whip";
    }
    public int cost() {
        return coffee.cost() + 700;
    }
}

// 사용 예
Coffee coffee = new BasicCoffee();
coffee = new MilkDecorator(coffee);
coffee = new WhipDecorator(coffee);

System.out.println(coffee.getDescription()); // Basic Coffee, Milk, Whip
System.out.println(coffee.cost()); // 4200

```

### 장점

- 기존 코드를 변경하지 않고 기능 추가 가능 (Open/Closed Principle 준수)
- 유연한 조합 가능 (필요한 기능만 붙일 수 있음)
- 상속보다 구성(composition)을 통한 확장이므로 더 유연함

### 단점

- 데코레이터가 많아지면 구조가 복잡해질 수 있음
- 디버깅이 어려울 수 있음 (많은 객체의 포장을 따라가야 함)
