## 작업 과정에서 배운 것

### 1. 추상화의 이점

오늘 코드 리뷰 시간에 승진님의 코드를 보면서, 처음부터 추상화를 철저히 고려해둔 설계 방식이 매우 인상적이었다.

대부분의 클래스들이 인터페이스로 정의되어 있었다. 구현체와의 결합도를 최대한 줄이면서, 이후에 기능 확장이나 변경이 생기더라도 사용하는 쪽에서는 거의 영향을 받지 않도록 설계되어 있었다.

나는 보통 기능 확장이 실제로 일어난 후에 필요성을 느끼고, 그때부터 인터페이스를 추출해서 적용하는 경우가 많았다. 그러다보니 기존의 코드들과 충돌이 생기거나, 예상치 못한 문제를 유발하는 경우도 종종 있었다.

이번 리뷰를 하면서, 사전에 추상화를 염두에 두는 것이 얼마나 중요한지 느낄 수 있었다. 작은 기능이라도 인터페이스로 미리 추상화해두고, 변화에 유연한 구조를 만들어두는 습관을 길러야겠다.

<br>

## 어려웠던 점

### 1. 경로에 대한 처리

`/mypage////`처럼 비정상적인 경로가 들어왔을 때, HTML 파일은 잘 응답되었지만 CSS 스타일이나 이미지가 모두 깨져 보이는 문제가 있었다.

사실 구현 의도대로라면 HTML 파일조차 제대로 찾지 못했어야 정상이다.

먼저, HTML 파일이 찾아졌던 것은, 자바의 `File` 클래스가 내부적으로 연속된 슬래시를 하나의 경로 구분자로 인식하여 무시했기 때문이다. `new File("/mypage/////index.html")` 와 같이 중첩된 슬래시가 있어도 `/mypage/index.html` 경로로 파일을 제대로 찾고 있었던 것이다.

하지만 CSS나 이미지처럼 HTML 내부에서 상대 경로로 불러오는 리소스들은 문제가 달랐다. 브라우저는 사용자가 입력한 URL을 기준으로 상대 경로를 해석하기 때문에, 중첩된 슬래시가 포함된 경로를 그대로 요청했고, 그에 대응하는 정적 리소스를 서버에서 찾지 못하는 상황이 발생했다.

결국 문제 해결을 위해, 연속된 슬래시가 포함된 비정상적인 경로가 들어오면 이를 정규화된 경로(`/mypage` 등)로 리다이렉트하도록 처리했다. 단순한 문자열 치환 문제처럼 보였지만, 작게 보이는 차이 하나가 의도치 않은 동작을 유발할 수 있다는 점을 배울 수 있었다.

동일한 URL 입력에 대해서도, 브라우저, 서버, 파일 시스템이 각각 다른 방식으로 해석할 수 있기 때문에, 경로를 명확하게 정규화하는 작업이 얼마나 중요한지 깨달을 수 있었다.

<br>

### 2. 코드 리뷰 피드백을 정리하는 것이 생각보다 시간이 많이 들었다

다른 사람의 코드를 보고 피드백을 남기는 과정이 그렇게 단순한 일이 아니라는 걸 느꼈다. 단지 기능적으로 잘못된 부분만을 지적하는 것이 아니라, 왜 이렇게 설계했는지를 먼저 이해하려는 자세가 필요했다. 

지난주까지는 미션의 사이즈가 크지 않아서 코드를 쉽게 이해할 수 있었지만, 이번 주에는 구조도 복잡해지고, 클래스들이 상속 관계로 얽혀있기도 해서, 동작의 흐름을 한 번에 이해하기 어려웠다. 여러 클래스들을 오가면서 구조를 이해해야했다.

처음엔 한 눈에 안 보이던 구조적인 부분도 다시 읽어보니 나름의 설계 의도가 담겨 있었고, 그런 맥락을 이해한 뒤에야 제대로 된 피드백을 줄 수 있었다.

그래서 리뷰 코멘트를 작성하는 데 생각보다 시간이 오래 걸렸지만, 덕분에 다른 사람의 코드 흐름을 읽고 구조를 파악하는 힘을 기를 수 있었다.

# 2. 회고

## Keep

### **1. 애매하게 알고 있던 내용들도 다시 한 번 찾아보자**

- 수업을 하면서, 공부하는 내용과 관련하여 등장하는 개념들이 있었다. 자주 들어봤던 개념이지만 정확히 알고 있지는 못하다는 생각이 들었다.
- A라는 개념을 완전히 이해하기 위해서는 B라는 개념을 알아야 하는 상황이 있다.
- A에 대해서만 공부를 하고 B에 대해서는 대충 넘어가버리면, 결국 A에 대해서도 제대로 알지 못하게 된다.
- 오늘은 꼬리를 물듯이 키워드를 타고 타고 넘어가면서, 모르는 개념들에 대해 계속 찾아봤다. 덕분에 머릿속에 흩어져있던 개념들이 서로 연결되면서 정리되는 느낌이 들었다.
- 앞으로도 대충 지나가지 않고, 확실히 다지고 넘어가는 학습 태도를 가져야겠다.

### 2. 내가 겪은 문제를 다른 사람들에게도 알려주자

- 스크럼 시간에, URL 슬래시 처리와 관련된 문제를 그룹 멤버들과 공유했다.
- 사실, 다른 사람들은 이 문제를 어떻게 해결했는지 궁금해서 물어봤던 건데, 그룹 멤버들도 미처 생각하지 못했던 문제였고, 내가 말을 꺼낸 덕분에 문제를 알게 되었던 것이었다. 같이 문제의 원인을 생각해보면서 이야기를 나눌 수 있었다.
- 문제를 공유하는 게, 꼭 내가 도움을 받기 위한 것만은 아니라는 것을 느낄 수 있었다.
- 아직 해결하지 못한 문제라고 하더라도, 그것을 공유하는 게 다른 사람들에게도 도움이 될 수 있다는 것을 깨달았다. 남들이 모르고 넘어갈 수 있는 부분을 먼저 알려줄 수 있다는 것만으로도 충분히 가치 있는 일이라는 것을 느꼈다.

<br>

## Problem

### **1. 조사를 한 내용을 다른 사람들에게 설명하려니 쉽지 않았다**

- 인터넷에서 내용을 조사해서 찾은 내용을 가져와 적는다고 해도, 그것이 내 지식이 되기까지는 많은 시간이 필요한 것 같다. 수업 시간에 조사한 내용을 발표하려고 하니, 방금 본 내용인데도 글을 보지 않고서는 술술 설명할 수 없었다.
- 다른 사람의 언어로 적힌 내용이다보니 여러 번 읽어봐도 남의 말을 외우고 있는 느낌이지, 내 머릿속의 지식처럼 느껴지지 않았다.

### **2. 다른 할 일에 밀려서 미션을 거의 진행하지 못했다**

- 오전 수업과 오후 코드 리뷰 작성으로 하루의 대부분이 지나갔다.
- 남는 시간엔 수업 중 놓친 개념들을 복습하다 보니, 실제 미션 구현에 쓸 수 있는 시간이 거의 없었다.
- 특히 수업 내용 정리와, 추가 조사에 시간이 많이 소요되었다. 그것도 의미 있는 시간이긴 했지만, 계획했던 진도에 비해 너무 지체되었다는 아쉬움이 남는다.

<br>

## Try

### **1. 공부를 할 때 조사한 내용을 그대로 옮겨적지 말고 나의 언어로 한 번 바꿔보자**

- 인터넷에서 본 내용을 그대로 옮겨 적는 것만으로는 진짜 공부가 되지 않는다.
- 나에게 있어 자연스러운 표현과 용어로 다시 한 번 정리해보는 시간을 가지자.
- 말로 설명하거나 글로 써보는 과정을 거치고나면, 이해도 훨씬 잘 되고, 기억에도 오래 남을 것이다.

### **2. 우선순위를 정해두고 할 일을 하자**

- 회고를 매일 작성해야 하기는 하지만, 그날 궁금했던 내용은 기록해두고, 시간의 여유가 있을 때 자세히 찾아보는 방식으로 했어도 괜찮았을 것 같다.
- 미션은 이번 주 금요일이 되기 전에 마무리하는 것이 좋기 때문에, 우선순위를 앞에 두고 먼저 수행했어야 했다는 생각이 든다.
- 당장 해야하는 일과 나중에 해도 되는 일을 잘 구별해서 수행하자.

### 3. DNS 조회 (도메인 → IP 주소)

- `www.example.com` → `93.184.216.34`
- DNS 캐시 계층 (순차적으로 확인)
    1. **브라우저 DNS 캐시: 브라우저가 이전에 방문한 도메인에 대한 캐시**
    2. **운영체제 DNS 캐시: OS 수준에서 전체 애플리케이션 공통으로 사용하는 캐시** 
    3. **라우터/게이트웨이 캐시: 동일 네트워크 내의 모든 장비에서 자주 요청되는 도메인에 대한 캐시**
    4. **ISP DNS 서버: ISP(인터넷 서비스 제공자)의 DNS 서버**
    5. 최상위 DNS 서버(루트, TLD, 권한 서버): 처음부터 도메인을 찾아나섬
        - 재귀적으로 조회
- 한 번 조회된 IP는 브라우저/OS/라우터 등에서 TTL(Time To Live) 시간 동안 캐시됨

<br>

### 4. TCP 연결 (3-way 핸드셰이크)

브라우저는 해당 IP 주소와 TCP 연결을 시도 → 3-Way Handshake 방식으로 연결

**3-Way Handshake**

- TCP는 연결 지향 프로토콜
- 데이터를 전송하기 전에, 양쪽이 먼저 연결을 확립해야 함

1. **클라이언트 → 서버: SYN**
    
    ```jsx
    [클라이언트] -- SYN (ISN = X) --> [서버]
    ```
    
    - 클라이언트가 연결을 요청
    - 자신이 사용할 초기 시퀀스 번호(ISN)를 보냄
    - SYN: 접속 요청 플래그
2. **서버 → 클라이언트: SYN-ACK**
    
    ```
    [클라이언트] <-- SYN + ACK (ISN = Y, ACK = X+1) -- [서버]
    ```
    
    - 서버는 접속 요청을 수락하며 응답
    - 자신도 연결할 준비가 되었음을 알림 (SYN 포함)
    - 동시에 클라이언트의 SYN에 대한 확인 응답(ACK) 전송
3. **클라이언트 → 서버: ACK**
    
    ```
    [클라이언트] -- ACK (ACK = Y+1) --> [서버]
    ```
    
    - 클라이언트가 서버의 응답을 수신했음을 ACK로 확인
    - 이제 연결이 완전히 성립(Established)됨

<br>

### 5. TLS 핸드셰이크 (HTTPS인 경우)

- HTTPS = HTTP + TLS → 암호화된 HTTP 통신

**TLS(Transport Layer Security):** 

- 인터넷 상의 데이터를 도청, 위조, 변조로부터 보호하기 위한 암호화 통신 프로토콜

**TLS 핸드셰이크 주요 목표**

1. 서버(및 클라이언트)의 신원 검증
2. 양측이 사용할 암호화 방식(알고리즘) 협상
3. 공통 세션키 생성 (대칭키)
4. 이후 통신은 이 세션키를 기반으로 암호화된 데이터 송수신

**TLS 핸드셰이크 전체 흐름**

**1. ClientHello (클라이언트 → 서버)**

- 클라이언트가 서버에게 핸드셰이크 시작 신호 전송
- 포함 내용:
    - 클라이언트가 지원하는 TLS 버전
    - 암호화 알고리즘 목록 (Cipher Suites)
    - 랜덤 값 (Client Random)
    - 세션 ID (이전 세션 재사용 시)

**2. ServerHello (서버 → 클라이언트)**

- 서버가 선택한 암호 알고리즘을 알려줌
- 서버의 랜덤값 (Server Random)을 전송
- 서버의 인증서(SSL 인증서) 전달

**3. 인증서 검증 (클라이언트 측)**

- 브라우저(클라이언트)는 서버의 인증서가 유효한지 확인
    - 신뢰할 수 있는 CA에서 발급되었는지
    - 인증서의 도메인 이름이 일치하는지
    - 만료되지 않았는지
    - 중간 인증서 체인도 유효한지
- 검증 실패 시, 경고 메시지(예: "이 연결은 안전하지 않음")를 표시하고 연결 중단

**4. 세션키 생성 (키 교환)**

- 클라이언트와 서버는 서로의 랜덤값을 조합하거나,
- Diffie-Hellman, ECDHE 등을 통해 세션키(대칭키)를 공동 생성

**5. Finished 메시지 교환**

- 세션키를 이용해 암호화된 Finished 메시지를 주고받음
- 이걸로 "우리 둘 다 같은 세션키로 암호화할 준비가 되었다"는 걸 검증

**6. 암호화된 HTTP 통신 시작**

- 위 과정을 마치면 `HTTPS` 통신이 본격적으로 시작됨
- 이제는 모든 HTTP 요청/응답이 TLS 세션키로 암호화되어 송수신됨

<br>

### 7. 웹 서버 처리

서버는 HTTP 요청을 수신하고 처리:

- **정적 리소스** 요청이면: HTML/CSS/JS/이미지 등 반환
- **동적 페이지** 요청이면: 백엔드 로직 (예: PHP, Node.js, Spring 등)이 작동하여 HTML 생성

<br>

### 8. HTTP 응답 반환

```
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1024
```

- 응답 본문에 HTML 콘텐츠 포함
- 상태 코드에 따라 결과 전달 (200, 404, 500 등)

<br>

### 9. HTML 파싱 및 리소스 로드

브라우저는 받은 HTML을 파싱하면서 다음을 수행:

**렌더링 준비 과정**

1. **DOM 트리 생성** – HTML 구조 분석
2. **CSSOM 생성** – CSS 파싱
3. **렌더 트리 생성** – DOM + CSSOM 결합
4. **레이아웃 계산** – 각 요소의 위치 계산
5. **페인팅** – 각 요소를 픽셀로 변환
6. **컴포지팅** – 여러 레이어를 조합해 화면 출력

**추가 리소스 요청**

- `<link>`, `<script>`, `<img>` 등을 통해 CSS, JS, 이미지 등의 추가 요청이 자동 전송
- 이 과정도 모두 병렬적으로 처리

<br>

### 10. JavaScript 실행 및 렌더링 완료

**JS 엔진 작동**

- 자바스크립트 실행으로 DOM 조작, 이벤트 등록 등 동적 기능 활성화
- React/Vue/SPA의 경우, JS가 페이지 전체를 구성함 (CSR)

**비동기 처리**

- AJAX, Fetch, Promise 등으로 비동기 데이터 로딩
- 데이터 도착 시, DOM 수정 및 재렌더링

<br>

### 11. 브라우저에 화면 출력

렌더링 트리 → 화면에 실제로 **페이지가 시각적으로 표시됨**

- 화면에 보이는 시점은 “First Paint”, “First Contentful Paint” 등으로 측정
- 이 이후에도 백그라운드에서 이미지나 데이터 계속 로드될 수 있음

## OSI 7계층 모델 vs. TCP/IP 4계층 모델

### OSI 7계층 모델 (Open Systems Interconnection Model)

| 계층 | 이름 | 역할 요약 |
| --- | --- | --- |
| 7 | 애플리케이션(Application) | 사용자 인터페이스 제공 (ex. 웹 브라우저, 메일) |
| 6 | 표현(Presentation) | 데이터 형식 변환, 암호화, 압축 등 |
| 5 | 세션(Session) | 연결 설정/유지/해제 (ex. 로그인 세션) |
| 4 | 전송(Transport) | 신뢰성 있는 데이터 전송 (ex. TCP, UDP) |
| 3 | 네트워크(Network) | 라우팅, 논리적 주소 지정 (ex. IP) |
| 2 | 데이터 링크(Data Link) | 물리적 주소(MAC), 프레임 전송 |
| 1 | 물리(Physical) | 전기적 신호, 케이블, 하드웨어 연결 |

<br>

### TCP/IP 4계층 모델

| 계층 | 이름 | 역할 요약 |
| --- | --- | --- |
| 4 | 애플리케이션(Application) | 응용 계층 기능 포함 (OSI 5~7계층 통합) |
| 3 | 전송(Transport) | TCP, UDP |
| 2 | 인터넷(Internet) | IP 주소, 라우팅 |
| 1 | 네트워크 접근(Network Access) | OSI 1~2계층 통합 (LAN, MAC, 전송 매체) |

<br>

### **차이점**

| 구분 | OSI 7계층 | TCP/IP 4계층 |
| --- | --- | --- |
| 계층 수 | 7개 | 4개 |
| 설계 목적 | 이론적 표준화 모델 (국제 표준화기구 ISO) | 실용 중심 모델 (인터넷 설계 기반) |
| 사용 범위 | 교육·이론 중심 | 실무·인터넷 프로토콜 스택 |
| 계층 간 결합도 | 계층별로 명확히 분리 | 일부 계층 통합 (5~7, 1~2) |

<br>

### 주요 프로토콜과 계층

| 계층 | 대표 프로토콜 | 설명 |
| --- | --- | --- |
| 응용 계층 (OSI 7 / TCPIP 4) | **HTTP**, FTP, SMTP, DNS | 사용자에게 직접 보이는 서비스 |
| 전송 계층 (OSI 4 / TCPIP 3) | **TCP**, **UDP** | 포트 기반 통신, 신뢰성/속도 선택 |
| 인터넷 계층 (OSI 3 / TCPIP 2) | IP, ICMP, ARP | 주소 지정, 라우팅 |
| 데이터링크/물리 계층 | Ethernet, Wi-Fi | MAC주소, 전송 신호 |

<br>

## HTTP의 Stateless

**HTTP의 Stateless(무상태성)**

- 각 요청이 서로 독립적
- 서버가 이전 요청의 상태(정보)를 기억하지 않음

**예시**

1. 사용자가 로그인 요청을 보냄 → 서버가 인증 후 응답함
2. 다음 요청을 보낼 때, 서버는 이 사용자가 로그인한 상태인지 모름
    - 따라서 매번 요청마다 필요한 정보를 클라이언트가 직접 포함시켜야 함 (ex. 세션 ID, 토큰)

### Stateless의 장점

- **구조 단순화**
    - 서버가 클라이언트 상태를 저장하지 않아 로직이 간단해짐
- **요청 재처리 용이**
    - 동일한 요청은 항상 동일하게 처리됨 → idempotent(멱등성) 보장에 유리
- **수평 확장(Scalability)**
    - 서버가 상태를 저장하지 않기 때문에 여러 서버 간 요청을 분산하기 쉬움 (로드밸런싱)
- **리소스 절약**
    - 서버가 사용자 상태를 메모리/디스크에 저장하지 않으므로 RAM/스토리지 절약
- **캐싱에 유리**
    - 상태에 따라 결과가 달라지지 않으므로 프록시/브라우저에서 효율적으로 캐싱 가능

### Stateless의 단점

- **인증 상태 유지 어려움**
    - 서버가 클라이언트 상태를 기억하지 않아 인증 유지 기능을 별도로 구현해야 함
- **상태 기반 기능 구현 번거로움**
    - 장바구니, 사용자 설정 등 지속적인 상태 저장이 필요한 기능을 직접 설계해야 함
- **클라이언트 부담 증가**
    - 클라이언트가 매 요청마다 필요한 모든 정보를 함께 보내야 함 (예: 인증 토큰, 사용자 ID)
- **복잡한 UX 제공 어려움**
    - 사용자의 히스토리나 진행 상황을 기억하지 못해 복잡한 사용자 경험 구현이 어려움
- **상태 공유가 필요한 기능엔 추가 기술 필요**
    - 예: 세션, 쿠키, JWT, 서버 저장소 등이 필요

<br>

### 참고) 수평 확장이란?

- 서버의 처리 능력을 높이기 위해 "서버 개수"를 늘리는 방식
    - 하나의 서버 성능을 높이는 것이 아니라, 여러 서버에 부하를 분산시킴

**수평 확장 vs 수직 확장**

| 구분 | 수평 확장 (Horizontal Scaling) | 수직 확장 (Vertical Scaling) |
| --- | --- | --- |
| 방법 | 서버 여러 대 추가 | 기존 서버의 CPU, RAM 증설 |
| 장점 | 장애에 강하고 유연한 확장 | 설정 간단, 변경이 빠름 |
| 단점 | 로드 밸런싱, 상태 공유 문제 발생 | 한계에 도달하면 확장 불가능 |
| 특징 | 클라우드/마이크로서비스 친화적 | 물리 장비 한계에 영향 받음 |

**예시: 웹 서비스 트래픽 증가**

- 기존에 `server1`만 있던 서비스를
- `server1`, `server2`, `server3` 으로 확장
- 사용자 요청은 로드 밸런서가 각 서버에 분산

**HTTP의 Stateless와 수평 확장**

- HTTP는 Stateless(무상태)하기 때문에 수평 확장이 쉬운 구조
    - 서버가 클라이언트의 상태를 기억하지 않기 때문에 어떤 서버에 요청이 가더라도 같은 응답을 줄 수 있음
    - 서버 간에 세션 동기화나 공유가 불필요

<br>

### State를 관리해야 하는 이유

1. **사용자 인증/권한 관리**
    - 사용자가 인증된 상태라는 것을 서버가 알고 있어야 함
    - 매 요청마다 로그인할 수 없기 때문에, 사용자 식별 정보를 유지해야 함
2. **개인화된 사용자 경험 제공**
    - 사용자의 이름, 언어 설정, 테마, 장바구니 등
    - 요청 간 유지되는 상태 정보로 관리해야 사용자 맞춤 서비스 가능
3. **세션 기반 비즈니스 로직 구현**
    - 쇼핑몰, 결제, 회원가입 등 → 이전 단계에서 선택한 정보를 다음 단계에서 이어받음
    - 단계별로 상태를 이어나가야 함

<br>

### State를 관리하는 3가지 대표 방법

| 방법 | 특징 | 저장 위치 |
| --- | --- | --- |
| 쿠키(Cookie) | 클라이언트에 저장되는 작은 데이터 | 클라이언트(브라우저) |
| 세션(Session) | 서버가 사용자별 상태를 저장 | 서버 |
| JWT (JSON Web Token) | 클라이언트가 상태 정보를 암호화된 토큰으로 보관 | 클라이언트 (토큰에 정보 포함) |

<br>

### **클라이언트 측 상태 관리 방식 (Client-side)**

| 방법 | 설명 | 저장 위치 | 특징 |
| --- | --- | --- | --- |
| **LocalStorage / SessionStorage** | 웹 브라우저에 직접 저장하는 키-값 저장소 | 브라우저 내부 | 요청에 자동 포함 안 됨 (JS로 직접 넣어야 함) |
| **URL 파라미터 / 해시** | 상태 정보를 URL 쿼리스트링 등에 포함 | 주소창 | 단순 상태 전달에 유용, 보안 취약 |
| **클라이언트 메모리 상태** | React/Vue 등에서 상태를 메모리에서 유지 | RAM (페이지 새로고침 시 사라짐) | 빠르지만 휘발성, SSR 연동 어려움 |
- 클라이언트가 상태 정보를 저장하고, 요청 시마다 서버에 전송하거나, 자체적으로 관리
- 주로 단기 상태 유지나 인증 상태 전달용으로 활용

<br>

### **서버 측 상태 관리 방식 (Server-side)**

| 방법 | 설명 | 저장 위치 | 특징 |
| --- | --- | --- | --- |
| **Context 기반 상태 관리** | 요청 내에서 생성된 상태(Context)를 통해 내부 처리에 사용 | 서버 애플리케이션 내 메모리 | 주로 RPC, gRPC 등 내부 통신에 사용 |
| **DB 기반 상태 저장** | 사용자별 상태를 DB에 저장 (ex. 장바구니) | RDB, NoSQL 등 | 영속성 높음, 느릴 수 있음 |
| **Redis / 캐시 기반 상태 저장** | 세션, 인증정보, 임시 상태 등을 Redis에 저장 | Redis (서버 캐시) | 속도 빠르고 확장성 높음, TTL 설정 가능 |
| **Sticky Session (로드밸런서)** | 같은 클라이언트 요청을 항상 같은 서버로 보냄 | LB + 서버 세션 | 상태 공유는 없지만 로드밸런서 의존 |
- 서버가 사용자의 상태 정보를 저장하고, 클라이언트는 식별자(key)만 보내는 구조
- 주로 장기 상태 유지, 보안, 사용자 흐름 제어에 사용됩니다.

<br>

## 3. 쿠키 vs 세션 차이 정리

| 항목 | 쿠키 (Cookie) | 세션 (Session) |
| --- | --- | --- |
| **저장 위치** | 클라이언트(브라우저)에 저장 | 서버에 저장 |
| **관리 주체** | 클라이언트가 보관, 서버가 읽음 | 서버가 상태 관리, 클라이언트는 세션 ID만 보관 |
| **전송 방식** | 매 요청마다 자동으로 서버에 전송됨 | 세션 ID만 쿠키나 URL 등을 통해 전송 |
| **저장 용량** | 약 4KB 제한 | 서버에 따라 제한 거의 없음 |
| **유효 기간** | 설정 가능 (지정 안 하면 브라우저 종료 시 삭제) | 보통 타임아웃(예: 30분) 또는 브라우저 종료 시 삭제 |
| **보안성** | 사용자가 볼 수 있어 노출 위험 있음 | 서버에만 저장되므로 보안성 높음 |
| **확장성 문제** | 없음 (클라이언트에 저장하므로 서버 부담 없음) | 서버 세션 공유 필요 → 분산 환경에서 관리 복잡 |
| **사용 예시** | 자동 로그인, 언어 설정, 다크모드 | 로그인 인증 상태, 사용자 정보, 장바구니 |

<br>

## JWT(JSON Web Token)

- 서버가 인증 후 클라이언트에게 디지털 서명된 토큰을 발급하고, 클라이언트가 이를 저장해 다음 요청부터 사용하도록 하는 Stateless 인증 방식
- 서버가 별도의 세션 저장 없이도 요청을 검증 가능
- 보통 HTTP Header의 Authorization에 담아 전송

### 구성 요소

JWT는 `.` 으로 구분된 3개의 부분으로 구성됨

```
xxxxx.yyyyy.zzzzz
 ↑     ↑     ↑
Header.Payload.Signature
```

| 부분 | 설명 |
| --- | --- |
| Header | 토큰 유형, 서명 알고리즘 (예: HS256) |
| Payload | 사용자 정보, 권한, 토큰 만료시간 등 실제 데이터 (Base64로 인코딩된 JSON) |
| Signature | 위 정보를 기반으로 한 서명 (비밀키 기반, 위변조 방지용) |

<br>

## Access Token vs Refresh Token

| 비교 항목 | Access Token | Refresh Token |
| --- | --- | --- |
| 목적 | 인증(자격 증명) | 재인증(토큰 재발급) |
| 사용 시점 | 매 API 요청 | Access Token 만료 시 |
| 만료 시간 | 짧음 (수분~수시간) |  |
| 저장 위치 | 클라이언트 메모리, 쿠키 | 쿠키(httpOnly), DB, Redis |
| 탈취 시 위험 | 제한적 | 매우 치명적 |
| 서버 저장 필요 | 보통 없음 (Stateless) | 있음 (보안 이유로) |

<br>

## JWT vs. Session

| 항목 | 세션 기반 인증 | Refresh Token 기반 인증 |
| --- | --- | --- |
| **클라이언트 인증 방식** | 세션 ID로 사용자 상태를 서버에서 조회 | Access Token 자체가 인증 정보 (Stateless) |
| **서버 상태 의존성** | 상태 전적으로 서버에 있음 | Access Token은 Stateless, Refresh Token만 상태 필요 |
| **확장성** | 수평 확장 시 세션 동기화 필요 (Sticky Session, Redis 등) | 서버가 상태를 거의 안 가지므로 확장 용이 |
| **토큰 재발급 처리** | 필요 없음 (세션이 만료되면 재로그인) | Access Token 짧게, Refresh Token으로 재발급 가능 |
| **세션 내용** | 유저 정보, 권한, 상태 등 다양한 내용 | Refresh Token만 저장하거나 사용 이력 관리 |
| **전송 방식** | 주로 쿠키 기반 | 주로 Authorization 헤더 (또는 httpOnly 쿠키) |
| **멀티 플랫폼** | 쿠키 의존 → 웹 환경에 최적 | 모바일, SPA, API 등 다양한 플랫폼에 적합 |
- 세션은 Stateful 인증
- JWT는 Stateless 인증을 전제로 함
    - 재인증을 위한 보조 수단(Refresh Token)만 예외적으로 상태 저장

<br>

**JWT는 Stateless → 수평 확장에 유리**

- JWT는 Access Token 자체에 사용자 정보를 담고 있음
    
    → 서버는 토큰을 검증만 하면 됨 (별도 상태 저장 없음)
    
- 따라서 요청이 어떤 서버로 가도 상관없음
    
    → 즉, 서버 간 상태 공유 필요 없음 → 수평 확장(Scale-out)에 매우 적합
    

<br>

**세션은 Stateful → 수평 확장에 불리**

- 세션은 사용자의 상태 정보를 서버 메모리(또는 Redis 등)에 저장
- 클라이언트는 세션 ID만 쿠키로 갖고 있고, 서버는 이 ID를 통해 사용자 정보를 조회함
- 문제 → 서버가 여러 대일 경우, 세션 ID가 저장된 서버로만 요청이 가야 함
    - 서버 1에 저장된 세션 정보를 서버 2는 모름
    - 세션 ID는 있지만 해당 사용자 정보가 없는 서버로 요청이 가면 로그인 상태가 유지되지 않음
    

<br>

**Sticky Session이란?**

- 클라이언트의 요청을 항상 같은 서버 인스턴스로 라우팅하는 방식

| 장점 | 단점 |
| --- | --- |
| 서버 간 세션 공유 없이 세션 유지 가능 | 서버 장애 시 해당 사용자 세션 모두 손실 |
| 설정만으로 간단히 구현 가능 | 로드 밸런싱 효과 반감, 특정 서버에 부하 집중 |

<br>

## CI/CD

- 소프트웨어 개발과 배포의 효율성과 품질을 높이기 위해 널리 사용되는 **자동화**된 개발 파이프라인

| 용어 | 뜻 |
| --- | --- |
| **CI** (Continuous Integration) | 지속적인 통합 |
| **CD** (Continuous Delivery / Continuous Deployment) | 지속적인 전달 / 지속적인 배포 |

<br>

### CI (지속적 통합: Continuous Integration)

- 여러 개발자가 동시에 작업한 코드를 자주 통합하고, 이를 자동으로 빌드하고 테스트하는 과정.
- **필요한 이유**
    - 여러 명이 작업하면 충돌 가능성이 커지기 때문에 통합을 자주 해서 문제를 조기에 발견함
    - 커밋할 때마다 자동 테스트로 코드 품질을 보장
    - 빌드/테스트 자동화로 개발 속도 향상

<br>

### CD (지속적 전달 / 배포: Continuous Delivery / Deployment)

| 구분 | 설명 | 배포 방식 |
| --- | --- | --- |
| **Continuous Delivery** | 운영 배포 직전까지 자동화 (배포는 사람이 결정) | **수동 승인 필요** |
| **Continuous Deployment** | 운영까지 자동 배포 (완전 자동) | **자동 배포** |
- **필요한 이유**
    - 코드가 준비되는 즉시 배포 가능 → 릴리즈 속도 증가
    - 수동 배포의 실수를 줄이고, 안정성과 일관성 확보
    - 사용자 피드백을 더 빠르게 반영 가능

<br>

### CI와 CD의 차이

| 항목 | CI (통합) | CD (배포) |
| --- | --- | --- |
| 핵심 역할 | 코드 병합 + 테스트 | 코드의 배포 가능 상태 유지 + 실제 배포 |
| 시점 | 개발 중 | 개발 완료 후 |
| 목적 | 코드 품질 유지 | 사용자에게 기능 전달 |
| 자동화 범위 | 빌드, 테스트 | 테스트 이후 → 배포까지 |
| 실패 시 영향 | 개발자가 수정하면 됨 | 운영 서비스에 영향 줄 수 있음 |

<br>

## 안전한 서버 배포를 위한 대표적인 전략

### **Blue-Green Deployment**

- 두 개의 완전한 환경을 번갈아 가며 운영
    - 새 버전(Green)을 미리 배포하고 테스트까지 끝낸 뒤, 트래픽을 기존 환경(Blue)에서 새 환경으로 한 번에 전환하는 방식
    - 트래픽 스위칭: Load Balancer(Route 변경)로 한순간에 전환

```
       사용자
         ↓
  [Load Balancer]
   ↙        ↘
[Blue 서버]   [Green 서버]
(현재 운영)    (새 버전 대기)
```

**특징**

| 항목 | 설명 |
| --- | --- |
| 배포 대상 | 전체 사용자에게 일괄 |
| 배포 전 테스트 | Green 환경에서 실제 운영과 동일하게 테스트 가능 |
| 롤백 | 트래픽만 다시 Blue로 돌리면 즉시 복구 |
| 트래픽 전환 방식 | 로드밸런서 설정 변경, DNS 스위칭 등 |
| 운영 비용 | 두 환경을 동시에 유지해야 하므로 비용 증가 가능성 있음 |

**장점**

- **무중단 배포 가능**: Green 환경 준비 후 한 번에 전환
- **빠른 롤백**: 문제가 생기면 트래픽만 Blue로 되돌리면 됨
- **운영 안정성**: 새 버전을 실제처럼 충분히 검증 가능

**단점**

- **리소스 이중화 필요**: 서버, DB, 인프라 2세트 유지
- **데이터베이스 동기화 어려움**: Blue/Green이 동일한 DB를 사용할 경우 구조가 복잡해질 수 있음
- **배포 간격이 김**: 점진 배포 불가 → 사용자 전원이 영향을 받음

<br>

### **Canary Deployment (카나리아 배포)**

- 일부 사용자에게만 새 버전을 점진적으로 배포
    - 마치 카나리아가 광산의 독가스를 감지하듯, 소수 사용자에게 먼저 반응을 보고 이상 없을 때 점점 확장하는 전략
- 트래픽의 일부만 Canary 서버로 전달
- 이상 없으면 점차 Canary 서버 비율을 확대

```
        사용자 트래픽
           ↓
    [Load Balancer]
     ↙          ↘
[Stable 서버]  [Canary 서버]
  (기존 버전)   (새 버전, 1% → 5% → 20%...)
```

**특징**

| 항목 | 설명 |
| --- | --- |
| 배포 대상 | 일부 사용자부터 시작, 점진 확대 |
| 위험 분산 | 전체 사용자에게 배포 전에 문제 사전 발견 가능 |
| 롤백 | Canary 서버만 초기화 → 영향 최소화 |
| 트래픽 제어 방식 | Nginx, Istio, AWS ALB, Envoy 등을 통한 비율 기반 분산 |

**장점**

- **안전한 실 사용자 테스트**: 실제 환경에서 반응, 성능, 오류 확인 가능
- **롤백 간단**: 전체 롤백 필요 없이 일부 서버만 차단 가능
- **점진적 위험 통제**: 트래픽을 1% → 5% → 20% → 100%로 서서히 확장

**단점**

- **구현 복잡도 높음**: 트래픽 분산, 모니터링 자동화 필요
- **사용자 간 불일치 가능**: 어떤 사용자는 새 기능을 보고, 어떤 사용자는 구버전 사용
- **A/B 테스트와 혼동 우려**: 의도된 실험인지, 배포 오류인지 관리가 필요

<br>

## Observability

- 소프트웨어 시스템의 동작 상태를 외부에서 모니터링, 분석, 디버깅할 수 있게 만드는 능력
- 복잡한 분산 시스템, 마이크로서비스, 클라우드 환경에서 장애 탐지·원인 분석·성능 개선을 가능하게 함

### 1. Log (로그)

- 시스템에서 발생한 이벤트나 메시지의 기록
    - 예: 사용자가 로그인함, 결제 실패, 예외 발생 등

**특징**

| 항목 | 설명 |
| --- | --- |
| 형태 | 문자열 기반 (예: JSON, 텍스트, key-value 등) |
| 내용 | 특정 시점의 상세 정보 |
| 시간 중심 | 이벤트가 언제 발생했는지 중심 |
| 사용 목적 | 디버깅, 오류 추적, 감사 기록 등 |

**예시**

```json
{
  "timestamp": "2025-07-23T12:34:56Z",
  "level": "ERROR",
  "service": "user-service",
  "message": "로그인 실패: 비밀번호 불일치",
  "userId": "1234"
}
```

<br>

### 2. Metric (메트릭)

- 시스템의 상태를 수치로 표현한 시계열 데이터
    - 예: CPU 사용률, 요청 수, 응답 시간, 에러율 등

**특징**

| 항목 | 설명 |
| --- | --- |
| 형태 | 숫자 기반의 시계열 데이터 |
| 목적 | 성능 모니터링, 알림(Alert), 대시보드 시각화 |
| 저장소 | Prometheus, InfluxDB 등 |
| 처리 방식 | Aggregation(합계, 평균 등)에 최적화됨 |

**예시**

```
http_requests_total{status="200", method="GET"} 1520
```

<br>

### 3. Trace (분산 추적)

- 하나의 요청이 시스템 전체를 거쳐가는 흐름을 추적
- 마이크로서비스 환경에서 특히 중요

**특징**

| 항목 | 설명 |
| --- | --- |
| 구성 | Trace → Span(작은 작업 단위)들의 집합 |
| 목적 | 병목 분석, 성능 이슈 파악, 요청 흐름 이해 |
| 저장소 | Jaeger, Zipkin, OpenTelemetry 등 |
| 연관성 | 로그/메트릭과 연계 가능 (예: 오류 발생 지점 추적) |

**예시**

```
[사용자 요청]
 → [API Gateway]
   → [Auth Service]
     → [User DB]
   → [Billing Service]
```

각 단계가 Span이 되고, 전체가 하나의 Trace로 묶임 (Trace ID로 식별)
