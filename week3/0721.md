## 작업 과정에서 배운 것

### 1. 역할을 처음부터 명확하게 나누자

클래스들의 책임과 역할을 분리하면서 애매한 부분들이 있었다. ‘굳이 이렇게까지 나눌 필요가 있을까?’ ‘이 정도 역할은 한 요소가 담당해도 되지 않을까?’ 같은 생각들이 들었다.

그중에서 몇몇 부분들은 딱히 건드리지 않고 그대로 남겨두기도 했다. 결과적으로 보자면, 그런 부분들이 이후에 구조 확장에서 문제가 되는 경우가 많았다. 

당장 보기에 긴가민가한 부분들은, 프로그램의 규모가 더 커졌을 때 문제를 일으키게 될 확률이 높다는 것을 깨달을 수 있었다. 약간이라도 위화감이 드는 부분들은 다소 번거롭더라도 조기에 정리해두는 게, 장기적으로 볼 때 더 효율적이라는 교훈을 얻었다.

<br>

### 2. 프레임워크 없이 구현하는 것

평소에는 서버를 개발할 때 Spring과 JPA를 주로 사용하기 때문에, 복잡한 요청을 간단하게 처리할 수 있었다. 이번에는 JDBC로 직접 DB 연결과 쿼리 작성을 해보면서, DB와 SQL의 기초적인 흐름을 오랜만에 다시 느껴볼 수 있었다.

프레임워크가 얼마나 많은 것을 대신 처리해주고 있었는지 새삼 느낄 수 있었다. 또 한편으로는 그 내부가 어떻게 동작하고 있는지 더 깊게 이해할 수 있는 기회이기도 했다.

엘리베이터만 타다보면 계단을 올라갈 수 있는 체력은 점점 떨어지게 된다. 프레임워크 없이 구현해보는 과정은 번거롭고 어려웠지만, DB에 대한 기초를 다시 한 번 다질 수 있는 좋은 경험이었다.

<br>

## 어려웠던 점

### 1. 동적 HTML - StringBuilder 방식 vs. Template Engine 방식

로그인 여부에 따라서 상단 버튼의 내용을 동적으로 다르게 응답해줘야 했다.

처음에는 미션에서 주어진 힌트와 같이 `StringBuilder`를 사용하여 HTML을 직접 문자열로 생성하는 방식으로 구현하려고 했다. 그러나, 코드가 너무 길어져 가독성이 떨어지고, 하드코딩이 되어 수정이 어려워진다는 문제가 있었다.

그래서 템플릿엔진처럼 HTML에 Placeholder를 뚫어두고, 적절한 값을 채워넣는 방식으로 구현해보고자 했다.

Placeholder명과 치환할 값을 Map 형태로 저장한 다음, `replace()` 메서드를 통해 HTML 내의 Placeholder들을 찾아 적절한 값으로 교체하도록 구현했다. 훨씬 직관적인 코드로 기능을 구현할 수 있었고, 유지보수성도 좋아졌다.

다만, HTML 문서가 복잡해지고 Placeholder의 종류가 다양해지면, 현재의 방식은 `replace()` 메서드의 호출이 반복되기 때문에 성능적으로 비효율적이라는 한계 또한 있었다. 추후 미션에서 조금 더 나은 방식이 있을지 고민해봐야겠다.

<br>

### **2.** 라우팅을 계층구조로 수행?

라우팅 과정이 복잡해지면서 계층적으로 구조를 나누고 싶었다.

처음에는 URL 경로가 도메인별로 나뉜다는 점(`/user`, `/mypage` 등)을 고려하여, 도메인에 대한 분기를 먼저 수행하고, 도메인 내에서 추가적인 분기를 수행하고자 했다.

이를 위해 라우터 내부에 다시 라우터맵을 가질 수 있게 하고, 마지막 계층에서는 리졸버맵을 통해 응답을 생성하는 구조를 구현했다. 예를 들어, `/user/login` 요청은 `DomainRouter → UserRouter → LoginResolver`로 순차적으로 라우팅되도록 설계했다.

하지만 몇 가지 문제가 있었다.

- 경로의 계층 수가 일정하지 않음:
    - 같은 계층에서도 어떤 경로는 바로 응답을 만들어야 하고, 어떤 경로는 더 깊은 라우팅이 필요한 경우가 발생한다.
    - 라우터가 라우터맵을 가져야 할 수도, 리졸버맵을 가져야 할 수도 있게 되어, 구조적으로 일관성이 떨어졌다.
- 라우팅 단계에서 HTTP 메서드를 고려하지 않음:
    - 라우터가 경로만으로 리졸버를 매핑해주게 된다.
    - 같은 경로에서 HTTP 메서드(GET/POST)에 따라 응답이 달라져야 하는 경우, 이를 리졸버 내부에서 처리해야 했다.
    - 라우터와 리졸버의 역할 분리가 모호해졌다.

이를 해결하기 위해, `/user/login`과 같은 전체 경로 문자열을 키로 사용하여 라우팅을 일차적으로 수행하고, 그 내부에서 HTTP 메서드를 기반으로 다시 리졸버를 찾는 2단 Map 구조로 재설계했다.

또한, 모든 라우팅 정보를 `RouteRegistry`라는 전담 클래스에서 등록하고 관리하도록 함으로써, 라우팅 정보가 코드 전반에 흩어지지 않고 한 곳에서 명확하게 확인할 수 있게 했다. 

이를 통해, 라우터는 라우팅만, 리졸버는 응답 생성만을 담당하게 되어 역할 분리가 명확해졌다. 특정 경로에 대해 어떤 메서드가 허용되는지도 쉽게 확인 가능하고, `405 Method Not Allowed` 처리도 깔끔하게 구현할 수 있었다.

<br>

### 3. 정적 파일 응답 전담 클래스?

처음에는 각 리졸버 내부에서 정적 리소스 응답까지 직접 처리하도록 구현했다.

예를 들어, `/user/login` 경로에 대한 `GET` 요청은 `LoginResolver`에서 로그인 화면 HTML을 반환하고, `POST` 요청은 로그인 처리를 수행하는 방식이었다.

또한 어떤 리졸버에도 매핑되지 않은 경로의 경우에는, 마지막에 `DefaultResolver`가 응답 가능한 정적 리소스가 존재하는지 확인하여 응답하도록 했었다.

하지만 이 방식에는 다음과 같은 문제점이 있었다

- 정적 리소스 응답에 대한 책임이 여러 리졸버에 분산
    - 각 리졸버가 도메인 비즈니스 로직과 정적 파일 응답 처리를 동시에 담당한다.
    - 다수의 리졸버에 정적 리소스 응답에 대한 로직이 중복되어 존재하게 된다.

이 문제를 해결하기 위해 `DefaultResolver`의 이름을 `StaticFileResolver`로 변경하고, 정적 리소스에 대한 응답을 전담하게 했다.

2번 항목에서 언급했듯이, 라우팅을 경로 + HTTP 메서드 기준의 2단 Map 구조로 리팩토링했기 때문에, 동일한 경로여도 HTTP 메서드가 다르면 다른 리졸버에 매핑할 수 있게 되었다. 따라서 정적 파일 리소스에 대한 요청을 명시적으로 StaticFileResolver에 매핑시켜주었다. 어떤 리졸버에도 매핑되지 않는 경로에 대해서도 StaticFileResolver가 정적 리소스를 찾아주도록 처리했다.

정적 리소스 응답 책임이 `StaticFileResolver`에 집중되면서 리졸버들 사이의 역할 분리가 명확해졌다.

# 2. 회고

## Keep

### **1. 기능 구현에 만족하지 않고, 더 좋은 구조를 계속 고민하는 자세**

- 기능 구현을 넘어서 더 좋은 구조를 만들기 위해 코드를 오랫동안 들여다보았다. 한 번 리팩토링을 마쳤던 코드들도 다시 보면 마음에 들지 않는 부분이 나왔다.
- 여러 차례의 리팩토링을 거치고 나니 처음보다 훨씬 체계적인 코드를 만들 수 있었다.
- 리팩토링에는 끝이 없는 것 같다. 앞으로도 자신의 코드에 쉽게 만족하지 않고, 끊임없이 고민하는 자세를 가져야겠다.

### 2. 다른 사람의 코드에서 발견한 새로운 방식을 적극적으로 적용해보는 자세

- 코드 리뷰나, 그룹/스쿼드 세션을 하면서, 생각치도 못했거나 처음 보는 방식으로 구현을 한 사람들을 볼 수 있었다.
- 예전에는 그런 것을 보면, ‘아, 이런 방식도 있구나’ 라고 머릿속으로만 생각하고 넘어가는 경우가 많았던 것 같다.
- 이번 주말 동안에는 그 중에서 인상적이었던 몇 가지 방식들을 내 코드에도 적용해보면서 리팩토링하는 시간을 가졌다. 직접 사용할 때만 느낄 수 있는 이점과 한계들을 체감할 수 있었고, 단순히 머릿속의 지식으로만 끝날 때보다 훨씬 깊은 공부를 할 수 있었다.
- 앞으로도 감상 수준에서 끝내지 않고, 능동적으로 흡수하고 적용해보는 습관을 들이고 싶다.

<br>

## Problem

### **1. 더 나은 구조를 찾는 과정에서 시행착오를 너무 많이 겪게 된다**

- 더 나은 구조를 찾기 위해서 리팩토링을 수 차례 진행했다.
- 결과적으로 처음보다 개선된 코드를 완성할 수 있었지만, 그 과정에서 많은 시행착오를 겪었다.
- 특히 두 가지 방식 사이에서 고민하다가, 양쪽을 여러 번 오가는 일들도 많았다.
- 수행한 작업들을 다시 되돌리면서 꽤 많은 시간이 소모되었다.

### **2. 예외 처리에 대해 뒤로 넘겨둔 부분이 있다**

- 기능 구현과 리팩토링에 밀려 예외 처리에 대해서는 나중으로 미뤄둔 감이 있다.
- 예외 처리도 기능만큼이나 서비스에서 중요한 부분이고 꼭 필요한 부분이다.
- 뒤로 미뤄두다보면, 예외 처리해야할 케이스들이 점점 늘어나고, 나중에는 기억하지 못해 놓치는 일들도 생길 수 있다.
- 404, 405, 500와 같은 기본적인 에러에 대한 대응들은, 미리 구조화해두면 이후 과정에서도 편하게 사용할 수 있다.

<br>

## Try

### **1. 무턱대고 리팩토링하지 말고 조금 더 신중하게 생각해보자**

- 코드로 일단 작성해보는 행동력은 좋지만, 불필요한 시행착오를 여러 번 경험할 필요는 없다.
- ‘더 좋은 구조일 것 같다’는 막연한 느낌만으로 명확한 기준 없이 접근하면, 오히려 혼란을 키우게 될 수 있다.
- 리팩토링을 하기에 앞서 전체 구조에 어떤 영향을 미칠지, 개선점은 무엇이고, 발생 가능한 부작용은 무엇인지 신중하게 생각해보고 실제 구현에 옮기자.

### **2. 다양한 예외 상황들을 미리 생각해보고 처리해두자**

- 가능하면 예외 상황들을 발견했을 때, 미리 조치를 취해두고 다음 기능으로 넘어가자.
- 정 그럴 수 없는 상황이라면, 적어도 주석이나 TODO 기능으로 무슨 문제가 있는지 확실하게 기록을 해둬서 나중에 놓치고 넘어가는 일이 없도록 주의하자.

# 3. 학습내용

## 자바에서 파일 읽기 - `File` vs `ClassLoader`

### 1. File 클래스 사용 방식

- `java.io.File`은 파일 시스템 상의 절대경로 또는 상대경로를 기반으로 파일에 접근
- OS 상에서 해당 경로에 실제로 존재하는 파일이어야 함

### 코드 예시

```java
File file = new File("src/main/resources/sample.txt");
BufferedReader reader = new BufferedReader(new FileReader(file));
```

### 장점

- 파일 시스템과 직접 연결되어 있어 외부 파일 입출력 처리에 적합
- 테스트 파일 등 개발 중 임시 리소스 접근에 유리

### 단점

- 배포 후 jar 파일로 패키징되면 상대경로 접근이 깨짐 → `File` 경로 기준이 애매해짐
- `src/main/resources`에 위치한 리소스를 직접적으로 읽을 수 없음 (컴파일 시 경로가 바뀜)

### 2. ClassLoader 사용 방식

- `ClassLoader`는 클래스 경로 (`classpath`) 상에 있는 **리소스 파일을 읽어올 때 사용**
- 주로 `.jar`로 패키징된 이후에도 안정적으로 파일 접근 가능

### 코드 예시

```java
InputStream inputStream = getClass().getClassLoader().getResourceAsStream("sample.txt");
BufferedReader reader = new BufferedReader(new InputStreamReader(inputStream));
```

또는 정적 컨텍스트에서는:

```java
InputStream inputStream = ClassName.class.getClassLoader().getResourceAsStream("sample.txt");
```

### 장점

- jar 파일 내에 포함된 리소스도 읽을 수 있음
- 리소스 파일을 classpath 기준으로 접근하므로 배포 환경에서도 일관된 동작 보장

### 단점

- 파일 경로가 classpath 기준이므로 디렉토리 구조나 위치를 잘 이해해야 함
- `null` 반환 가능성 있음 → 경로가 잘못되었을 경우 확인 어려움

### 비교 요약

| 항목 | `File` 방식 | `ClassLoader` 방식 |
| --- | --- | --- |
| 경로 기준 | 파일 시스템 경로 | 클래스패스 기준 (`src/main/resources`) |
| 파일 위치 조건 | OS의 실제 경로에 파일 존재 | classpath 상의 리소스 (주로 `resources` 폴더) |
| jar 배포 후 사용 | 경로 깨짐 가능성 | 정상 작동 |
| 외부 파일 접근 | 가능 | 불가 (jar 내부 파일만) |
| null 가능성 | (경로 잘못되면 예외 발생) | (경로 잘못되면 `null` 반환) |
| 주 사용 용도 | 외부 설정 파일, 로그 등 | 설정 파일, 정적 리소스, 템플릿 등 |

## 데메테르의 법칙(Law of Demeter)

- "최소 지식 원칙 (Principle of Least Knowledge)"이라고도 불림
    - "객체는 자신이 직접 알고 있는 객체에만 메시지를 보내야 한다"는 원칙
- "친구의 친구에게 말하지 마라" (Don't talk to strangers)
    - 자신이 직접 가지고 있는 객체에게만 메시지를 보내고, 그 객체의 내부에 있는 객체까지 접근하는 것은 피해야 한다.

### 예시 코드

**위반 예시**

```java
Order order = customer.getOrder();
String address = order.getDeliveryInfo().getAddress(); // 깊게 체인된 접근
```

→ 이 코드는 `customer` → `order` → `deliveryInfo` → `address`까지

너무 깊이 내부 구조에 의존하고 있어 LoD를 위반함

**개선 예시**

```java
String address = customer.getDeliveryAddress();
```

→ `customer` 클래스에게 직접 주소를 달라고 요청하도록 리팩토링

→ 내부 구조를 알 필요 없이 한 단계 객체와만 소통

### 적용 규칙

객체는 다음 중 하나에 해당하는 객체에만 메시지를 보낼 수 있다:

| 허용 대상 | 설명 |
| --- | --- |
| 자신 (`this`) | 자기 자신 |
| 자신의 필드 | 직접 가지고 있는 인스턴스 변수 |
| 메서드의 매개변수 | 호출 시 전달받은 객체 |
| 메서드에서 생성한 지역변수 | 메서드 내에서 생성된 객체 |

그 외의 객체 (ex. 필드의 필드, 반환값의 필드 등)는 "낯선 객체"로 간주하고 접근 금지

### LoD를 어겼을 때의 문제점

- 객체 간 결합도 증가 → 하나의 내부 구조 변경 시 ripple effect 발생
- 코드의 가독성 저하 → 객체 간 관계가 복잡하게 드러남
- 테스트 어려움 → 특정 객체의 내부까지 mocking 해야 함
- 객체지향의 캡슐화 원칙 위반 → 내부 정보가 외부로 새어 나감

### LoD 적용 시 주의할 점

- 무조건적인 적용은 과도한 위임 메서드를 양산할 수 있음
    
    → getter를 숨기기 위해 모든 정보를 위임하면 클래스가 비대해질 수 있음
    
- 적절한 추상화와 위임을 통해 객체 간 역할과 책임을 명확히 분리하는 것이 핵심
