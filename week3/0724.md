## 작업 과정에서 배운 것

### 1. 새로운 시각으로 코드를 검증받는 것의 중요성

오늘은 지수님께서 남겨주신 코드 리뷰를 읽어보면서, 코멘트를 남기고 다시 한 번 코드를 되돌아보는 시간을 가졌다.

작성 당시에는 별 문제를 느끼지 못했던 코드들이었는데, 처음 읽어보는 사람 입장에서는 어색하거나, 일관적이지 못하게 느껴지는 부분이 있었던 것 같다. 지적을 받고 나서 다시 읽어보니 수긍이 가는 영역이 있었다.

자신의 코드는 여러 번 읽고, 여러 번 직접 수정하기 때문에 그 과정을 거쳐서 변해왔는지 모두 알고 있다. 또, 약간 이상한 부분이 있더라도 이미 그것에 익숙해져서 문제를 잘 느끼지 못하는 경우도 많다. 하지만, 처음 보는 사람에는 그런 어색함이 오히려 더 적나라하게 드러나는 것 같다.

처음 읽어보는 사람들도 어색함을 느끼지 않을 만큼, 일관성 있고 명확한 코드를 작성하기 위해 더욱 노력해야겠다. 

<br>

### 2. 다른 분야의 입장에서도 생각해보기

종합프로젝트의 위치 기반 기능을 구상하면서, 실제로 사용할 API들을 조사하고 각각의 요청값과 반환값을 찾아보았다. 백엔드 입장에서는 비교적 익숙한 형식의 자료였지만, 기획/디자인 쪽에는 다소 생소하게 느껴질 수 있겠다는 것을 새삼 깨달을 수 있었다. API 문서의 주요 내용을 이해하기 쉽게 정리해보는 시간을 가졌다.

또한 사용자, 프론트엔드, 백엔드 각각의 입장에서 필요한 정보가 다르다는 점도 흥미로웠다. 예를 들어, ‘출발지에서 목적지까지의 경로를 찾는다’는 같은 목표가 있다고 했을 때,

- 사용자는 장소를 키워드 수준으로 입력해야 함
- 프론트엔드는 키워드의 검색 결과를 사용자에 보여주고, 한 곳을 선택하게끔 해야 함
- 백엔드는 최종적으로 선택된 출발지와 목적지의 경위도 좌표로 API 요청을 보내야 함

이렇게 각 분야에서 중요하게 생각해야할 데이터와 정보가 조금씩 달랐다.

사용자의 입력으로부터 우리가 목표로 하는 데이터를 만들어내기까지, 어떤 프로세스를 거칠지, 어떤 API를 활용할 수 있을지 정리했다. 기획/디자인, 프론트엔드, 백엔드 각 분야 별로 어느 영역까지만 신경쓰면 되는지 조금 더 명확하게 구분할 수 있었다.

## 어려웠던 점

### 1. 이미지 파일 처리

이번 미션에서는 이미지 업로드 기능을 구현해야했다. 

기존에는 HTTP 요청의 body를 `String` 타입으로 읽도록 구현되어 있었다. 단순한 폼 데이터 처리하기에는 전혀 문제가 없었다.

하지만, 이미지는 텍스트가 아니라 바이너리 형식으로 전송되기 때문에, 이를 문자열로 변환하면 데이터가 깨지거나 손실될 가능성이 높다. 이를 해결하기 위해 `HttpRequest`의 `body` 필드를 `byte[]`로 변경하고, `HttpRequestParser` 역시 `InputStream`을 통해 바이트 단위로 데이터를 읽도록 수정했다.

하지만 여기서 또 다른 문제가 발생했다. 헤더를 읽는 부분은 여전히 `BufferedReader`를 사용하고 있었기 때문에, 내부적으로 `InputStream`을 읽으며 버퍼를 소진해버리고 있었다. 이로 인해 헤더를 읽는 과정에서 이미 body 부분까지 읽어버려, body를 정상적으로 읽지 못하는 문제가 있었다.

결국 헤더 부분까지 `InputStream` 기반으로 읽도록 `HttpRequestParser`의 전체 코드를 수정해야했다. 문자열과 비교했을 때, 바이트가 다루기 더 복잡하기 때문에 쉽지 않은 작업이었다. 

이전 미션에서 `body` 필드를 처음 만들 때, `String`으로 할지, `byte[]`로 할지 고민했던 기억이 떠올랐다. 당시에는 두 가지 방식을 모두 경험해보고 싶어서, `byte[]` 방식으로 한 번 구현해보고 `String` 방식으로 바꿨었다. 지금에 와서 다시 `byte[]` 방식으로 바꾸려니 정말 큰 작업이었다. 실제 프로젝트였다면 가볍게 넘어갈 부분이 아니었던 것 같다. 처음부터 확장성과 유연성을 고려한 구조로 설계하려는 자세를 가져야겠다.

# 2. 회고

## Keep

### **1. 다른 종합프로젝트 팀과 고민 공유하기**

- 점심시간이나 여유 시간이 생길 때, 다른 팀들은 프로젝트를 어떻게 진행하고 있는지 자주 이야기 나누었다.
- 내가 고민하고 있는 부분들을 다른 팀에서도 비슷하게 고민하고 있다는 것을 알 수 있었다. 혼자만의 어려움이 아니라는 점에서 위안이 되기도 했다.
- 한편으로는, 다른 팀에서 고민하고 있는 부분에 대해 내 생각을 말해보면서 약간이나마 도움을 줄 수도 있었다.
- 비록 팀은 다르지만, 같은 역경을 헤쳐나가는 동료라는 마음으로, 프로젝트가 끝날 때까지 편하게 도움을 주고 받을 수 있는 관계가 되고 싶다.

<br>

## Problem

### **1. 클래스의 네이밍에 혼란의 여지가 있다**

- 지수님의 코드 리뷰에서 `HttpRequestParser`와 `CookieParser`, `KeyValueParser`에 대한 질문이 들어왔다.
- 모두 파싱을 하는 클래스들인데 `HttpRequestParser`는 싱글톤 객체로 관리하고, 나머지 두 클래스는 객체 생성 없이 유틸리티 클래스로 사용하는 이유가 뭔지 물어보셨다.
- `HttpRequestParser`는 `HttpRequest` 객체를 생성하는 주요 로직을 담당하고 있기 때문에 유틸리티 클래스로 만들기 부적절하다고 생각했고, 나머지 두 클래스들은 `HttpRequestParser` 안에서 호출되어 단순히 문자열을 정제하는 작업만을 수행하므로 유틸리티 클래스로 만드는 것이 낫겠다고 생각했다.
- 다만, 세 클래스에 모두 Parser라는 단어를 사용하다보니, 비슷한 계층이나 역할에 속한다고 착각할 수 있겠다는 생각이 들었다.

### **2. 회고 작성에 점점 더 많은 시간이 걸린다**

- 매일 배운 점과 고칠 점을 찾아 회고를 작성하는 습관을 들이고 있다.
- 하지만 회고의 텀이 짧다보니, 새로운 인사이트가 개선사항이 떠오르지 않을 때도 있다.
- 회고를 쓰기 시작한지도 어느새 3주차이기 때문에, 이미 다룬 내용과 겹치지 않게 쓰기가 점점 힘들어지고 있다.
- 일정 기준 이상으로는 분량을 채워야 할 것 같다는 생각이 들어, 내용을 한참 고민하기도 한다.

<br>

## Try

### **1. 동작과 계층을 모두 고려하여 네이밍을 구분하자**

- 세 클래스 모두 파싱 작업을 수행하기는 하지만, `HttpRequestParser`는 `HttpRequest` 객체를 생성한다는 점에서, 정말 단순한 문자열 파싱만을 수행하는 나머지 두 클래스들과는 성격이 다르다.
- 그런데 모두 `Parser`라는 비슷한 이름을 붙여줬기 때문에, 처음 보는 사람의 입장에서는 비슷한 특성을 가졌거나, 같은 계층에 속한 클래스라고 오해할 수 있다.
- 클래스 이름만 보고도 그 클래스가 어떤 위치와 역할을 가지는지 파악할 수 있도록 네이밍에 신경쓰자.

### **2. 회고의 분량에 대해 너무 부담가지지 말자**

- 회고도 결국 성장을 위한 하나의 수단일 뿐이다. 회고를 위한 회고는 쓰지 말자.
- 배울 점이나 고칠 점이 하루에 몇 개씩 쏟아져나오기는 힘들다. 앞으로는 더욱 힘들어질 것이다.
- 분량에 강박을 가지지 말고, 적은 양이더라도 충실하게 작성해보려고 하자.

# 3. 학습내용

## **서버와 브라우저, 파일 시스템 간의 경로 해석 차이**

### 1. **브라우저: URL을 문자열 그대로 해석**

- 브라우저는 입력된 URL 문자열을 있는 그대로 해석하여 요청을 보냄
- 슬래시(`/`)를 경로 구분자로 인식하지만, 연속된 슬래시는 정규화하지 않음
    - 예: `/mypage////style.css` → 서버에 그대로 이 경로로 요청
- HTML 내부의 상대 경로(`../`, `./`, `folder/file`)도 현재 URL 기준으로 단순 계산
- **예시**
    - 현재 URL: `http://example.com/user////`
    - HTML 내부: `<link href="style.css">`
    - 브라우저 요청 경로 → `http://example.com/user////style.css`

<br>

### 2. 서버: 요청 경로를 어플리케이션 로직에 따라 해석

- 서버는 URI를 기준으로 라우팅하거나 정적 파일 경로로 변환
- 개발자가 작성한 로직에 따라 연속된 슬래시가 허용될 수도, 오류 발생할 수도 있음
- 정적 파일 처리 시에는 `File` 클래스를 사용해 OS 경로로 매핑하는 경우가 많음
- **예시**
    - 요청: `/mypage////style.css`
    - 라우팅: `/mypage/style.css`와 같이 완전히 다른 경로로 처리할 수 있음
    - 정규화 미흡 시 → 404 오류 발생

<br>

### 3. 파일 시스템: 운영체제가 슬래시를 정규화

- 자바의 `File` 클래스나 OS 커널은 여러 개의 슬래시를 하나로 인식하는 경우가 많음
- 즉, `new File("/mypage////index.html")`은 내부적으로 `/mypage/index.html`로 해석
- **특징**
    - 윈도우: `\`를 경로 구분자로 사용하지만, `File` 클래스는 `/`도 지원
    - 유닉스/리눅스: `/`를 사용하며 연속된 `/`는 무시됨 (`////` → `/`)

→ 브라우저는 경로를 있는 그대로 요청하므로, 서버가 반드시 정규화 작업을 수행해야 함

→ 전처리 과정에서 경로 정규화 후 리다이렉트하는 방식이 안정적
